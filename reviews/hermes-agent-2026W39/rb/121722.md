Routing the policy lookup to the serving profile is the right fix for #121705, and migrating all six call sites consistently (including the `_resume_caller_is_admin` boundary) is good discipline. But "fail closed" currently only covers a **missing** routed config; a routed config that exists but declares no admin list still resolves to `enabled=False`, which is treated as *allow-everything* — so for that shape the change widens permissions instead of narrowing them.

### 1. Blocker — a routed profile with no `allow_admin_from` opens commands the launch profile gates

`policy_for_source` sets `enabled=bool(admin_ids)` (`gateway/slash_access.py:93`). No admin list for the scope ⇒ `enabled=False` ⇒ `is_admin()` returns True for everyone and `can_run()` returns True for everything (`gateway/slash_access.py:38-47`). That is the documented, deliberate "unconfigured installs are unaffected" default.

The new resolver passes the routed profile's config straight through (`gateway/slash_commands.py:225`), so when that profile declares the platform but lists no admins, it inherits precisely that allow-everything policy — while `_check_slash_access` short-circuits on `not policy.enabled` (`gateway/run_busy.py:1087`) and never reaches the `user_allowed_commands` list. Reproduced through the real dispatch gate at this head:

```
routed 'beta' policy : enabled=False admin_user_ids=set()
central gate /restart   : ALLOWED      (launch profile: DENIED)
central gate /approvals : ALLOWED
boundary is_admin('mallory') -> True    -> "Only gateway admins can change the persistent
                                           approval mode." is NOT returned
```

The last line is the part that matters. `_handle_approvals_command` re-checks admin at a **side-effect boundary** precisely because, as its own comment puts it, "This mutates profile-wide security policy. The central slash gate can allow selected commands to non-admin users, so enforce admin again at this side-effect boundary" (`gateway/slash_commands.py:979-985`). That defence is `policy.is_admin(...)`, and it is void whenever the resolved policy is `enabled=False`. So a non-admin routed onto an ungated profile can flip the persistent dangerous-command approval mode. The same defeat applies to `_resume_caller_is_admin` (`gateway/slash_commands_session.py:308-310`), which is the guard for cross-origin session reads/resumes (`gateway/slash_commands_session.py:353`, `:371`, `:810`, `:929`, `:970`).

For contrast, on this PR's base the same caller is denied, because the launch config's admin list is what governs:

```
BASE: policy comes from launch config -> enabled=True can_run('restart')=False
```

So the behaviour difference is introduced by this change, not pre-existing. Note the fail-closed `SlashAccessPolicy` at `gateway/slash_commands.py:197-201` gets this right (`enabled=True`, empty sets) — the missing case is the sibling one, where the config is present but ungated.

**Fix:** treat "routed profile config exists but resolves to a disabled policy" as fail-closed rather than passing it through, i.e. after `policy_for_source(profile_config, source)` at `gateway/slash_commands.py:225`, return `fail_closed` when `not policy.enabled` and the launch profile's own policy *was* enabled. That preserves the intended "no admin list anywhere ⇒ everything allowed" default for single-profile installs (the `not multiplex_profiles` early return at `:195-196` already keeps that path untouched) while stopping a multiplexed runner from delegating to a weaker per-profile policy than the one it had. A test asserting `/approvals` and `_resume_caller_is_admin` on a gated launch profile + ungated routed profile would pin it.

### 2. Non-blocking — the primary branch compares against `""` when `_primary_profile_name` is unset
