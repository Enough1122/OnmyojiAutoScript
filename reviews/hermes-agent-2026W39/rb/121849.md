### 1. Blocker — `is_compression_edge` returns False for edges created by `publish_compression_child`

The new shared definition requires the child to start at or after the parent ends:

```python
# hermes_state_common.py:314-316
parent_ended_at, started_at = parent.get("ended_at"), child.get("started_at")
return (parent.get("end_reason") == "compression" and parent_ended_at is not None
        and started_at is not None and started_at >= parent_ended_at)
```

But the canonical compression path stamps them in the opposite order, inside one transaction (`hermes_state_compression.py:230`):

- `_publish_child_session_row` INSERTs the child with `started_at = time.time()` (`hermes_state_compression.py:227`)
- **later in the same transaction**, `UPDATE sessions SET ended_at = ?, end_reason = 'compression'` stamps the parent (`hermes_state_compression.py:306-308`)

So on every real rotation `child.started_at < parent.ended_at`. Reproduced through the repo's own `publish_compression_child` at this head:

```
parent ended_at : 1790346244.678652 end_reason: compression
child  started_at: 1790346244.67778
child.started_at >= parent.ended_at ? False   (delta = 0.000872s)
is_compression_edge(child, parent) -> False
```

The gap is sub-millisecond, so it is not a theoretical margin — the ordering makes `>=` false **always**. Consequences at this head:

```
compression root for s_c = s_c     (full lineage root = s_p)
session_search(query="quokka") -> 2 hits: ['s_c', 's_p']
base tree (130b8f2c)       -> 1 hit : ['s_p']
```

That is the exact symptom #121831 is about, reappearing on the compression axis: one conversation now yields two hits, and `_hydrate_hit` labels the continuation from its own row (`tools/session_search_tool.py:355-361`) so the second hit has `title=None` — the "hit wearing no title" shape the PR set out to remove, just moved to a different edge. Same script against the PR base folds to one hit, so this is introduced by the change under review, not pre-existing.

This test is not new logic — it is the *old* one that `hermes_state_compression.py:653-660` deliberately removed:

> "The old `child.started_at >= parent.ended_at` test was too brittle (gateway + compression races insert the real continuation before `ended_at` is written, while a stale websocket later creates a sibling that passes it). Instead exclude branch/delegate/tool children and prefer children that continue the chain or are still live…"

`get_compression_tip('s_p')` and `get_compression_lineage('s_c')` agree the edge exists (`['s_p', 's_c']`), because that walk keys on `end_reason = 'compression'` plus the fork/delegate/tool exclusions (`hermes_state_compression.py:29-49`, `:681-687`) and never consults the timestamps. So the two surfaces now disagree in the other direction: state folds correctly, search splits.

**Fix:** drop `started_at >= parent_ended_at` from `is_compression_edge` and use the exclusions the state package already trusts — `end_reason == "compression"` on the parent, and the branch/delegate/reset/tool markers on the child (`model_config.$._branched_from` / `$._delegate_from` / `$._reset_from`, and `source != 'tool'`, as in `hermes_state_sessions.py:458-463`). That keeps the `/new` case you are fixing — a reset child carries `_reset_from`, so it is excluded — while recognizing real rotations. Reusing `get_compression_lineage`/`_is_compression_child_row` semantics directly would also remove the duplicated rule entirely.

Note this changes the router too: `hermes_cli/web_routers/sessions.py:310` now shares this predicate, so `/api/sessions/search` gains the same regression. Worth confirming against the dashboard surface before merging.

### 2. Non-blocking — the new test hand-crafts an ordering production never produces, which is why it is green

The control case at line 1092 therefore passes by construction and cannot detect finding 1. Seeding the continuation through `db.publish_compression_child(...)` (or leaving the timestamps to the DB) would make the control case reflect reality.
