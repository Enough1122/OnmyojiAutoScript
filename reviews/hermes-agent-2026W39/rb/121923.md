Reviewed at head `3156772f`. The design rationale is sound and the prompt-immutability invariant is the right constraint, but the whitelist is expressed in **transport-agnostic names applied to a per-transport payload**, and `api_kwargs` is not in a single wire vocabulary. On the two most-used modes this either hard-fails the request or silently does nothing.

### 1. Blocker — three of the four whitelisted keys crash every `codex_responses` request

`_MUTABLE_REQUEST_KEYS` (`agent/turn_api_request.py:47`) is `{"reasoning_effort", "max_tokens", "temperature", "top_p"}`, and `_apply_request_mutations` writes them verbatim into `api_kwargs` (`agent/turn_api_request.py:50-72`, called at `agent/turn_api_request.py:125`).

But `api_kwargs` for `api_mode == "codex_responses"` is a **Responses-API** payload built by `ResponsesApiTransport.build_kwargs` (`agent/transports/codex.py:710-720`) whose vocabulary is `model` / `instructions` / `input` / `reasoning` / `max_output_tokens`. It carries no `reasoning_effort`, no `max_tokens`, no `top_p`.

Then `perform_api_call` re-runs the transport preflight over the mutated dict immediately before the call:

```python
# agent/turn_api_call.py:90-94
if agent.api_mode == "codex_responses":
    next_api_kwargs = agent._get_transport().preflight_kwargs(
        next_api_kwargs, allow_stream=False, is_github_responses=agent._is_copilot_url(),
        sanitize_harmony_tokens=agent._is_codex_backend(),
    )
```

`preflight_kwargs` enforces a closed allow-list and **raises** on anything outside it (`agent/codex_responses_adapter.py:924-927`, `:996-998`). Reproduced at this head:

```
reasoning_effort  -> ValueError: Codex Responses request has unsupported field(s): reasoning_effort.
max_tokens        -> ValueError: Codex Responses request has unsupported field(s): max_tokens.
top_p             -> ValueError: Codex Responses request has unsupported field(s): top_p.
temperature       -> survives (allowed at agent/codex_responses_adapter.py:914)
```

Failure path: a plugin registers `pre_api_request` returning `{"reasoning_effort": "low"}` (exactly the example in your PR description) → `_apply_request_mutations` adds the key → `perform_api_call` → `preflight_kwargs` → `ValueError` → propagates out of `_run_api_retry_loop` into `handle_api_error` (`agent/conversation_loop.py:1477-1490`). The retry loop **cannot escape it**: each attempt rebuilds the request via `build_api_request` and re-fires the hook, so the same key is re-added and the same `ValueError` recurs. The turn burns its full retry budget and then fails. A plugin that previously only observed can now take down every turn on Codex/Responses routes.

**Fix:** resolve each key to the current transport's wire name before writing, and skip what the active mode can't express — e.g. have `_apply_request_mutations` take the `api_mode`/transport and map `reasoning_effort` → `{"reasoning": {"effort": ...}}` and `max_tokens` → `max_output_tokens` for `codex_responses`, `max_tokens` → `max_completion_tokens` for modern OpenAI chat families (`run_agent.py:698-704`), and no-op for modes that don't carry the knob. The whitelist should describe *semantic* knobs and the mapping to wire names should be per-transport.

### 2. Blocker — the hook runs after the Astra route sanitizer and reintroduces fields that route rejects

`ResponsesApiTransport.build_kwargs` runs `_sanitize_astra_request_kwargs` (`agent/transports/codex.py:756`), which deliberately strips sampling knobs for the official OpenAI Responses/Astra route, *after* `request_overrides`, precisely so "an override can't put a rejected field back on the wire" (`agent/transports/codex.py:395-411`).

`_fire_pre_api_request_hook` runs **after** that, at `agent/turn_api_request.py:202`. So a hook returning `{"temperature": 0.2, "top_p": 0.9}` puts both fields back into the payload after the route contract removed them. Reproduced at this head:

```
after Astra sanitizer (build time): {}
after hook:                         {'temperature': 0.2, 'top_p': 0.9}
after preflight (send time):        ValueError: Codex Responses request has unsupported field(s): top_p.
```

The comment at `agent/turn_api_request.py:121-123` states the guard's intent as "a plugin's returned dict must never be able to abort the request" — but on this route the mutation is exactly what aborts it. The guard protects the *function call*; it cannot protect the *payload* from later validation. `temperature` is in `_PREFLIGHT_OPTIONAL_FIELDS` (`agent/codex_responses_adapter.py:914`) so it passes preflight and reaches the wire on a route whose documented contract is that sampling knobs are rejected.

**Fix:** run the same per-route sanitizers after the hook mutation (or restrict the whitelist to keys the active route already accepts). Concretely: re-apply `_sanitize_astra_request_kwargs`-equivalent filtering post-mutation, so a hook cannot widen what a route's contract allows.

### 3. Non-blocking — `max_tokens` is silently inert on modern OpenAI chat families

`_max_tokens_param` (`run_agent.py:698-704`) emits `max_completion_tokens` for direct-OpenAI / Azure / Copilot and for `gpt-4o`-era families, else `max_tokens`. A hook returning `{"max_tokens": 4242}` on such a route adds a second, unused key while the real cap stays put:

```
chat_completions built caps: {'max_completion_tokens': 32000}
after hook             : {'max_completion_tokens': 32000, 'max_tokens': 4242}
agent's cap read-back  : 32000   (hook asked for 4242)
```

The plugin's intent is dropped with no log — `_apply_request_mutations` logs at INFO that it "set" the key (`agent/turn_api_request.py:69-72`), so the log line actively misleads. This is the silent-failure half of finding 1: a plugin author sees a success log and a well-formed request, and the routing never takes effect.

**Fix:** same mapping as #1; when a hook asks for a knob the active mode cannot express, either log at WARNING that it was dropped or apply it to the correct wire key.

### Minor

- The tests only cover `api_mode == "chat_completions"` against a bare OpenRouter client (`tests/agent/test_pre_api_request_mutation.py:105-126`). That's why the Codex crash is invisible here: the suite never builds a Responses-shaped payload, so `preflight_kwargs` is never invoked on a mutated dict. A test that runs one turn with `api_mode="codex_responses"` and a hook returning each whitelisted key would have caught both blockers.
- `test_hook_rewrites_sampling_knobs_on_the_wire` asserts `kwargs["reasoning_effort"] == "low"` (`tests/agent/test_pre_api_request_mutation.py:152`) on a `chat_completions` payload. That assertion is correct *for that mode only*; as written it reads as a general statement about the wire, which is exactly the assumption the Codex path breaks. Worth a comment naming the mode the assertion is scoped to.

The whitelist approach, the non-dict tolerance, the separate mutation guard, and the docs updates are all good work. The gap is that the whitelist is a list of *conceptual* knobs while the payload it is written into is a *provider-specific* one; the mapping between them needs to be explicit rather than assumed.
