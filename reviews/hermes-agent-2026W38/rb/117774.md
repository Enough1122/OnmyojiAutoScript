## Overview

This PR bounds background-completion agent wakes with a per-session budget (default 8, `background_process_completion_wake_budget`, 0 = unlimited) plus a gateway-wide breaker (15/10s, 30s cooldown), collapsing excess completions into a single `completion_overflow` summary per scope. The direction is right and the tests cover both seams. The findings below are non-blocking robustness nits at the enqueue seam; the wake-capping behavior itself looks correct.

## Findings (non-blocking)

1. **Narrow `except` at the sole enqueue seam can skip `_completion_event.set()`** — `tools/process_registry.py:1572`. `_completion_wake_config()` catches only `(TypeError, ValueError, OSError)`, but it calls `load_user_config_effective()` + `cfg_get()`, whose failure modes (e.g. malformed-YAML errors, unexpected `AttributeError`/`KeyError` from a corrupt config) are outside that tuple. If it raises, `_enqueue_completion_wake` propagates out of `_move_to_finished` before `session._completion_event.set()` runs, so any thread waiting on the completion event hangs until its own timeout. Repro: corrupt the profile config such that config loading raises a non-covered exception, then complete a `notify_on_complete` job and observe the waiter. Suggested fix: catch `Exception` in `_completion_wake_config` (a budget misread must degrade to the default, never break completion delivery), and/or set `_completion_event` in a `finally`.
2. **Queued overflow summary dict is mutated after `put`** — `tools/process_registry.py:1585` (per-session) and `:1600` (global). The same dict object is enqueued once and then updated in place (`summary["count"] = ...`) on later suppressions. `queue.Queue` passes references, so a consumer that already dequeued the summary can observe a torn count, and the requeue path in `gateway/run.py:3052` may re-format a dict that is concurrently mutated by the producer thread. In practice the effect is cosmetic (a stale summary count in a notification), but the race is real. Suggested fix: enqueue an immutable snapshot (e.g. `dict(summary)`) per update instead of mutating the queued object; please confirm the consumer never relies on identity.
3. **Per-session wake ledger is never evicted** — `tools/process_registry.py:1571` (`_completion_wake_ledger.setdefault(...)`). One small entry accumulates per session key for the life of the gateway process. Growth is slow, but a long-lived gateway with high session churn leaks memory without bound. Suggested fix: prune ledger entries when their session leaves `_finished` (same TTL), or cap the dict size; at minimum please confirm an eviction path exists elsewhere.
