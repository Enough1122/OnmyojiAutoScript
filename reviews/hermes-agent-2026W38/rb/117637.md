This PR adds a completed-compaction frequency window to `ContextCompressor`: a new
`_compression_frequency_window` key persisted through `patch_session_model_config`, a
`frequency:<seconds>` block reason, and a gate in `_automatic_compression_blocked_locally()`
(agent/context_compressor.py) that refuses automatic compaction once 3 completed boundaries
fall inside 600s. It also classifies `frequency` as a transient guard
(agent/conversation_compression.py) and updates the status warning. The implementation is
coherent and matches the file's existing conventions: state is reset in both
`_reset_session_compaction_state()` and `bind_session_state()`, carried across a
compression rotation from the parent row, cleared when the window lapses, and covered by
two new tests (in-memory trip + restart persistence). Note the branch is ~120 lines behind
current main (`agent/context_compressor.py` context differs only by offset, semantics
unchanged), so a mechanical rebase is needed; line numbers below are this diff's post-image.

1. Non-blocking — the new guard also blocks the provider-proven overflow recovery path, and
   the deferral it produces tells the user the wrong thing.
   `agent/context_compressor.py:2740-2749`: the frequency check sits after the cooldown loop,
   so `ignore_cooldown=True` skips only the summary-failure cooldown — unlike the cooldown,
   which is bypassed for exactly this case (`bypass_cooldown=True`, see the contract in
   `agent/conversation_compression.py` `compress_context()`: "the provider already rejected
   the request, so deferring until the cooldown lapses wedges the session"). Consequence: a
   session that already compacted 3x in the window and then hits a real
   `context_length_exceeded` cannot compact again; the attempt is refused, the transient
   signal is set (agent/conversation_compression.py:1383), and the turn ends via
   `agent/turn_overflow.py:170-174` / `agent/turn_preflight.py:193-198` with the soft-defer
   result whose text (agent/conversation_loop.py `_compression_deferred_result`) is
   "Context compression is temporarily paused after a recent failed attempt. Please retry in
   a moment — compression will resume automatically (or run /compress to force a retry
   now)." For a frequency block nothing failed, and "in a moment" can be up to 600s
   (`_FREQUENT_COMPACTION_WINDOW_SECONDS`), so a retry reproduces the same message until the
   window lapses (`/compress` does work — `force=True` skips the gate, so the advice itself
   is sound). Please confirm the overflow-path behaviour is intended (the transient
   classification suggests it is); if so, a clause in the guard's comment and a
   frequency-aware defer text would save the next reader the same trace.

2. Non-blocking — the guard's window arithmetic is only exercised for the "already armed"
   direction. `_frequency_guard_remaining()` (agent/context_compressor.py:2175-2187) has a
   second branch at :2185 that clears the persisted state once the window has lapsed, plus a
   backwards-clock re-anchor at :2180-2182; neither is covered by the two new tests
   (tests/agent/test_compaction_anti_thrash.py:132-151 pins the trip and the reason string,
   tests/agent/test_compression_anti_thrash_persistence.py:74-86 pins restart inheritance).
   Given how much this codebase leans on "a guard must not be permanent", one test that
   advances `time.time()` past `started_at + 600` and asserts compaction is allowed again
   (and that the persisted key is cleared) would be cheap insurance.
