This PR adds an opt-in "Jev" triage router in front of `hermes kanban specify`: a new module `hermes_cli/kanban_triage_router.py` (177 lines) runs a fast/cheap classification call for triage tasks whose combined title+body length is under `auxiliary.triage_router.max_body_chars` (default 300), and a clean `TRIVIAL` reply auto-promotes the task with a templated minimal spec instead of paying for the full `triage_specifier` call (`hermes_cli/kanban_specify.py:200-211`). The DB side is a small, well-scoped extension — `specify_triage_task(..., event_extra=...)` merges extra keys into the single existing `specified` event (`hermes_cli/kanban_db.py:3487`, `:3537-3540`), with `payload or None` preserving today's exact payload for every existing caller. Config defaults, the CLI picker, four docs files and ~300 lines of tests (including an injection-framing test) are included, and every failure mode fails open to the unmodified full-specify path. The design is sound and the tests are above average for this campaign; the issues below are wiring gaps rather than logic bugs — nothing here regresses existing behaviour, which is why I am not calling any of them a blocker.

1. **The documented opt-in is unreachable from the dashboard/desktop Models page (HTTP 400).** `hermes_cli/main_provider_setup.py:64` adds `("triage_router", "Triage router", …)` to `_AUX_TASKS`, but the parallel canonical registry `_AUX_TASK_SLOTS` in `hermes_cli/web_server_config.py:532` — whose own comment says *"Canonical auxiliary task slots. Keep in sync with DEFAULT_CONFIG['auxiliary']"* — is not updated by this diff. Consequences: `POST /api/model/set` with `scope=auxiliary, task=triage_router` hits `web_server_config.py:777` (`raise HTTPException(status_code=400, detail=f"unknown auxiliary task: {slot}")`), and `GET /api/model/auxiliary` (`hermes_cli/web_routers/models.py:186`, iterates `_AUX_TASK_SLOTS`) never lists the slot, so the Models page has no row to click. That directly contradicts this PR's own docs, which tell users to "set `auxiliary.triage_router.model` to opt in" (`website/docs/user-guide/features/kanban.md:662`) and ship a copy-pasteable block (`website/docs/user-guide/configuration.md:1505-1510`). Repro: start the dashboard, `curl -X POST /api/model/set -d '{"scope":"auxiliary","task":"triage_router","provider":"openrouter","model":"typesafe/jev-latest"}'` → 400. Fix: add `"triage_router"` to `_AUX_TASK_SLOTS` (and the desktop i18n label table if the picker needs one), matching the `_AUX_TASKS` entry added here.

2. **`_ask_jev` omits the per-task relay-affinity scope that every sibling out-of-turn aux call site binds.** `hermes_cli/kanban_triage_router.py:118` calls `call_llm(...)` with no surrounding `set_affinity_scope`, while the four comparable call sites in this codebase all bind one for exactly this reason: `hermes_cli/kanban_specify.py:163-164` (`_call_aux`, comment cites the relay rejecting the call with 400 MissingSessionID, #112043), `hermes_cli/kanban.py:853-854`, `hermes_cli/goals.py:1657-1658`, and `tools/kanban_tools.py:405-406` (#113669). On an OpenCode-relay target the pre-check therefore resolves through `agent/opencode_affinity.py` to a fresh ephemeral `oneshot-<hex>` key instead of the task's sticky `kanban:<task_id>` session — so the router's call and the follow-up `triage_specifier` call are not on the same affinity scope, and if the #112043 rejection mode still applies to this transport the call fails outright. Either way the outcome is silent: the `except Exception` at `:129-136` logs at INFO and returns `None`, so `is_trivial()` returns False and the operator sees an opt-in feature that simply never fires, with no error surfaced in `hermes kanban specify --json` or the dashboard. Fix: wrap the `call_llm` in the same three-line `set_affinity_scope(f"kanban:{task.id}")` / `reset_affinity_scope(token)` guard used by `_call_aux`, or factor that guard into a shared helper both modules call.

3. **Auto-promotion path from untrusted, gateway-authored input — please confirm the intended trade-off.** The module docstring at `hermes_cli/kanban_triage_router.py:11-18` correctly states that titles/bodies arrive from Slack/Discord/Telegram, `kanban-act capture`, the dashboard and worker agents, none operator-authored. A clean `TRIVIAL` verdict at `hermes_cli/kanban_specify.py:200` then promotes that text to `todo` and, with no parents, `recompute_ready` flips it to `ready` immediately — i.e. a worker-claimable task produced from an untrusted one-liner, with only the ≤300-char gate (`:101-106`) and Jev's instruction-following standing between the two. The prompt-injection framing is reasonable and the fall-through default is conservative, but the classifier is the *only* gate, and `max_tokens=8` means the verdict is one token that a manipulative body is explicitly trying to steer. Suggest skipping auto-promotion when `task.created_by` is not an operator/local origin (or gating it behind an explicit `allow_gateway`-style key), so gateway-sourced tasks always take the full specify path.
