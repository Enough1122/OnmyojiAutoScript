1. `gateway/platforms/api_server_runs.py` (new-side line 619, `agent_kwargs=dict(..., interactive_run=True)` in `_handle_runs`) combined with `gateway/platforms/api_server_clarify.py::interactive_run_toolsets` means `POST /v1/runs` runs now get the `clarify` tool by default, not only clients that opted in (explicit toolset lists or a room policy that takes over remain an opt-out, but the new default is not stated in the docs). A run that calls `clarify` parks inside the tool until the clarify timeout, which defaults to 3600s and is *unlimited* when configured `<= 0` (`tools/clarify_gateway.py:259-284`), and for that whole time it holds one thread of the process-wide default executor (`await loop.run_in_executor(None, lambda: _run_agent_sync(...))` in the same handler). A client that posts a run and ignores `clarify.request` therefore pins a worker thread for up to an hour before the turn proceeds with "user did not respond"; several such runs saturate the executor and other endpoints queue behind them. `/stop` and shutdown do release the wait (`clear_run_clarify` -> `clear_session`), so this is not a leak — it is a reachable stall, and unlike the approval flow (which the client can see as a documented `waiting_for_approval` status and turn off through the approval policy) it is a tool that waits for a content answer with no equivalent opt-out. Non-blocking: consider making clarify opt-in per run (a request field or an `api_server` config gate) or clamping the clarify wait to something a chat client can survive, and state the new default in the `website/docs/user-guide/features/api-server.md` section added here (it currently documents the endpoint's semantics but not that it is now on by default).
