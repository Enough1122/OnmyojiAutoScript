This PR adds `hermes kanban boards archive` / `boards restore`: `remove_board(..., archive=True)` gains a dedicated verb, `kanban_db` grows archive discovery (`_archived_entry_slug`, `_archived_board_dirs`, `archived_boards`, `find_archived_board`, `restore_board`), `list_boards` appends `boards/_archived/` entries when `include_archived=True`, the CLI zeroes task counts for archived rows, both verbs are denied to delegated-child sessions (`hermes_cli/kanban.py:225`), and four tests cover the happy path plus the slug-taken/unknown-slug refusals. The design (dir rename, `board.json` slug authoritative, restore refuses a taken slug) is sound and the diff is small; the two findings below are both about the metadata an archived row is built from, not about the archive/restore mechanics. Findings 1 was reproduced on a scratch checkout of `upstream/main` + this diff (`git archive upstream/main` into a temp dir, `patch -p1`, then a stdlib probe with `HERMES_KANBAN_HOME` pointed at a temp dir).

1. **Archived entries are built from the *live* board path, so they show the wrong name / `db_path`** — `hermes_cli/kanban_db.py:666` calls `meta = read_board_metadata(_archived_entry_slug(d))`, but `read_board_metadata` resolves `board_metadata_path(slug)` = `boards/<slug>/board.json` (`kanban_db.py:536-538`, `:563`) — i.e. the live directory, never the archived one. The archived dir's own `board.json` (which the sibling helper `_archived_entry_slug` already reads directly at `kanban_db.py:633-636`) is ignored. Reproduced: `create_board("media", name="Media Stuff")` → `remove_board("media", archive=True)` → `archived_boards()[0]["name"]` is `"Media"` (synthesized Title Case), not `"Media Stuff"`, and `db_path` points at `boards/media/kanban.db`. Re-creating a live `media` named `"Live Media"` makes the archived row report `name == "Live Media"` — the archived copy borrows the live board's metadata and its `db_path`, which `boards list --all --json` and any dashboard consumer can read as if it were the archived board's. The CLI's new counts guard (`kanban_boards.py:56-59`) already works around this for counts, so the JSON path is the visible gap. Suggested fix: build the entry from the archive's own file (`json.loads((d / "board.json").read_text())` merged over the defaults, as `_archived_entry_slug` does) and stamp `slug`/`archived`/`archived_path` from `d`; set `db_path` to `d / "kanban.db"` (or drop it for archived rows). Edge case of the same root cause: a hand-made dir whose name parses to `""` (e.g. `_archived/-1`) is listed with an empty slug and the *default* board's metadata.

2. **The `-<ts>` fallback in `_archived_entry_slug` does not strip a timestamp when a `-<n>` disambiguator follows, and truncates genuine numeric slug suffixes** — `hermes_cli/kanban_db.py:643` (`re.match(r"^(.*?)(?:-\d+)?$", d.name)`) returns `"media-342134231"` for `media-342134231-1` (the double-archive name `remove_board` writes, `kanban_db.py:674-677` of the base file) and `"proj"` for a board legitimately named `proj-2024`; the docstring above it promises "the directory name minus a trailing `-<ts>`/`-<n>` suffix". Verified by running the patched helper on synthetic dirs. This only matters for dirs without a readable `board.json` (the PR's own test builds one — `tests/hermes_cli/test_kanban_boards.py:404-408`), because archive keeps the file, so it is non-blocking: either fix the docstring to say only one trailing `-<digits>` group is stripped, or make the archive dir name unambiguous (e.g. `--<ts>` separator or a marker file) so the fallback never has to guess.
