**1. The signature drops `st_ctime_ns`, the field the repo's own helper adds for exactly this writer class (non-blocking)**

`_profile_file_signature` (`hermes_cli/profiles.py:575-582`) keys on `(mtime_ns, size, ino)`. The codebase already has a canonical change-detection key, and it is deliberately four fields wide — `utils.file_signature` (`utils.py:38-47`):

> mtime + size alone miss a replacement that preserves both (`cp -p`, `rsync -t`, a tar restore, a script pinning the timestamp with `os.utime`). The inode changes on an atomic replace and **ctime cannot be backdated from user space**, so the pair catches those writers.

The inode leg does not cover that class on its own: `copy2` / `cp -p` write through an existing path in place (truncate, same inode) and restore the source mtime, so a same-length rewrite lands the identical `(mtime_ns, size, ino)` triple. That writer exists in this very module — `_clone_file` does `shutil.copy2(src, dst)` into an existing profile path, with `config.yaml` in `_CLONE_MATERIALIZE` (`hermes_cli/profiles.py:891`, `:899-902`).

To be precise about impact: I could not find an in-repo path that trips it today. The clone destination's seeded `config.yaml` is a small `launch_model_seed` dump while the source is the full file, so `size` differs and the read is refreshed; `write_manifest` and `write_profile_meta` both go through `atomic_yaml_write`. So this is hardening, not a live stale read — but the fix is one token (`file_signature(path.stat())`), and it also stops this key from being the one place in the tree that uses a weaker signature than `_RAW_CONFIG_CACHE` / `_LOAD_CONFIG_CACHE` (`hermes_cli/config.py:42`, `:219-220`). Worth noting the new tests cannot detect the difference: all three edit tests change the file length (44→56, 37→42, 46→39 bytes), so `size` alone satisfies them (`tests/hermes_cli/test_profile_listing_cache.py:37,56,65`); nothing pins the inode/ctime half of the key.

**2. A transient read failure is now memoised for the life of the process (non-blocking, smaller)**

`_read_config_model._read` swallows every exception and returns `(None, None)` (`hermes_cli/profiles.py:628-630`), and `_load_yaml_dict` returns `None` on any error; the memo then stores that negative result under the file's signature. A momentary failure — Windows sharing violation while another process replaces the file, an AV scanner holding it, a transient `EACCES` — therefore sticks: the signature only changes if something writes the file again, so the roster and `hermes profile list` can keep showing no model / no description for the rest of a long-lived process. The PR's own rule for the absent-file case argues the same for the failed-read case: "A missing file is never cached: reading it costs nothing, and one created later must be picked up" (`hermes_cli/profiles.py:585-587`). Skipping the memo (or storing nothing) when `compute()` reports failure would keep the saving for the common path and preserve the retry.
