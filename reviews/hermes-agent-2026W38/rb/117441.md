This PR adds two built-in prefix patterns to `agent/redact.py` — `GOCSPX-…` (Google OAuth client secret, line 159) and `1//…` (raw Google OAuth refresh token, line 211) — plus two regression tests in `tests/agent/test_redaction_registry.py`. The pattern shapes are otherwise sound: both start with a literal prefix, so `_PREFIX_SUBSTRINGS` (line 1249) stays false-negative-free, and both body classes stay inside `_TOKEN_BODY_CHARS`. I confirmed against a checkout of current main that the `GOCSPX-` shapes genuinely leak today and are masked with the patterns in place. Two gaps are worth fixing before merge.

1. **A control/zero-width-split refresh token still leaks verbatim** — `agent/redact.py:211` vs `agent/redact.py:573,620,930`.
   `_TOKEN_BODY_CHARS` (line 573) is documented as "union of every `_PREFIX_PATTERNS` body class", and `_mask_control_split_tokens` only re-masks a split match when the original span holds solely those chars plus controls (line 620). `1//…` is the first built-in whose *literal prefix* contains `/`, which is not in that set, so the span check rejects every `1//…` match and the control-split pass (line 930) never joins it; the contiguous pass (line 931) cannot cover the split case because the fragment before the control char is far below the `{35,}` floor.
   Reproduction (verified on main with only this PR's two patterns registered via `register_redaction_patterns`): `redact_sensitive_text("session dump line: token=1//" + "a"*20 + "\x1b" + "b"*20 + " end", force=True)` returns the token byte-for-byte unchanged (same result with a ZWSP instead of ESC), while the contiguous form is masked and the analogous `GOCSPX-…\x1b…` split *is* masked — the `/` in the prefix is the only difference. This is the same leak shape #77484 added that pass for, so a refresh token pasted from terminal output (ESC) or web content (ZWSP) bypasses the new pattern.
   Suggested fix: run the span check against the match body rather than the whole span (i.e. exempt the pattern's literal prefix), or allow `/` only in the prefix position. Widening `_TOKEN_BODY_CHARS` globally with `/` is the riskier option — on the join path it could bridge a token into a path/URL fragment.

2. **`test_builtin_prefixes_cover_google_refresh_token` does not pin the new pattern** — `tests/agent/test_redaction_registry.py:275-277` vs `agent/redact.py:211`.
   The test asserts only on `"refresh_token": "<fake>"`, a shape `_JSON_FIELD_RE` (line 426, applied at line 836) already masks by key name alone. Verified on current main with no `1//` pattern present: that input comes back as `"refresh_token": "1//aaa...aaaa"`, so the test is green before and after the change — deleting the pattern would not fail it, and a future regression of exactly this pattern would go unnoticed. (The sibling `GOCSPX-` test is fine: that value leaks on main, so it does pin its pattern.)
   Suggested fix: assert on a shape only a prefix pattern can catch, e.g. `redact_sensitive_text(f"dump line: {fake} end", force=True)` or a bare `Bearer <fake>` in prose, and keep the `1//refresh` floor assertion.
