**Overview.** This PR removes the `_CONFIG_LOCK` from the cache-hit path of `_load_config_impl` (`hermes_cli/config.py`) and memoizes `_resolve_hook_callback_timeout` on the config cache signature (`hermes_cli/plugins.py`), so a cached config read no longer serializes behind `save_config()`'s atomic YAML write, and the per-message hook path stops doing a full config read on the gateway event loop. The new tests (`tests/hermes_cli/test_config_lock_free_cache_hit.py`) drive the real functions against a temp `HERMES_HOME`, including a "read while another thread holds the lock" case and a concurrent reader/writer torn-config check — the premise (cache hits blocked behind a writer) and the mirroring of the locked path's cache-hit logic (indices `cached[:8]` / `cached[8]` / `cached[9]`, env-snapshot re-validation) are correct: `_load_config_cache_sig` returns 8 ints, so the fast path's slicing matches the locked path exactly. The findings below are all non-blocking, but two of them are behavioural changes worth an explicit decision.

1. **The fast path skips `ensure_hermes_home()`, which is not only an mkdir memo — it is also the named-profile tombstone guard.** `hermes_cli/config.py:2330-2339` returns before the `ensure_hermes_home()` call that the locked path performs at `hermes_cli/config.py:2345-2347`. That call is guarded by a comment ordering the check *before* the memo (`hermes_cli/config.py:712-716`, "Check tombstones BEFORE the memo so a stale empty shell cannot skip the deleted-profile guard") and runs `assert_named_profile_home_live(home)`, which raises `FileNotFoundError("Named profile home does not exist: ... Create the profile explicitly before using it.")` for a tombstoned-or-missing named profile home (`hermes_constants.py:309` on upstream/main). Repro path: a process bound to a named profile home primes the cache, then the profile is deleted — `mark_named_profile_deleted(profile_dir)` is written *before* the directory is removed (`hermes_cli/profiles.py:1497` on upstream/main; the code explicitly anticipates a "tombstoned-but-present" state), and the deletion path then does service stop / multiplexer notify / identity purge before the tree goes away. During that window `config.yaml` is still present with an unchanged stat signature, so `load_config_readonly()` now serves the cached config, where the pre-PR code (and any cache miss today) raises the guard error. The cached object is keyed by path, so there is no cross-profile value leak — this is guard consistency, not a data exposure. Suggested fix: call the memoized `ensure_hermes_home()` before the fast-path lookup (it is a dict lookup + `is_dir()` on the hot path), or at minimum run `assert_named_profile_home_live()` in the fast path. Please confirm whether skipping the guard is intended.

2. **The hook-timeout memo bypasses the env-ref invalidation the config cache deliberately implements.** `hermes_cli/plugins.py:1136-1145` keys the memo only on `_load_config_cache_sig()`, which is a pure file-stat signature (`hermes_cli/config.py:2238-2255`; `file_signature` = mtime/size/inode/ctime). The config cache itself never trusts the signature alone: `hermes_cli/config.py:2359-2361` (and the new fast path at `hermes_cli/config.py:2337-2338`) re-validates the stored env snapshot with `_env_ref_lookup`, precisely because a value expanded from `${VAR}` can change without the file changing (#58514 in the comment above it). The memo has no equivalent check. Repro: set `plugins.hook_callback_timeout: ${HOOK_TIMEOUT}` in `config.yaml`, let the first resolve memoize the expanded value, then change `HOOK_TIMEOUT` in-process — e.g. edit `.env` and call `reload_env()` (`hermes_cli/config.py:2773-2787`), which rewrites `os.environ` without touching any cache. Pre-PR, `_resolve_hook_callback_timeout()` → `load_config_readonly()` re-expanded and returned the new value; now the memo returns the old one until `config.yaml`'s stat changes. The same pinning can cross secret scopes in a multiplexed gateway: `_env_ref_lookup` resolves `${VAR}` per profile scope (`hermes_cli/config.py:1655-1669`, see the #84079 note), and the memo's key contains no path/scope component, so the first scope's value sticks. Suggested fix: fold the resolved values of the config's env refs (or at least the `plugins.*` subtree's snapshot) into the memo key, or re-run the env-snapshot check before returning a memo hit. Related: the docstring at `hermes_cli/plugins.py:1133` states "The value only changes when config.yaml does", which is not true for env-templated values — please align the comment with the intended contract.

3. **Torn memo read: `sig` and `value` are published separately and readers do not take the lock.** `hermes_cli/plugins.py:1142-1145` reads `_HOOK_TIMEOUT_CACHE["sig"]` and then `["value"]` outside `_HOOK_TIMEOUT_CACHE_LOCK`, while the writer sets `sig` first and `value` second at `hermes_cli/plugins.py:1149-1151`. A reader interleaved between those two stores sees the *new* signature with the *previous* value and returns it, i.e. one hook invocation runs with the timeout from the previous config revision. Impact is small and self-healing, but the fix is one line: store a single immutable entry under one assignment (`_HOOK_TIMEOUT_CACHE["entry"] = (sig, resolved)`), which is atomic under the GIL — the same "replace wholesale, never mutate in place" argument the config fast path relies on.

**Minor:**
- `hermes_cli/config.py:2340-2343` swallows every exception from the fast path with a bare `except Exception: pass`. That is the right failure mode (fall back to the locked path), but a genuine bug in the fast path becomes invisible. Consider narrowing the catch or emitting one `logger.debug` on the first fallback.
- Freshness window: the fast path stats the file and then returns the cached object, so a read that races a concurrent `save_config()` can return the pre-write config even though the write completed first (`hermes_cli/config.py:2335-2339`). Callers that write-then-read are unaffected (their stat sees the new file); only a read already in flight can be stale. Fine unless strict cross-thread read-your-write ordering is required — flagging so it is a decision, not an accident.
- `_reset_hook_callback_timeout_cache()` (`hermes_cli/plugins.py:1119-1123`) has no production caller, so the memo is not dropped by any reload path or by `_LOAD_CONFIG_CACHE.clear()`. Existing tests that clear only the config caches (see `tests/hermes_cli/test_plugins.py::test_hook_callback_timeout_reads_config`) now additionally depend on the new temp home's stat signature differing from the previously memoized one; wiring the reset into the reload path the docstring alludes to would make that dependency explicit.
