Heals a wedged checkpoint directory: when a git call against the per-project store index fails, `_run_git` now probes for an abandoned `<GIT_INDEX_FILE>.lock`, removes it if it is old enough to have no owner, and retries once (tools/checkpoint_manager.py:242-323), with a regression test for both the stale and the live case (tests/tools/test_checkpoint_stale_lock.py:40-64). The staleness heuristic is sound: every index-touching call is bounded by `_GIT_TIMEOUT * 2` (:612, :844) while `_STALE_LOCK_AGE` is `max(120, _GIT_TIMEOUT * 4)` (:64), the removal only ever targets the store index (a lock whose owner is a live `git add` in another process cannot reach the threshold), and the lock is only consulted after a failure. Both findings below are low-severity follow-ups to an otherwise correct fix.

1. **Non-blocking — the retry can raise where the first attempt never does** — tools/checkpoint_manager.py:313-319. The first attempt converts every unexpected failure into `(False, "", msg)` — `TimeoutExpired`, `FileNotFoundError`, and a catch-all `Exception` (:286-301) — but the retry after clearing the lock catches only `subprocess.TimeoutExpired`. Any other `OSError` (a transient fork/exec failure is the classic case) now escapes `_run_git`, which every caller treats as non-raising: `ensure_checkpoint` says "Never raises" and wraps only `_take` (:716, :734-737), while the tool-facing APIs `safe_restore_plan` / `_diff_staged_tree` (:690-698, :615-621) call `_run_git` with no broad handler, so a restore path can now fail with an exception instead of the `{"success": False, ...}` dict its callers expect. Suggested fix: hoist a single guarded `_attempt()` helper (same three handlers for both calls), or wrap the retry in the same `try/except Exception` as the first attempt.

2. **Non-blocking — only the index lock is healed; the same silent wedge remains for the store's ref locks** — tools/checkpoint_manager.py:935-938 (`update-ref`, no `index_file`) and :382 (the same call during index seeding). A git process killed mid-`update-ref`/`gc` leaves `refs/...lock` or `HEAD.lock` in the shared store, and because those calls pass no `index_file`, `_stale_index_lock` returns `None` immediately (:257-258) — so every later checkpoint of that directory keeps failing at the same step with the snapshot silently dropped, which is exactly the failure mode this PR's own docstring describes ("checkpoints are best-effort, so nothing surfaces to the user"). Either feed the store-level lock paths through the same probe, or state the index-only scope in `_stale_index_lock`'s docstring so the next reader does not assume the wedge class is covered.

Minor: the docstring says a live `git add` holds the lock "for less than `_GIT_TIMEOUT`" (:254-256) while `_stage_all` passes `timeout=_GIT_TIMEOUT * 2` (:612) — the 4× threshold still covers it, but the stated bound is wrong; also the probe runs on *any* non-zero exit, including the expected `allowed_returncodes` ones (`read-tree` → 128, `diff --cached --quiet` → 1), so an abandoned lock costs a second full git invocation on those paths too.
