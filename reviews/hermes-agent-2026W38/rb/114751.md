This fixes a real loss mode and is mostly well built: `_send_inner` (`plugins/platforms/wecom/adapter.py`) now retries a send that failed while the websocket was down, and fails closed as `send_path_degraded` when the 15s wait is exhausted — a genuine delivery-ledger token (`_RUNTIME_RETRYABLE_ERRORS` in `gateway/delivery_ledger.py`), with `_trigger_failed_obligation_redelivery` correctly reusing the existing `gateway_runner` / `_owner_profile` contract (`gateway/platforms/base.py`). The retry loop, the group-chat guard and the stale-req_id purge hold up. One problem with the transient marker set:

1. **`connection interrupted` and `websocket closed` do not prove non-delivery — retrying them can duplicate a message that was already delivered** — `plugins/platforms/wecom/adapter.py` (`TRANSIENT_SEND_ERROR_MARKERS`) — `_request()` writes the frame first and only then awaits the ack (`await self._send_json({...})` followed by `return await asyncio.wait_for(future, timeout=timeout)`), so a send whose ack future is failed by `_fail_all(RuntimeError("WeCom connection interrupted"))` from `_listen_loop` may already have been written to the socket and processed by WeCom; what was lost is the acknowledgement, not the message. The PR excludes timeouts for precisely this reason ("the frame may already have landed and a blind retry duplicates it"), but that reasoning applies unchanged to these two markers, which come from the post-write ack path rather than from a pre-write rejection. Only `846609` (server-side rejection carrying an errcode) and `websocket is not connected` (raised by `_require_ws` before any frame is written) are provably undelivered. Suggest narrowing the marker tuple to those two and letting the ack-path failures fall through to the existing fail-closed shape.

The duplicate-send path above is untested: `tests/gateway/test_wecom_redelivery.py` drives only 846609, so a send failed via `connection interrupted` after a successful write is never exercised.
