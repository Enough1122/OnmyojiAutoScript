## Findings

1. **The new gateway test module is POSIX-only but unmarked — both tests fail on Windows.**
   - `tests/gateway/test_loop_liveness_load_context.py:70` — `with patch.object(sw.os, "getloadavg", side_effect=OSError("unsupported")):`. `patch.object` defaults to `create=False`; Windows has no `os.getloadavg` attribute at all. Verified on this Windows 11 host, CPython 3.11.16 (win32): `hasattr(os, "getloadavg") is False`, and the identical call raises `AttributeError: <module 'os' (frozen)> does not have the attribute 'getloadavg'`. So the test written to exercise the missing-`getloadavg` fallback *errors* on the one platform where that fallback is real, instead of testing it.
   - `tests/gateway/test_loop_liveness_load_context.py:57` — `assert re.search(r"load1=[0-9]+\.[0-9]+", joined)`. On Windows, `_host_load_suffix()` (post-image `gateway/shutdown_watchdog.py:89-90`) takes the `AttributeError` branch and returns `load1=unknown ncpu=<n>`, so this assertion fails there as well. (The production fallback itself is correct — I confirmed the `unknown` path is what a Windows host would emit.)
   - Suggested fix: `patch.object(..., create=True)` (or `monkeypatch.delattr(os, "getloadavg", raising=False)`), and make the numeric `load1` assertion conditional on `hasattr(os, "getloadavg")` — or skip the module with the repo's OS markers (`tests/conftest.py` `_OS_MARKS`). Ubuntu CI lanes are unaffected; Windows developers running the full suite are not.

2. **`preexec_fn` is invoked in exactly the context CPython documents as unsafe.**
   - `hermes_cli/kanban_db_dispatch.py:2923` (`preexec_fn=priority_preexec,`) with the child-side hook at `:2447`. The call site is `_default_spawn`, reached from the in-gateway dispatcher: `gateway/kanban_watchers.py:256` ("tick runs `kanban_db_dispatch.dispatch_once` in a thread") → `gateway/kanban_watchers_dispatcher.py:189` (`_kbd().dispatch_once(...)`), and `kanban.dispatch_in_gateway` is `true` by default (`hermes_cli/config_defaults.py:1841`). So in the default configuration the hook runs in a forked child of a **multi-threaded** process, from a **non-main** thread — the documented `preexec_fn` hazard ("not safe to use in the presence of threads… the child process could deadlock before exec is called"). The hook body allocates Python objects (`getattr`, `os.sched_param(0)`), so an allocator/lock state inherited at fork is a live (if low-probability) risk; a child-side deadlock hangs the `Popen()` call itself, i.e. wedges the dispatch tick — the failure class this PR is otherwise about.
   - Repo policy points the other way too: `tests/tools/test_windows_compat.py:66` asserts guarded process-management files must not contain `preexec_fn` ("use `start_new_session=True` instead"), and `scripts/check-windows-footguns.py:220` documents the guarded-POSIX-call pattern. `kanban_db_dispatch.py` is not in `GUARDED_FILES` and the checker has no rule for `setpriority`/`sched_*`, so nothing currently fails — this is the tree's first production `preexec_fn`.
   - Suggested fix (pick one, please confirm intent): keep the hook but say in a comment why it is acceptable here (best-effort, no imports/logging/allocation-heavy work in the child); or apply priority from the parent on the returned pid (`os.setpriority(os.PRIO_PROCESS, proc.pid, 19)` immediately after `Popen` returns — the worker is a Python-interpreter startup away from its first fork, so the race window is small); or use the parent-side path when `dispatch_in_gateway` is on and reserve `preexec_fn` for the single-threaded entry points (`hermes kanban dispatch`, `run_daemon`).
