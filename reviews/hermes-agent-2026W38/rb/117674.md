This PR bounds how many MCP servers connect at once during discovery. `tools/mcp_tool_discovery.py` gains `_DISCOVERY_CONNECT_CONCURRENCY = 3` (line 27) and `_discover_all` now funnels every connect through a semaphore (`_connect_bounded`, lines 386–394); `_run_discovery_pass` scales its MCP-loop timeout to `120 * ceil(N/3)` (lines 418–419). `tests/tools/test_mcp_tool.py` adds `TestDiscoveryConnectConcurrency` (line 2773) pinning both the cap and the "a capped pass still connects every server" property. The core mechanism is sound — the semaphore is released on every exit path (`async with`), `gather(..., return_exceptions=True)` ordering and the failure/success bookkeeping are unchanged, and each connect keeps its own `connect_timeout` (default 60s, `tools/mcp_tool.py:233`), so the cap only bounds queueing, not per-server deadlines. The two notes below are non-blocking.

1. **The scaled pass budget now outlives the cross-process discovery lock's fail-soft wait, re-opening the unguarded-discovery window (#62771).** `discover_mcp_tools` holds the cross-process lock for the whole pass (`tools/mcp_tool_discovery.py:560` → `_register_mcp_servers` → `_run_discovery_pass`, line 504). A second process that cannot take the lock waits `_MCP_DISCOVERY_LOCK_MAX_RETRIES * _MCP_DISCOVERY_LOCK_RETRY_DELAY_S` = 240 × 0.5s = **120s** (`tools/mcp_tool.py:685`, retry loop at `tools/mcp_tool_discovery.py:516–519`), then logs "running discovery unguarded" (line 526) and discovers anyway. Previously the holder was hard-capped at 120s and, with the unbounded gather, realistically finished in ≈ the slowest single connect (≤ 60s default), i.e. inside the waiter's budget. With the cap of 3 the same fleet now takes `ceil(N/3)` waves: with N ≥ 4 and connects that run long (e.g. npx cold cache / registry stall, each still up to its 60s default timeout), the holder legitimately runs 120–240s+, the waiter gives up at 120s, and two processes spawn the same stdio servers concurrently — duplicate subprocess trees (the resource spike this PR targets) and the exact race the lock exists to prevent. Suggested fix: make the two numbers derive from each other — raise `_MCP_DISCOVERY_LOCK_MAX_RETRIES`/delay to cover the new worst-case pass duration, or keep an overall ceiling on the pass so lock-holding time stays bounded. Please confirm which bound is intended to be authoritative.

2. **No overall ceiling on the new timeout (robustness regression vs. the old hard 120s cap).** `120 * waves` (line 419) grows without bound in N — 30 servers → 20 min, 60 servers → 40 min — and `_run_on_mcp_loop` blocks the calling thread for that whole window while holding the lock. This only bites when connects outlive their own `wait_for` (e.g. the `except` path's `await server.shutdown()` at `tools/mcp_tool_discovery.py:289` hanging on a wedged subprocess), which is exactly the case the old flat 120s cap used to abort. Consider an explicit upper bound (e.g. `min(120 * waves, <a few minutes>)`) so a single stuck connect cannot pin the caller for tens of minutes; the existing timeout path (stale `_server_connecting` cleanup + cooldown) already handles an early abort gracefully.
