> AI code review — automated follow-up for reference; not a maintainer.

This PR adds emoji reactions to group-room messages: a new pure module `group-reactions.ts` (toggle + chip collapse + a 12-reaction cap), the strip/chip UI in `group-chat-view.tsx`, a `GroupReaction` type on `GroupMessage` in `types.ts`, a `react` label in all four locales, and tests (unit + one render test). The helper is well covered and its semantics are right — same emoji retracts, a different emoji replaces, one reaction per person, input never mutated — and the render test drives the real component end to end. Two things are worth fixing before merge; both are claims the code does not actually keep.

1. Reactions never leave this machine, but the new comments say they travel to every member.
   - Evidence: `group-chat-view.tsx:1081-1082` ("the room's normal persistence + sync carry it to every member") and `group-reactions.ts:10-11` ("Reactions ride the message itself, so they travel with the room log to every member exactly like the text does"). `group-reactions.ts:20-22` justifies the cap by the same idea ("the room log is synced through profile ui_meta with a byte budget").
   - Reality: the gateway/ui_meta mirror rebuilds every message field-by-field with a whitelist — `id`, `from`, `text`, `at`, `thread`, `truncated` — and never copies `reactions` (upstream/main `group-chat.ts:315-346`; the room's log is typed `GroupMessage[]` at `group-chat.ts:61-71`). The merge path keeps the local rich entry whenever the entry key already exists (`group-chat.ts:667`, `group-chat.ts:763-767`), so nothing is lost locally — the reactions simply are not projected.
   - Risk / repro: react on Desktop, then open the same room on the mobile/gateway surface (or another Desktop pulling the same profile's ui_meta): the messages arrive without any reaction and no chip ever renders. The cap rationale is off for the same reason — reactions are not in the ui_meta envelope, so `GROUP_REACTION_LIMIT` is not what protects that byte budget.
   - Suggested fix: either carry `reactions` through the projection (same slice/trim discipline as `text`/`thread`, and drop them first when the envelope is over budget), or correct both comments and the cap rationale to state that reactions are desktop-local for now.

2. `reactToEntry` addresses the log by render index, so a head-trim between paint and click writes the reaction onto the wrong message.
   - Evidence: `group-chat-view.tsx:1083-1092` — `log: current.log.map((message, at) => at === index ? {...} : message)` — called from the strip at `group-chat-view.tsx:1227` and from the chip at `group-chat-view.tsx:1250`. The index is the array position the render loop passes to `renderEntry(entry, index)`.
   - Risk: every `updateGroupChat` re-runs `trimGroupChatLog`, which head-drops the oldest entries once the retained log passes its character budget (`group-chat.ts`, `trimGroupChatLog`). If a member turn or any other room write drops entries between the paint and the click, `index` points at a neighbour and the reaction lands on a different message — silently, since the chip then renders on the wrong entry.
   - Suggested fix: carry the entry's identity into the handler (`entry.id`, else `at` + `from.name` + `text`) and resolve it inside the updater, the way other room writes key their target.

Minor:
- Chips you did not pick are `disabled` (`group-chat-view.tsx:1248`), so you cannot join an emoji someone else already used from the chip — only the strip can add. The 1:1 thread's picker allows it; consider letting a non-mine chip add your reaction (keeping the retract label for `mine` only).
- Hardcoded English aria-labels on an i18n'd surface: `Remove ${chip.emoji} reaction` (`group-chat-view.tsx:1242`) is not translated, while the react button does use `b.group.react` (`:1191`, `:1223`). A locale key for the retract label would match the rest of the pane.
- Cap semantics vs docs: `types.ts:173` says "Epoch seconds — newest wins when the per-message cap trims" and `group-reactions.ts:55` says "Trim oldest first", but trimming is by array position (`group-reactions.ts:56`) and a replaced reaction keeps its original slot (`group-reactions.ts:52`) — the dropped entry can be newer by `at` than one that is kept. Harmless at 12 entries; align the wording or sort by `at` before slicing.
- i18n wording: zh `回应` (`i18n.ts:977`) and zhHant `回應` (`i18n.ts:1228`) sit directly beside reply `回复`/`回覆` and read as "respond" rather than "react"; `表情回应` / `新增反應` would be unambiguous.
- The react affordance lives inside the hover toolbar, which only renders when `entry.text.trim() || !isUser`, so an image-only message from the human cannot be reacted to. Fine if intended.
