This PR adds `TeamsAdapter.edit_message()` (`plugins/platforms/teams/adapter.py:720-745`) so gateway streaming can update an already-sent Teams activity instead of falling back to fresh sends, plus two tests in `tests/gateway/test_teams.py:421-453`. The approach is the SDK-correct one: the activity is built with `MessageActivityInput().with_text(...)`, `activity.id` is set, and `App.activity_sender.send(activity, conv_ref)` is called — in the pinned SDK (`microsoft-teams-apps==2.0.13.4`, `microsoft_teams/apps/activity_sender.py:66-75`) a truthy `activity.id` routes to `activities.update(activity_id, activity)`, so this is an update, not a second create. The method also follows the file's existing conventions (`_conv_refs` lookup as in `_send_via_conv_ref`, `format_message`, `SendResult` with `retryable=True` on failure), and it is reachable: Teams does not set `SUPPORTS_MESSAGE_EDITING = False`, and `MAX_MESSAGE_LENGTH = 28000` (`adapter.py:344`) means the stream consumer caps/splits streamed payloads to that limit, so oversized-edit concerns are handled upstream. No blocker found; the item below is the only case I could not settle statically.

1. Edit target may not be the conversation the preview was actually posted to (channel threads) — `plugins/platforms/teams/adapter.py:732` + `:740`, compare `:705-707`.
   `edit_message` always updates through the cached conversation reference (`conv_ref = self._conv_refs.get(chat_id)`, cached in `_on_message` at `adapter.py:499` from the inbound `conv.id`), while the streaming preview is created by `send()` with `reply_to=self._initial_reply_to_id` (the inbound message id), and `send()` posts through `self._app.reply(chat_id, reply_to, chunk)` whenever `reply_to.isdigit()` — which Teams activity ids are. The SDK's `App.reply(conversation_id, message_id, activity)` forwards to `to_threaded_conversation_id(conversation_id, message_id)`, i.e. `…;messageid=<reply_to>` after stripping any existing `;messageid=` suffix (`microsoft_teams/apps/app.py:342-367`, `microsoft_teams/apps/utils/thread.py:8-27`).
   Risk: for a top-level channel post these ids coincide (`conv.id` already carries `;messageid=<post id>` and `reply_to` is that same id), but for a user message *inside* an existing channel thread, `conv.id` carries the thread root id while the preview is posted to `…;messageid=<inbound message id>`. The update in `edit_message` then targets the root conversation with a message id that lives in the threaded conversation; if Teams does not normalize that, the update fails, `SendResult(success=False)` sends the consumer into `_on_edit_failure` → fallback mode (preview frozen at partial text, answer tail delivered as a separate message). Group chats are unaffected — `send()`'s comment at `adapter.py:709` says threaded sends 400 there and the flat `_app.send(chat_id, chunk)` path is used, whose conversation id matches the cached ref.
   I could not verify this without a live Teams tenant, so please confirm rather than treat it as established: either exercise a channel-thread reply end to end, or make the edit target explicit by using the same threaded conversation id that `send()` used (e.g. route edits through `to_threaded_conversation_id(chat_id, reply_to)` when the preview was posted as a reply), and note in the docstring which chat types the edit path covers. A cheap guard would be to treat a failed update as "editing unavailable" explicitly (see Minor 2) so the degradation is visible in logs.

Minor:
- `plugins/platforms/teams/adapter.py:739` assigns `activity.id` directly; the SDK exposes the `with_id()` builder on the same model (`microsoft_teams/api/models/activity.py:111`, `id: Optional[str]` at `:71`), so `MessageActivityInput().with_text(...).with_id(str(message_id))` would match the chaining style already used at `adapter.py:598`.
- `plugins/platforms/teams/adapter.py:745` returns `retryable=True` for every exception, including permanent ones (deleted activity, stale conversation reference). `SendResult.retryable` is documented as "transient connection error — base retries automatically" (`gateway/platforms/base.py:1608`), and the Slack edit path pairs it with `error_kind="transient"` (`plugins/platforms/slack/adapter.py:2392`). Classifying with `classify_send_error(exc)` (`gateway/platforms/base.py:1666`) — e.g. `retryable=False` / `error_kind="not_found"` for 404s — would let callers branch without substring matching.
- Tests: the success case only exercises the mocked `MessageActivityInput` (`tests/gateway/test_teams.py:88` installs `MagicMock` for it), so nothing pins that a real `MessageActivityInput` accepts the `id` assignment — fine for this suite, just noting the SDK-level behavior is unverified by tests.
