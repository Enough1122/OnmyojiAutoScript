This PR adds an optional `connectionId` pin to `pluginRest`: `PluginRestOptions` gains the field (`apps/desktop/src/api/plugins.ts:44-50`), and the request object spreads the pin **after** `...profileScoped()` (`plugins.ts:91-92`) so it beats the ambient registry tag that `hermesApi` spreads underneath (`{ ...connectionScoped(), ...request }`, `apps/desktop/src/api/client.ts:145-147`), with an `opts.connectionId ? … : {}` guard so an absent pin never forwards `undefined` and clears that tag. Two tests in `apps/desktop/src/api/plugins.test.ts:11-40` drive `pluginRest` through a mocked `window.hermesDesktop.api` and assert the outgoing request for both the pinned and the unpinned case. The core mechanics are right, and the option reaches out-of-tree plugins without extra wiring (`contrib/plugin.ts:24` re-exports `PluginRestOptions`, `src/sdk/index.ts:1752` re-exports it again as `@hermes/plugin-sdk`). The two items below are scope/consistency gaps in the feature's semantics, not defects in the new lines; both are cheap to close and worth a decision before plugins start relying on the pin.

1. **The connection is pinned, but the window's ambient profile still rides along** — `apps/desktop/src/api/plugins.ts:91-92`.
   `...profileScoped()` (called with no argument, so it reads the ambient `_apiProfile`, `client.ts:66-73`) is spread *before* the pin, and `PluginRestOptions` (`plugins.ts:44-53`) exposes no `profile` field — so a caller can pin the connection but cannot neutralize the profile that the window's *own* gateway scope contributed. The codebase states the opposite rule for exactly this pairing: "a profile belongs to ONE gateway, so a Bot on another connection is (its connection, its profile) — never the active connection with the Bot's profile name" (`client.ts:75-84`, `ownerScoped`). Repro path: window is on the local pool with profile `work` selected; a plugin calls `rest('/outputs', { connectionId: 'hermes-vps' })`; the request that leaves the renderer is `{ connectionId: 'hermes-vps', profile: 'work' }`; main's `dispatchRegistryApiRequest` then calls `ensureRegistryBackend('hermes-vps', 'work')` (`apps/desktop/electron/main.ts:16733-16750`). On a host that has no `work` profile this is a loud 404, but on a host that happens to have a same-named profile the pinned plugin silently reads *that* profile's data while the UI believes it is reading the always-on gateway's own scope — the silent half is the problem. Suggestion: either state in the JSDoc that the ambient profile intentionally rides the pin, or accept an optional profile in the same pin (e.g. `{ connectionId, profile: null }` meaning "the pinned host's primary") so the caller can pin both halves together.

2. **`pluginSocket` cannot be pinned, so a pinned plugin splits REST and live events across two gateways** — `apps/desktop/src/api/plugins.ts:92` vs `plugins.ts:103`.
   `pluginSocket` still resolves its backend through `activeConnection()` (`plugins.ts:103`), which reads the ambient tag via `getApiRequestConnection()` (`plugins.ts:24`) — i.e. the window's active/primary connection, which the PR explicitly does *not* change. For this PR's own motivating case (a plugin owned by one always-on gateway, window active elsewhere), `ctx.socket('/events')` (`contrib/plugin.ts:223`) dials the *window's* gateway, not the pinned one: either the connect fails and the caller falls back to polling (benign, and the docstring already requires a polling fallback), or the same plugin id is installed on the ambient gateway and the UI renders another machine's event stream next to the pinned gateway's REST data. Suggestion: accept the same scope on the socket (`socket(path, onMessage, { connectionId })`, forwarded to `activeConnection`), or have `pluginSocket` refuse to connect when the plugin's REST calls are pinned, so the fallback is explicit rather than accidental.
