Ownership-alone vs. entry-shape gating is pinned by tests. Overall sound; both findings below are edge cases worth a look.

1. **Owned-but-unfenceable entries are never reclaimed** (non-blocking) — `main.ts:startPoolIdleReaper` routes to `retireIdle` whenever `teardownStopsBackend(entry, owned)` is true, but `pool-retire.ts` `retire()` immediately returns false for entries where `fenceable(entry)` (`Boolean(entry.process || entry.connectionPromise)`) is false. An entry with neither `process` nor a live `connectionPromise` whose scope is in `sshConnections` therefore returns false every reaper tick and never reaches `stopPoolBackend` — which, per this PR's own comment, is what kills the spawned serve and drops the entry. Reachability depends on whether a pool entry can lack both while the SSH connection is still registered (mode switches, failed connects) — suggest confirming; if reachable, fall back to `stopPoolBackend` when `ownedRemote && !fenceable(entry)`.
2. **`prepare()` awaits `connectionPromise` with no deadline** (non-blocking) — `pool-retire-http.ts` `request()`: `const descriptor = await entry.connectionPromise` has no timeout of its own; `timeoutMs: 3000` only covers the transport call after resolution. A descriptor entry whose connect never settles hangs `retireIdle`; the reaper's `void retiring.catch(...)` discards the pending chain and retries next tick, accumulating one pending promise per tick for a permanently hung connect. Suggest racing the await against a short timeout.
