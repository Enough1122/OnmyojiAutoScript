Two issues.

1. **Non-blocking: the ambiguity guard hangs on a substring of git's warning while `rev-parse` exits 0 and silently picks a winner** — `hermes_cli/kanban_db_workspace.py` (new `_resolve_start_commit`, the line `if result.returncode != 0 or len(commits) != 1 or "ambiguous" in stderr.lower():`, new line ~393). Verified on git 2.55.0 with both a branch and a tag named `ambiguous`: `git rev-parse --verify --end-of-options "ambiguous^{commit}"` exits **0**, prints the resolved sha on stdout, and emits only a *warning* on stderr (`warning: refname 'ambiguous' is ambiguous.`), resolving to the tag (`refs/tags/` precedes `refs/heads/` in `rev-parse`'s order). So the fail-closed verdict rests entirely on an English message substring. Two consequences: (a) the wording is a localized string, and `_git` (`kanban_db_workspace.py:38-46`) sets no `LC_ALL`/`LANG` for the subprocess, so under a translated git the guard can silently stop firing and the worktree is created from whichever ref git happened to prefer — a silent wrong base commit, i.e. the failure this whole guard exists to prevent; (b) it is coupled to output text rather than ref state. Suggested fix: resolve candidates explicitly and require a unique match, e.g. check `refs/tags/<ref>`, `refs/heads/<ref>`, `refs/remotes/<ref>` (plus a raw object id) with `rev-parse --verify --quiet` and raise when more than one distinct commit matches; or, minimally, pass `LC_ALL=C` in `_git`'s env and keep the warning check. The new tests (`tests/hermes_cli/test_kanban_worktree_start_ref.py`) pin the current behaviour and would keep passing either way.

2. **Non-blocking: a `start_ref` that travels to another machine via `kanban transfer` now hard-fails dispatch instead of degrading to HEAD** — `hermes_cli/kanban_transfer.py:272` (`UPDATE tasks SET workspace_path = NULL, branch_name = NULL`) scrubs host-local fields on import but necessarily leaves `start_ref` intact (it is a portable ref, correctly so), and the PR adds `start_ref="release/base"` to that round-trip test. `_resolve_worktree_workspace` then raises `ValueError` ("does not uniquely resolve to a commit in ...") for a ref that exists only in the exporter's repository — a different clone state, an unfetched tag, or a branch the importer never had. Before this change such a task started at HEAD; now it cannot be dispatched at all, with an error the operator has to trace back to a transferred board. This is a deliberate fail-closed choice, so it may be intended — but it deserves a documented escape hatch (clear `start_ref` on import, or a `kanban update --start-ref` path) since the transfer test now depends on the field travelling.
