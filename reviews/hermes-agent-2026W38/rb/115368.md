The latch being separate from notice delivery (so a flood-wait retry cannot re-inject) is a genuinely good catch, and the tests cover redirect/steer/decline/flood-wait. Two behavioural notes:

1. **Recovery cancels a live model request, reversing the watcher's documented "never kills the turn" contract** — 非阻塞. `redirect()` during a model request cancels that request and retries the loop (agent/interrupt_control.py:256-259), and the watcher docstring changed from "Notify-only: never kills the turn (contrast `gateway_timeout` / `shutdown_watchdog`)" to describing redirect-based recovery (gateway/run_watchers.py, `_session_stall_watcher`). Idle time is derived from `get_activity_summary()`, so a legitimately slow request that produces no activity — a large-context non-streaming call, a provider that buffers, a long reasoning pass — is indistinguishable from a wedged one and will be cancelled at the stall timeout (`session_stall_timeout: 300` by default, hermes_cli/config_defaults.py) and retried. The latch bounds this to one cancel per stall episode, so it is not a loop, but the retry discards that request's progress and can cost another full generation. If the agent exposes a "model request in flight / last delta age" signal, gating the inject on it (or using `steer()` for a request that is known to be progressing) would avoid cancelling healthy work.

2. **The latch is set even when the nudge was not delivered** — 非阻塞. `_inject_session_stall_recovery` writes `recovery_map[session_key] = True` both in the no-live-agent branch (gateway/run_watchers.py:161, for `None`/`_AGENT_PENDING_SENTINEL`) and unconditionally after the inject (run_watchers.py:165), regardless of whether anything was sent — `inject_session_stall_recovery` returns False when `redirect()` declines *and* `steer()` returns False (gateway/session_stall.py:69-77). The docstring frames this as deliberate ("latch immediately, independent of user-notice delivery"), and the user notice still goes out, so the cost is only that a genuine stall whose injection failed gets no second attempt until the pending event clears. Consider latching failed injections separately (keep a distinct "attempted" marker to prevent flooding) so a failed nudge can be retried.
