## Overview

This PR fixes real concurrency hazards in the Hindsight provider (client-construction orphaning, stale prefetch publishing across session switches, shutdown racing close). The approach — a client lifecycle lock, a prefetch generation fence, and retiring the client under the lock before closing — is sound and the new tests cover the advertised interleavings well. One residual race remains in the stale-daemon retry path itself (non-blocking).

## Findings

### 1. Concurrent stale-daemon retries can still orphan a freshly built client — plugins/memory/hindsight/__init__.py:553 (non-blocking)

**Risk:** `_run_hindsight_operation` publishes the observed-broken client through the shared `self._broken_client` attribute outside `_client_lock`, then calls `_get_client(recreate=True)`, which retires whatever is cached unless it differs from `_broken_client`. If two threads fail against the daemon at once, thread B can execute `self._broken_client = self._client` *after* thread A has already rebuilt and cleared the marker — stamping A's just-built client as "broken". B's recreate check (`self._client is not _broken_client`) then fails against the fresh client, so B evicts it, builds a second replacement, and the evicted client's aiohttp session is never closed. Thread A also keeps using the evicted client for its in-flight retry. This partially undermines the PR's own "exactly one replacement must ever be constructed" guarantee (which the new `test_retry_does_not_orphan_a_sibling_client` pins only for the readers-plus-one-retry case, not dual-retry).

**Fix:** Don't pass the broken-client identity through shared state. Capture it in a local (`broken = self._client`) and pass it as an argument to `_get_client(recreate=broken)` for the identity check, or set `_broken_client` while holding `_client_lock` so the stamp-and-retire pair is atomic against a sibling rebuild.

## Minor

- `_get_client`'s lock-free fast path (`if not recreate and (client := self._client) is not None`) can hand out a client that `shutdown()` is concurrently closing. This hazard pre-dates the PR (shutdown used to close `self._client` in place) and is out of scope, but worth knowing the lifecycle still isn't fully linearizable.
