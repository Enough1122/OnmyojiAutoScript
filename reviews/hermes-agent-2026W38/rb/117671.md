The direction is right, it matches how `_resolve_api_key_provider_secret` resolves registry provider keys, and the new test does drive the intended path (mocked pool `select() -> None` falls through to the rung-8 resolver; I traced the ladder, no test run needed). One substantive gap remains on the source helper the PR picked.

1. **The new call sites use the unguarded `get_env_value_prefer_dotenv`, so a raw `op://` reference in `.env` now shadows the resolved value and is sent to OpenRouter as the API key.**
   - Evidence: `hermes_cli/runtime_provider_backends.py:166-167` (post-image) now call `get_env_value_prefer_dotenv("OPENROUTER_API_KEY")` / `("OPENAI_API_KEY")`; `hermes_cli/config.py:2735-2738` implements it as `load_env().get(key) or _scoped_environ_get(key)` — the raw `.env` string wins with no guard. The credential pool's near-identical helper `agent/credential_pool.py:2573-2588` (`get_env_prefer_dotenv`) explicitly returns the scoped value when the `.env` value starts with `op://`, precisely so "every provider auth attempt" does not "receive a URL instead of a key".
   - Risk / repro path: a user with the 1Password integration (`OPENROUTER_API_KEY=op://Vault/Item/field` left in `.env`, while the resolved key is exported into `os.environ` at startup — see `website/docs/user-guide/secrets/onepassword.md` and `agent/secret_sources/onepassword.py:217+`; `override_existing` defaults true, "a stale .env line must not silently defeat it", `agent/secret_sources/onepassword.py:278-279`) hits an exhausted/benched pool — exactly this PR's scenario. Before: `get_secret_str` read `os.environ` and used the resolved key. After: the raw `op://Vault/Item/field` string is truthy, `has_usable_secret` accepts it (the placeholder checks at `hermes_cli/auth.py:294-306` do not match `op://`), and it becomes `runtime["api_key"]` → OpenRouter returns 401. The repo already pins the opposite precedence for this same variable: `tests/hermes_cli/test_env_loader_op_bootstrap.py:109-118` — "A raw op:// reference in .env must lose to the resolved os.environ value".
   - Suggested fix: read through the guarded helper (or lift the `op://` carve-out into `hermes_cli.config.get_env_value_prefer_dotenv`, which also protects its other call sites) and add a resolver-path regression test mirroring `test_credential_pool_prefers_resolved_env_over_raw_op_ref`.
   - Context: the same hazard already exists on main in `_resolve_api_key_provider_secret` (auth.py:363+, also `get_env_value_prefer_dotenv`), so this is a pre-existing gap in the shared helper rather than a new pattern — but this PR extends it to a path that previously read `os.environ` only, i.e. a behaviour regression for that configuration.
