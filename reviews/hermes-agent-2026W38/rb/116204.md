The findings below are cost/consistency concerns, not correctness failures.

1. **Non-blocking — every tool start of every delegated child performs a full SQLite write transaction on the shared session database.** `tools/delegate_tool_registry.py::_update_subagent_progress` (new function, called from `tools/delegate_tool_progress.py::_on_tool_started`) calls `_sync_shared_roster(record)` -> `tools/delegation_roster.py::publish_many`, which per call does `mkdir`, `_secure_state_db_files(create_main=True)`, a fresh `open_db` connection, a `DELETE`+`INSERT ... ON CONFLICT` transaction with `busy_timeout=200 ms`, and `_secure_state_db_files` again. The target file is the same `state.db` the transcript/FTS writer uses (`hermes_state.py:164 DEFAULT_DB_PATH = get_hermes_home() / "state.db"`), and the 1 s heartbeat (`_heartbeat_publish_once`) already republishes the whole live set, so the per-tool write buys sub-second freshness on `tool_count`/`last_tool` at the cost of a connection + write transaction + 3 metadata-repair calls per tool call (failures are swallowed with a warning, so a contended write silently skips the update). Suggest updating only the in-memory record on tool start and letting the heartbeat carry it to disk, or throttling the disk publish to the heartbeat interval.

2. **Non-blocking — the roster heartbeat is a bare `threading.Thread`.** `tools/delegate_tool_registry.py::_ensure_roster_heartbeat` starts `threading.Thread(target=_run_roster_heartbeat, daemon=True)`, which root `AGENTS.md` rules out for background work in favour of `agent.memory_provider.spawn_context_thread` ("or the worker runs with no scope and fails closed"). The PR compensates deliberately: each record carries `_roster_home` and `_snapshot` binds it via `_record_profile_scope` (`set_hermes_home_override`), which is what makes the vault redaction scope follow the record owner, and `list_live`/`publish_many` take explicit paths. Worth confirming that nothing else on that thread needs the wider runtime scope (secret scope / terminal policy) before this ships; if it does, the fix is one line at the thread start rather than a redesign.

Minor: `_snapshot` hardcodes `"status": "running"` while `list_live` filters `status='running'`, so today the persisted status column and its filter can never discriminate — fine as forward-looking shape, but the column is currently dead weight in the read path.
