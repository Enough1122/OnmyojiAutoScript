Both items below are edge cases, not blockers.

1. Empty User PATH is still written as `"<hermesBin>;"`, leaving an empty PATH element — scripts/install.ps1:3469
   `Set-UserPathRaw -Value "$hermesBin;$currentPath" -Kind $rawUserPath.Kind` runs with `$currentPath` empty whenever `HKCU\Environment\Path` does not exist yet or is empty (fresh profile, or a profile that never had a user PATH — the first-run case for this installer), producing e.g. `C:\Users\x\AppData\Local\hermes\bin;`. In POSIX-layer shells an empty PATH element means the current working directory, so Git Bash / MSYS / Cygwin users (which this installer explicitly supports — HERMES_GIT_BASH_PATH, `scripts/tests/test-install-ps1-gitbash-compatibility.ps1`) gain CWD on PATH in every new shell; Windows' own `CreateProcess` lookup ignores empty elements, so the blast radius is those shells and any tool that follows POSIX rules. Contrast `Set-ManagedNodeFirstOnUserPath` (scripts/install.ps1:1132), which writes a clean single entry in exactly this situation, and the new test covers the empty-PATH case only for `Add-UserPathEntries` (scripts/tests/test-install-ps1-user-path-raw.ps1:122-125) — the `Set-HermesBinOnUserPath` block (same file, lines 143-162) always seeds a non-empty value, so the case is untested. Suggested fix: `$newPath = if ($currentPath) { "$hermesBin;$currentPath" } else { $hermesBin }` plus one scratch-registry assertion for the empty value. (The shape is pre-existing, but this PR rewrites this line and owns the new test file.)

2. A non-string `Path` value silently reads as "empty", and the next write then replaces the user's whole PATH — scripts/install.ps1:1019
   `if ($value -isnot [string]) { return $empty }` maps an unreadable value to `@{ Value = ""; Kind = ExpandString }`. With, say, a REG_MULTI_SZ `Path` (uncommon, but some tooling writes one), every caller sees "no entries": `Add-UserPathEntries` / `Set-ManagedNodeFirstOnUserPath` / `Set-HermesBinOnUserPath` conclude every entry is missing, and `Set-UserPathRaw` overwrites the value with only the newly added entries — the user's existing PATH entries are dropped and the kind is flipped to REG_EXPAND_SZ. Static read of the helper; I did not reproduce it (needs a hand-built REG_MULTI_SZ value). Suggested fix: fold `string[]` in as `$value -join ';'` while keeping the real kind, or return a "do not write" flag that makes the callers skip the write instead of writing from an empty read.
