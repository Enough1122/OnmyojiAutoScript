The privacy contract holds — raw args/results/error messages are never written, only digests. However the tamper-evidence guarantee breaks on legitimately long runs.

**1. Receipts longer than the 64 KiB tail window fork the chain and make `verify` report a false tamper — blocker** — `plugins/run-receipts/receipts.py:44` (`_TAIL_BYTES = 64 * 1024`) and `_read_last_sha256` at `plugins/run-receipts/receipts.py:72-88`. The next record's `prev_sha256` is taken from `json.loads(lines[-1])` of only the last 64 KiB. If the previous record is larger than that, `lines[-1]` is a truncated fragment, `json.loads` raises, and the bare `except Exception: return GENESIS_PREV` silently resets the link to `"0"*64`. Reproduced locally against the PR's own `receipts.py`: a record with 500 tool-call entries (121 KB, well within a long autonomous turn — entries are ~200 bytes each and `tool_calls` is unbounded per run) followed by one more `write_receipt` leaves byte 2 carrying `prev_sha256 = 0000…0000`, and `verify_chain` then returns `ok=False` with `"line 2: prev_sha256='000…' does not match previous sha256 '99a68774…'"`. That is the plugin's central promise failing on its own output: a legitimate ledger is indistinguishable from a tampered one, and every subsequent receipt stays broken. Suggested fix: after reading the tail, only accept a parseable last line if the tail was not truncated at its head (or size <= `_TAIL_BYTES`); otherwise walk backwards a line at a time, or grow the window until the last complete line parses — and distinguish "unparseable tail" from "genesis" so a corrupt tail can never masquerade as the start of the chain.

**2. `verify` on a missing ledger exits 0 and prints "chain intact" — non-blocking** — `plugins/run-receipts/receipts.py:195-196` appends `"no receipts file found"` to `report["errors"]` but leaves `report["ok"]` at `True`. `format_verify` (`receipts.py:478-483`) then short-circuits on `ok`, so the operator sees `OK — 0 receipt(s), chain intact (<path>)`, and `_cli_handler` (`plugins/run-receipts/__init__.py:221-232`) returns 0. Verified by calling the function directly on a nonexistent path: `ok=True, errors=['no receipts file found']` → `"OK — 0 receipt(s), chain intact"`. The PR's own `test_verify_missing_file` (`tests/plugins/test_run_receipts.py`) asserts the error string but not `ok`, so the wrong exit code is unpinned. Set `ok = False` for that case (or have `format_verify` render the errors when `records == 0`).

**3. `test_concurrent_processes_do_not_fork_chain` cannot run on Windows — non-blocking** — `tests/plugins/test_run_receipts.py:321-339` passes a locally-defined closure (`_write_n`) as `multiprocessing.Process(target=…)`. On Windows the start method is `spawn`, which pickles the target: running the test file on Windows gives `_pickle.PicklingError: Can't pickle local object TestCommands.test_concurrent_processes_do_not_fork_chain.<locals>._write_n` and the test fails (15 passed, 1 failed in a local run). CI is unaffected because the Linux lane runs the file and the Windows lane (`tests-os.yml`) selects only `-m windows_only` tests — but this plugin explicitly implements `msvcrt` locking for `win32` (`receipts.py:102-106`, unlock at `:121-125`), so the platform is in scope. Move `_write_n` to module level (and pass the module path rather than the importlib-loaded module) so the test is portable.

Minor: `write_receipt`'s degraded path (`receipts.py:128-133`) appends without `flush()`/`os.fsync()` while the locked path fsyncs — an inconsistent durability guarantee for the one case where the lock was unavailable. Minor: `_pending_for`'s eviction (`receipts.py:237-241`) drops the oldest in-flight run at `_MAX_PENDING = 256`, after which `finalize_run` (`receipts.py:384`, counts assembled near `:423`) emits a receipt with `counts` all zero rather than marking it truncated; consider an `"evicted": true` flag so a zero-call receipt is not read as a real one.
