## Non-blocking

### 1. A mutation started for the previous scope still lands in the new scope's view — `apps/desktop/src/app/settings/custom-endpoints-settings.tsx:184` (also :264, :304)

The scope-change reset (:137-142) and the effect dependency (:173) only guard the *load* path — its `cancelled` flag. `handleSave` / `handleValidate` / `handleActivate` / `handleDelete` capture `scopeProfile` at render time and apply their result behind `mounted.current`, which is cleared on unmount only, never on a scope switch. So the response of a request issued for one profile is applied to the view of another.

Repro (two profiles): select profile A, click Save (or Delete) and switch the chip to B before the response lands — `setEndpoints(response.endpoints)` (:184 / :304) paints A's endpoint list, A's "saved"/"deleted" toast, and A's `onMainModelChanged?.()` under B's chip; the effect's own reset has already run, so nothing corrects the view until the next reload. `handleActivate` (:264) has the same shape, and its `refresh()` mid-handler re-reads the *new* scope while the follow-up callbacks describe the old one.

Suggested fix: capture the scope the request was issued for and re-check it at settle time (`$settingsRequestProfile.get()` or a ref), bailing out of the success, error and `finally` paths when it no longer matches.
