## Overview

This PR bounds `@`-reference expansion cost (per-branch byte budgets checked before materializing content, streaming subprocess caps, a 32-ref fan-out limit) and fixes a real shutdown race (#116535) where cancelling the awaiting handler task released the in-flight count while the executor worker thread kept running and could still touch `state.db`. Both halves are well-tested and a strict improvement. One residual race window remains in the new lease handoff (non-blocking), plus minor accounting nits.

## Findings

### 1. Residual shutdown-count race in the thread-start window — gateway/platforms/api_server.py:1259, gateway/platforms/api_server.py:1283, gateway/platforms/api_server.py:3877 (non-blocking)

**Risk:** `_adopt_api_worker` only increments the worker-owned count when the executor thread *starts* running `_run` (line 3877 is the first statement inside `_run`), while `_release_api_turn` (line 1283) releases the handler count as soon as the awaiting handler task is cancelled. If the handler is cancelled after the executor work item is queued but before the worker thread acquires `_api_worker_lock` in `_adopt_api_worker`, a shutdown snapshot in that window observes `active_agent_work_count() == 0` and `active_api_worker_count() == 0` and may close SessionDB handles just before the worker starts and touches `state.db` — the same use-after-close class as #116535. The window is microscopic (thread bootstrap vs. event-loop cancellation), and this PR strictly narrows the previous always-open hole, so this is not a blocker.

**Fix:** Hold the count across submission: increment `_active_api_workers` (or a separate "starting" counter folded into `_active_api_run_count`) under `_api_worker_lock` in the handler *before* `run_in_executor` submits, and let `_adopt_api_worker` convert rather than create the lease (worker entry decrements "starting" only if it added its own, exit path unchanged). Then a live-or-about-to-run turn is never uncounted.

### 2. Subprocess caps count characters, not bytes — agent/context_references.py:478 (non-blocking)

**Risk:** `_drain` accumulates `len(data)` from text-mode pipes, i.e. characters, and compares against `max_output_bytes`, a byte budget. For non-ASCII output (e.g. CJK diffs, up to 3–4 bytes/char in UTF-8) the worker can buffer several times the intended bytes before the kill triggers, loosening the GB-scale-allocation bound this PR is built to enforce. Same char/byte mixing in `_read_text_bounded` callers is harmless because `st_size` is bytes while the stream counts chars.

**Fix:** Count encoded size, e.g. `sizes[stream_name] += len(data.encode("utf-8", errors="replace"))`, or document that the cap is approximate for non-ASCII and size it accordingly.

## Minor

- `_release_api_turn` (gateway/platforms/api_server.py:1285) accesses `self._api_worker_lock` directly while `_adopt_api_worker`, `_enter_api_worker`, and `active_api_worker_count` all use the `getattr` fallback for partially-constructed adapters; unify on one pattern so a future non-`__init__` construction path cannot turn a handler `finally` into an `AttributeError`.
- `_read_text_range_bounded` allows `byte_budget + _INLINE_BYTES_SLACK` while `_read_text_bounded` enforces a bare `byte_budget`; the extra 512 chars are harmless but the two helpers should share one comparison so the budget means the same thing everywhere.
- `stream.read(_READ_CHUNK_CHARS)` on a text pipe blocks until the chunk is full or EOF, so on a slow trickle the cap reacts late; bounded in practice by the `proc.wait(timeout)` kill path, no action needed.
