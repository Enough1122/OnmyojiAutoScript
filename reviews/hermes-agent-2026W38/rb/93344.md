# PR #93344 — fix(mcp-oauth): try refresh_token before browser auth on 401 (Elliot-Construct)

## Follow-up 2026-09-25（maintainer 点名要求解释测试覆盖争议 → 实跑定论）

背景：我方 2026-08-26 指出「测试未覆盖 refresh-before-browser-auth 路径」，作者 08-29 反驳称已覆盖；09-24 mikeypotter 点名要求解释分歧。

**实跑证据**（worktree 检出 PR head `3accb6f8db`，`pytest tests/tools/test_mcp_oauth.py`）：

- `TestRefreshOn401::test_refresh_on_401_with_valid_refresh_token` **FAILED** —
  `tests/tools/test_mcp_oauth.py:1180` 断言 `mock_add_auth.await_count == 1`，但 `_add_auth_header` 是 **sync** 方法
  （mcp 2.0.0（仓库 `pyproject.toml` pin）与已装 1.28.1 中均为 `def` 非 `async def`）→ `patch.object` 产出 MagicMock，
  其 `.await_count` 是 MagicMock，`== 1` 恒假。该断言不可能为真，测试无法通过。
- `TestRefreshOn401::test_no_refresh_falls_through_to_browser_auth` 同样 FAILED（SDK `context.lock` 抛
  `RuntimeError: The current task is not holding this lock`），fall-through 预期与 SDK 实际行为不符。
- 结构上两个测试都 patch 掉 `_refresh_token` / `_handle_refresh_response`，只驱动 override 的分发逻辑，
  真实刷新失败、token endpoint 错误、重试请求的 Authorization 头未更新都不会被发现。

结论：生产改动（`tools/mcp_oauth.py` 的 401 先刷新 + 60s 安全边际）无问题；缺口是新路径**没有能通过的测试**。
建议：改 `.call_count`、断言重试请求确实带上新 Authorization 头、补「刷新成功但重试仍 401 → 浏览器授权」分支。
