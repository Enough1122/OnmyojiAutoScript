This PR closes two halves of the 2026-09-20 cron-store loss: a by-id three-way field merge in `cron/jobs.py` (`_record_load_baseline` / `_reconcile_job_fields` / `_reconciled_payload_jobs`, wired into `_merge_unexpected_disk_jobs`) so a stale whole-file writer no longer reverts `last_run_at`/`last_status`/`state` it never touched, plus a new append-only journal `cron/lifecycle_journal.py` (creates/removals recorded at the `create_job` / `save_jobs(removed_ids=...)` choke points) with a `check_vanished_jobs` guard surfaced through `hermes cron status` (`hermes_cli/cron.py`). The merge design is sound and well tested (284 lines of concurrency tests, including the "disk always wins" inversion and intentional-deletion cases), and the journal-hooked-at-choke-points argument holds: every intentional delete path (`cron/jobs.py:2352`, `:2656`, `:3359`) does thread `removed_ids`. Two issues below, one of which makes the guard's user-facing output wrong on a routine flow.

1. **Blocker — the vanished-job guard is fed an enabled-only view, so completed/paused jobs are reported as VANISHED.** `hermes_cli/cron.py:501` is the only production caller and passes `list_jobs(include_disabled=False)`, which filters out every job with `enabled` falsy (`cron/jobs.py:2021-2022`); the two new call sites hand that filtered list straight to the guard (`hermes_cli/cron.py:509` and `:545`). `check_vanished_jobs` builds `present` exclusively from the snapshot it is given (`cron/lifecycle_journal.py:289-292`), so "absent from this view" is indistinguishable from "absent from the store". Repro: `hermes cron create "in 5 minutes"` (journals a `created` record), let the one-shot run — `_complete_job_record` sets `enabled=False, state="completed"` while keeping the record (`cron/jobs.py:1684`) — then run `hermes cron status` within the 24h window: it prints the red `⚠️ cron jobs VANISHED with no matching removal: <id> (name)` line even though the job is intact on disk. `hermes cron pause <id>` (`cron/jobs.py:2195-2196`, also `enabled=False`) reproduces it just as well, and the `if not jobs:` branch (`hermes_cli/cron.py:509`) passes `[]`, which flags *every* journalled create in the window whenever the store currently holds no enabled jobs. Since the report's own contract says the vanished shape should "page #alerts", a routine pause/completion now produces a false page and trains operators to ignore the one signal this module exists to provide. Fix: reconcile against the whole store — pass `list_jobs(include_disabled=True)`/`load_jobs()` from `hermes_cli/cron.py:501` (or make `check_vanished_jobs` fall back to `load_jobs()` when the caller supplies a filtered view, e.g. by accepting an explicit `jobs` snapshot only for store-equivalent lists). `tests/cron/test_cron_store_concurrency.py:272` asserts this wrong behaviour (`_print_active_jobs_summary([])` must print VANISHED), so that test needs the same correction, e.g. drive the false-positive case with a paused job and assert the guard stays quiet.

2. **Non-blocking — `prune()` can silently drop audit records appended during its rewrite.** `prune` reads the journal (`cron/lifecycle_journal.py:172-184`), then rewrites it from the in-memory `kept` list via temp file + `atomic_replace` (`:187-196`), while `_append` (`:67-77`) takes no lock and opens the path in append mode. An entry appended between the read and the replace — or written to the old inode by an append whose `open()` preceded the replace — is lost. The guard calls `prune()` on every reconciliation (`cron/lifecycle_journal.py:331`), i.e. from plain `hermes cron status`, so the window is exercised routinely; a dropped `created` record blinds the guard to that job's later loss (the exact failure this module exists to catch), and a dropped `removed` record turns a legitimate deletion into a false VANISHED alarm from issue 1's surface. The rewrite only happens when something is past the 14-day retention (`:187-190`), which keeps the odds low, but the module's stated invariant is that audit records are never lost. Fix: hold an `flock` on the journal (or a sibling `.lifecycle.lock`) across prune's read-and-replace, and have `_append` take the same lock, or re-read/re-append anything with an `at` newer than the snapshot before replacing.

Minor:

- `tests/cron/test_cron_store_concurrency.py:205-211` makes the journal unreadable with `os.chmod(journal, 0o000)`. That is POSIX-only: on Windows `os.chmod` merely toggles the read-only attribute, the `open()` still succeeds and the assertion `status == STATUS_UNAVAILABLE` fails; running as root bypasses it on POSIX too. The Linux CI lane is unaffected, but the repo does support Windows (the `msvcrt` lock fallback in `cron/jobs.py`), so a monkeypatched `open`/`read_entries` failure would be more portable — please confirm the intended platform scope.
- In the verify-after-stage merge loop (`cron/jobs.py:1600`, up to `_SAVE_JOBS_MERGE_ATTEMPTS` rounds), round 1 may already have adopted a sibling's value for a field; on round 2 that adopted value differs from the unchanged baseline, so it is classified as "ours changed" and a *second* sibling update to the same field in the same window is downgraded to a logged same-field conflict instead of being adopted (`cron/jobs.py:1489-1535`). Low likelihood (needs two sibling writes inside one save, i.e. the degraded-lock path) — please confirm this is acceptable rather than re-baselining the adopted values between rounds.
