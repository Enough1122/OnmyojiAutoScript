## Overview

This PR fixes a real shutdown race (#116535): cancelling the request-handler task drops the handler-side `_inflight_agent_runs` count while the executor worker behind `run_in_executor` keeps running, so the SessionDB close gate could close `state.db` under a live writer. The module-level worker-lifetime counter (taken on submit, released in the worker's own `finally`) closes that hole, and the new test reproduces the exact cancelled-handler scenario. The design is sound; the two findings below are non-blocking robustness nits.

## Findings (non-blocking)

1. **Worker count leaks if `run_in_executor` submission raises** — gateway/platforms/api_server_runs.py:57. `_track_api_worker` increments `_API_WORKER_LIVE` at wrap time, before `loop.run_in_executor` is ever called (call sites: gateway/platforms/api_server.py:3895 and api_server_runs.py:828). If the submission itself raises (e.g. the executor is shutting down), `_counted` never runs and the decrement at api_server_runs.py:65 never fires, leaving a permanent +1 that makes the close gate skip the SessionDB close forever. The failure direction is fail-safe (skipping the close leaves handles open per #102198), but the counter never recovers. Consider incrementing lazily inside `_counted` before `fn()`, or wrapping the submit in try/except that decrements on failure. Non-blocking.

2. **New test asserts the release without waiting for the worker `finally`** — tests/gateway/test_shutdown_executor_quiesce.py:328. The test polls until `worker_done` appears in `events`, then immediately asserts `api_worker_live_count() == 0`. But `worker_done` is appended inside `_blocked_turn`, while the decrement happens afterwards in `_counted`'s `finally` (api_server_runs.py:65) — there is a small window where the event is present and the count is still 1, which can flake under load. Poll on the count itself (e.g. wait until `api_worker_live_count() == 0`, mirroring the existing style) instead of asserting it once after `worker_done`. Non-blocking.
