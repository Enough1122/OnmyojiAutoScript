Makes the unknown-model context fallback fail closed (`DEFAULT_FALLBACK_CONTEXT` 256K → 64K) and adds a one-tier step-down when a provider rejects a request against a window that was only *assumed* (`step_down_assumed_context_length`, wired into `_adopt_provider_context_limit`), kept ephemeral and out of the cache. The direction — assume the small window, never persist a guess — is right, and the "configured/probed windows never step down" tests are the right shape. Two consequences of the new 64K value are worth a maintainer's look.

1. **The step-down lands below `MINIMUM_CONTEXT_LENGTH`** — `step_down_assumed_context_length(64_000)` returns `get_next_probe_tier(64_000)`, i.e. 32_000 (`agent/model_metadata.py:1274-1283`; pinned by `tests/agent/test_context_fallback_fail_closed.py:88`), but `MINIMUM_CONTEXT_LENGTH = 64_000` (`agent/model_metadata.py:323`) and the comment this PR adds to justify the fallback says such a tier is not runnable: "Tiers below the minimum would trip _enforce_minimum_context and refuse to start, so 64K is the cheapest assumption the agent can actually run on" (`agent/model_metadata.py:299-304`). Nothing refuses at runtime, so the cost is subtler: the compressor is retargeted to a window the rest of the agent treats as sub-minimum — `_compute_threshold_tokens` has to clamp a floor larger than the window (`agent/context_compressor.py:2547-2557`) — and `ensure_compression_feasibility_checked` only fires once a request reaches `MINIMUM_CONTEXT_LENGTH` (`agent/conversation_compression.py:2095`), which a 32K session can never reach, so the aux-feasibility probe that #114707 added to land *before* the first compaction is skipped for exactly the sessions that are now most likely to compact. Suggest clamping the step-down at the minimum (return None), or saying in the docstring why 32K is acceptable here when it isn't for the fallback. (non-blocking)
2. **The fallback constant is now also a real value, so `== DEFAULT_FALLBACK_CONTEXT` misreads a genuine 64K detection** — the sentinel used to be 256K, which no resolver returned by accident; at 64_000 it collides with a real probe tier *and* the minimum, so every "we only guessed" comparison now also fires on a detected window: `hermes_cli/azure_detect.py:267` returns None (wizard reports "could not detect") for a detected 64,000, `hermes_cli/model_setup_flows_custom.py:48-52` prints "Context length: not detected — using the default 64K tokens" for the same value, and the `/status` provenance label degrades from `detected` to `default` (`gateway/run.py:2394-2395`). The PR already recognised this class of bug one site over and pinned the other sentinel where stale rows made it load-bearing (`agent/model_metadata.py:1601-1603`, "these rows were persisted when the fallback was 256K, so the threshold must not move with it") — these three sites were left comparing against a constant that just moved. Suggest a distinct sentinel (or returning None from the resolver for these callers) instead of comparing to the fallback value. (non-blocking)
