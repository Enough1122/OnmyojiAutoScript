1. **Blocker (policy conflict): a permanent `tirith:*` allowlist entry bypasses the documented session-max invariant** — `tools/approval.py:673-676`. The repository states the invariant twice and enforces it once: `_persist_choice`'s docstring says "Tirith findings are session-max by design (no broad permanent allowlisting of content-level findings)" (`tools/approval.py:381-383`) and its body refuses exactly this (`if choice == "always" and not is_tirith:` at `:388`, so "always" is downgraded to session), while the human-decision gate hides "Always" for pure-Tirith prompts (`permanent_capable=any(not is_t for _, _, is_t in warnings)` at `:1222`, comment at `:1215`). Content-level rules are the reason for the invariant: a pattern key describes a command *shape* the operator chose to trust, whereas `homograph_url` / `curl_pipe_shell` fire on whatever payload an attacker puts in the command, so a permanent entry for them is a blanket disable of the rule that reads like an ordinary allowlist entry. Note the stated justification does not hold: because of `:388` and `:1222`, the interactive flow can never write a `tirith:` key into `command_allowlist`, so `tirith:<rule>` entries can only have been typed into config.yaml by hand and were dead config until this PR (`grep -rn "tirith:"` finds no other producer). Requested action: either (a) treat the operator's explicit config entry as the intended policy and update the invariant comments, `docs`/`hermes_cli/tips.py` guidance and the pytest comment at `tests/tools/test_cron_approval_mode.py:286` ("Approving one dangerous pattern must not suppress an independent Tirith finding") in the same PR — the new test directly contradicts that comment's intent — or (b) keep unattended mode at session-scope-only, i.e. drop the permanent lookup here.
