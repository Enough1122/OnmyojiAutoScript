This PR adds a useful per-row boundary around the ready/review dispatch calls, but the review-lane reservation still evaluates rows before that boundary. As a result, the exact malformed-row failure this PR is meant to contain can still abort the whole pass when the poisoned card is in the review lane.

1. **The review preflight calls `check_respawn_guard` outside the isolation wrapper** — `hermes_cli/kanban_db_dispatch.py:2360-2369`, `hermes_cli/kanban_db_dispatch.py:2451-2455`.

   `_any_spawnable_review()` is called before the new `_dispatch_lane_task_isolated()` loop (`:2490`). It directly invokes `check_respawn_guard()` for every review row. If the malformed `task_runs.ended_at`/BLOB value from the incident is on a review card, the resulting `ValueError`/`TypeError` escapes here, before `_isolate_row_error()` can record it, and the entire dispatcher tick still fails. I reproduced the propagation by making the preflight guard raise `ValueError`; the new tests only exercise a poison row in the ready lane, so they do not cover this path. Please make the reservation pass use the same per-row containment (or explicitly skip/record a row that cannot be inspected) and add a review-lane regression with a sibling card that must still dispatch.

2. **`sqlite3.Error` is too broad for a row-local boundary** — `hermes_cli/kanban_db_dispatch.py:105-110`, `hermes_cli/kanban_db_dispatch.py:2090-2098`.

   `sqlite3.Error` includes `OperationalError`, so a database-wide `database is locked`/I/O failure raised by the claim or guard is caught as if it were a malformed single row. The handler then tries to increment that card's failure counter (and can eventually auto-block it), while continuing through the rest of a board that is actually unavailable. Please narrow the caught SQLite classes to the row-data failure being fixed, or explicitly re-raise operational/database-lock errors, and add a test that raises `OperationalError` inside the per-row call.
