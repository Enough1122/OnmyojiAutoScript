This PR narrows the Slack synthetic-thread drop (`thread_id == creating message id`) to jobs whose first fire is beyond a 60-minute horizon, so a near one-shot created from a top-level Slack message keeps the thread the assistant opened under it. The core change is coherent: the stamp only exists when `reply_in_thread` is on (`gateway/relay/adapter.py:965`, `plugins/platforms/slack/adapter.py:2754`), delivery does post with the kept thread as `thread_ts` (`cron/scheduler_delivery.py:633`), and I ran the head `_origin_from_env` against the production string path — `"in 30m"` keeps the thread; `"in 61m"`, `"in 2h"`, `"30m"`, `"every 1h"`, `"0 9 * * *"`, `"not-a-timestamp"` drop it. The gap is that the decision is made once, at create time, and nothing re-evaluates it.

## Non-blocking

### 1. The synthetic thread survives a later schedule edit, re-opening the bug the drop rule exists for — `tools/cronjob_job_args.py:77` (with `cron/jobs.py:1996`)

The keep/drop decision is taken from the schedule passed at creation and is never revisited. `cron.jobs.update_job` merges `{**job, **updates}` (`cron/jobs.py:2007`) and only re-derives `repeat` on a kind flip (`_rederive_repeat_for_schedule_change`, `cron/jobs.py:1933`); `origin` is never touched, and `_action_update` does not re-run `_origin_from_env`. So a job that legitimately kept the thread as a near one-shot keeps it after the schedule is rewritten to a recurring or far-future one — exactly the state the drop rule was written to prevent (#117306's predecessor).

Reproduced (create path produces this origin; update + delivery-resolution code read from the head tree, both modules untouched by this PR):

```
create schedule="in 30m"          -> origin.thread_id = 1755043010.123456
update schedule="every 1h"        -> origin.thread_id = 1755043010.123456
update schedule="2027-06-01T09:00:00" -> origin.thread_id = 1755043010.123456
_resolve_single_delivery_target(job, "origin")
  -> {"platform": "slack", "chat_id": "D0BJTDCSR7C", "thread_id": "1755043010.123456", ...}
```

Every subsequent fire is then posted as a thread reply under the creation message, silently, with no user-visible signal. Suggested fix: record the fact at capture time (`origin["thread_id_synthetic"] = True` when thread == message id, set in `_origin_from_env`) and drop the thread when the effective schedule no longer qualifies — either in `update_job` on a schedule change, or in the delivery-side `_origin_delivery_thread` (`cron/scheduler_delivery.py:593`), which also self-heals records already stored. A test that flips a kept-thread job to `"every 1h"` would pin it.

### 2. The new tests never exercise the branch production uses — `tests/cron/test_cron_origin_synthetic_thread.py:112-153`

`_action_create` passes the raw schedule string (`tools/cronjob_tools.py:604`; `CRONJOB_SCHEMA` declares `schedule` as `{"type": "string"}`), so the code that actually runs is the `parse_schedule(schedule)` branch in `_first_fire_within_thread_horizon` (`tools/cronjob_job_args.py:33-38`). Every new test passes a dict (`{"kind": "once", "run_at": ...}`) or `None`, so the parse integration is untested: a string that fails to parse, a relative `"in 30m"`, and a recurring `"every 1h"` all take the suppressed-exception / non-`once` paths that no test asserts on. The code is correct today (verified by running the strings above through the head function), but a regression in the string path would not be caught. Adding three string-schedule cases would close it.

## Minor

### 3. Two staleness heuristics for the same stamp, one hardcoded horizon — `tools/cronjob_job_args.py:19`

Capture side decides by schedule (`_THREAD_HORIZON_MINUTES = 60`, no config), delivery side decides by chat (`_origin_thread_is_stale`, `cron/scheduler_delivery.py:582`: origin chat == Slack home chat ⇒ thread ignored). The 60-minute value is a judgment call, not backed by any session/thread lifetime in the codebase, and an operator with long-lived Slack threads cannot widen it — worth a `cron.slack_thread_horizon_minutes` knob or at least a comment on where 60 comes from. Two heuristics for one concept will drift.

### 4. The rule lives in one of the two origin builders — `hermes_cli/blueprint_cmd.py:38` (pre-existing)

`_resolve_origin()` there copies `HERMES_SESSION_THREAD_ID` verbatim and feeds `fill_blueprint(..., origin=...)` → `create_job_with_scheduler_registration` (`hermes_cli/blueprint_cmd.py:216`, `:225`), so a job created from a top-level Slack message via `/blueprint` pins the per-message thread unconditionally. Not introduced by this PR, but the synthetic-thread rule now exists in only one of the two builders, which is worth a follow-up.
