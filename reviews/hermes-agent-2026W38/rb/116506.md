Makes the profile skill count (`_count_skills`, used by `profiles.describe`,
`hermes profile info` and the dashboard's `skill_count` via `_cached_skill_count`) count the
profile-local `skills/` dir PLUS `skills.external_dirs` read from the target profile's own
`config.yaml`, deduplicated by frontmatter name. The premise is real (external dirs were
invisible to the count) and the new tests pin the union/dedup/per-profile behavior. Findings
are cleanup and accuracy issues rather than blockers.

1. `_walk_skill_count` is now dead code (non-blocking). `hermes_cli/profiles.py:684` lost its
   only caller (the new `_count_skills` at `hermes_cli/profiles.py:732` inlines a
   `iter_skill_index_files` + `parse_frontmatter` loop instead), and the same PR rewrites the
   two test references (`tests/hermes_cli/test_profiles.py`, the spy on `_walk_skill_count`
   now spies on `_count_skills`). Verified on a patched copy: `grep -rn _walk_skill_count`
   matches the definition only. Delete it, or keep it if a caller is intended.

2. The cost model documented above the cache no longer matches the code (non-blocking).
   `hermes_cli/profiles.py:650-656` still describes counting as a walk at "~4 fs calls per
   skill", which is why the polled callers were made to never walk on the request thread. The
   new implementation reads and YAML-parses every `SKILL.md` and, per call, also re-reads the
   profile's whole `config.yaml` through the uncached `_load_yaml_dict`
   (`hermes_cli/profiles.py:553-561`, called at `hermes_cli/profiles.py:710`) — the runtime path
   uses the cached `get_external_skills_dirs()` (`agent/skill_utils.py:337`) for the same data.
   The count is display-only (`hermes_cli/profile_cmd.py:102`,
   `hermes_cli/web_server_profiles.py:131`, `hermes_cli/web_routers/profiles.py:678`), so this
   is a cost/latency regression on a polled surface, not a correctness one. Cheapest fix:
   parse frontmatter from a bounded read (the loader itself only parses the first ~4000 bytes,
   `tools/skills_tool.py:205`) and cache the per-profile config parse.

3. Relative `external_dirs` entries resolve against the wrong home (non-blocking).
   `_collect_skills_dirs` resolves entries with `_home_relative(_expand_path(entry))`
   (`hermes_cli/profiles.py:718`), and `_home_relative` anchors relative paths at the
   PROCESS-active `get_hermes_home()` (`agent/skill_utils.py:267-270`). Counting a named
   profile's row from `list_profiles` / the dashboard route (no profile scope is bound at
   `hermes_cli/web_server_profiles.py:131` or `hermes_cli/web_routers/profiles.py:678`) therefore
   resolves a relative entry such as `shared-skills` against the default home instead of that
   profile's home — the count can include or miss the wrong directory, which is the same class
   of misleading count the PR fixes. The new per-profile test only covers ABSOLUTE entries
   (`tests/hermes_cli/test_profiles.py:890`, `:914`), so nothing pins this. Suggested: resolve
   relative entries against `profile_dir.parent` (or bind the profile home for the duration,
   the pattern `_review_skill_missing` uses). Worth confirming against how the runtime resolves
   the same entry for a `-p <profile>` child.

   Consider "N available" (or keep "installed" and count only the local dir).
