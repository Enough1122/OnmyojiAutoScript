> AI code review — automated follow-up for reference; not a maintainer.

This PR teaches the lifecycle ledger to *name* the killer of an unclean gateway death: `gateway/lifecycle_ledger.py` gains a bounded, fail-open attribution probe (macOS `log show` parsing of launchd exit/bootout/spawn records; a Linux `journalctl`/`dmesg` analogue), folds the result into the unclean-exit evidence and the WARNING line, carries `prior_killer*` keys onto the new sentinel, and surfaces them through `gateway/memory_status.py`; `tests/gateway/test_lifecycle_ledger_kill_attribution.py` (326 lines) drives parsing, fail-open, the ledger line and the off-loop execution. The design is sound — every step is `int()`-coerced before it reaches a command line (no injection surface), per-call timeouts keep the probe bounded, and failure degrades to `killer=unattributed reason=<why>`. Three gaps below, all non-blocking but worth fixing before this is relied on: the probe is still invoked blocking on the event loop, the macOS search window is anchored on "now" rather than on the death, and the Linux branch's query cannot match the record it greps for.

1. **The blocking probe is wired into the event loop, and the async variant this PR adds has no production caller.** `record_startup` (gateway/lifecycle_ledger.py:478-493) now runs `_probe_attribution` inline at :488 — two sequential `subprocess.run` calls, each capped at `_KILL_ATTRIBUTION_STEP_TIMEOUT_S` (5 s, :33-36), so up to 10 s of wall clock. The only production call site is `gateway/run.py:5444-5454` (`_lifecycle_record_startup()` → `record_startup()`) inside `async def start_gateway` (run.py:5359) — i.e. the loop thread, right after the control socket is up (run.py:5443), in a function whose own comment a few lines later says blocking startup work is pushed to an executor "so the asyncio event loop stays responsive" (run.py:5457-5460, for `discover_mcp_tools`). The PR ships `record_startup_async` (:496-516) for exactly this and documents the contract at :324-325 ("Blocking (subprocess) — call it from a thread, not the event loop") and :482-483 ("From an event loop use record_startup_async instead"), but nothing calls it: its only callers are the two new tests (tests/gateway/test_lifecycle_ledger_kill_attribution.py:260, :279). Repro: any unclean previous exit → the next boot stalls the loop for the duration of both `log show` calls (typically 1-3 s each on a 4-minute window; 5 s each is the worst case), and the control socket is already serving requests at that point. This is not a liveness-watchdog risk (that needs 3 consecutive 10 s misses — gateway/shutdown_watchdog.py:36-43), but it is added boot latency on the loop thread for a diagnosis-only feature, and it makes the async half dead code until wired. Suggested fix: `await record_startup_async()` at run.py:5448 (or `_best_effort` a `lambda: asyncio.to_thread(record_startup)`), keeping the sync entry point for non-loop callers and tests.

2. **The macOS window is anchored on "now", never on the death, so a restart more than ~3 minutes after the kill is silently unattributed.** `_probe_attribution` (:405-411) passes only the pid (:408), so `when` stays `None` and `_macos_attribution` (:242-245) anchors on `datetime.now(timezone.utc)`, searching only `[now-3min, now+1min]`. The evidence dict already holds the death-side timestamps (`prior_started_at`, `last_heartbeat_at` — the same values the WARNING line at :437-442 prints). Repro: gateway is killed at 08:00 and the next life boots at 08:20 (manual restart after the user notices, a reboot, a suspended host) → the exit record is outside the window → `killer=unattributed reason=no_launchd_exit_record`, which is the majority of the "only 3 of 15 unclean exits attributed" cases quoted in the test docstring. The `when` parameter is effectively dead as shipped. Suggested fix: pass the heartbeat/started-at anchor (parsed with `datetime.fromisoformat`) into `attribute_unclean_exit`, and/or widen the window to the previous life's span when it is known.

3. **The Linux branch's primary query cannot match the line it greps for, and the branch has no test.** `_linux_attribution` (:283-311) runs `journalctl _PID=<pid> --no-pager -n 200` (:288-291) and then greps the result for `code=killed, status=9/KILL` (:294). That "Main process exited, code=killed, status=9/KILL" record is emitted by systemd (PID 1) *for the unit* — its journal fields are `_SYSTEMD_UNIT=`/`_PID=1`, not `_PID=<the dead gateway pid>` — so `journalctl _PID=<pid>` returns only the dead process's own stdout/stderr and the regex will not match; the branch then falls through to `no_journald_or_dmesg_record`. The OOM half is similarly best-effort: `dmesg --ctime` (:298-300) is unreadable under the default `kernel.dmesg_restrict=1` on most distros. Nothing in the new test file exercises `_linux_attribution` (the tests cover darwin and an unsupported platform only), so this ships unverified. Please confirm on a systemd host; suggestion: query `journalctl -u <unit>` (or `_SYSTEMD_UNIT=` / `OBJECT_PID=<pid>`) and add a unit test with captured `journalctl` output, mirroring the darwin end-to-end test at tests/gateway/test_lifecycle_ledger_kill_attribution.py:114.

**Overlap — only one of these two can land as-is.** #117711 rewrites the same `record_startup`/claim block in `gateway/lifecycle_ledger.py` (it inserts `_carry_prior_exit_forward(claim, home)` immediately after the `claim` dict literal, base line ~275, and also adds `prior_*` handling). This PR replaces that whole block with `_claim_sentinel(evidence, home)` (:446-475) — a textual conflict in the same region; the second to land needs a rebase. They are complementary in intent (#117711's `gateway/restart_notice.classify_prior_life` *consumes* `prior_killer`/`prior_kill_sender`/`prior_kill_sender_label`, which this PR writes), so the combined shape must keep both: the `prior_killer*` keys from here plus the prior-exit carry-forward from #117711.

Minor:

Either filter the parsed lines (e.g. require the `[pid]` label match) or drop the parameter, so the contract matches the behaviour; as written, a pid reused inside the 4-minute window could contribute a foreign sender.
