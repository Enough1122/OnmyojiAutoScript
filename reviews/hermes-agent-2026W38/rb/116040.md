This PR makes linked git worktrees inherit project-skill trust from their canonical repository: `_canonical_git_root()` walks `.git` → `gitdir:` → the gitdir's `gitdir` back-reference → `commondir` to name the parent repo, `is_project_root_trusted()` accepts that root, `hermes skills trust` stores the canonical root, and the docs/prompt-builder notice follow. The goal is legitimate and the mismatch/backref tests are a good instinct, but the verification only proves the git metadata is *self-consistent* — it never proves the worktree belongs to the trusted repository, so a directory the user did not trust can borrow trust from one they did.

1. **BLOCKER — forged worktree metadata borrows trust from any already-trusted repo.** `agent/skill_utils.py:465-536` (`_canonical_git_root`) checks that `<root>/.git` is a file with a `gitdir:` line, that the target gitdir exists and contains a `gitdir` file whose resolved back-reference equals `<root>/.git`, and that it contains a `commondir` file resolving to an existing directory. All four of those artifacts are created by whoever supplies the directory, and nothing ties them to the canonical repo: `gitdir_path` is never required to live under `<canonical>/.git/worktrees/`, and `commondir` is free to name any repo (`agent/skill_utils.py:494`'s comment, "Verify mutual back-reference (prevents forged .git files from borrowing trust)", overstates what is enforced). `is_project_root_trusted()` (`agent/skill_utils.py:538-547`) then compares that borrowed root against `skills.trusted_project_dirs` and returns True. Verified with the function body taken verbatim from this PR, against a synthetic tree: trusted repo `T` with a normal `.git/` directory; attacker directory `E` containing `.hermes/skills/pwn/SKILL.md`, `.git` = `gitdir: E/fake-gitdir`, `E/fake-gitdir/gitdir` = `E/.git` (self-consistent), `E/fake-gitdir/commondir` = `T/.git` → `_canonical_git_root(E)` returned `T`, so `is_project_root_trusted(E)` is True and `get_project_skills_dirs()` serves `E/.hermes/skills`. `find_project_root` accepts a `.git` *file* by design (`agent/skill_utils.py:420-445`, "dir or worktree file"), so `E` only has to be a directory a session's cwd/workspace points at — e.g. one extracted from an archive (git refuses to track a path named `.git`, but a zip/tar can carry one) or any path another local process can write. That defeats exactly the consent decision the trust list expresses: untrusted skill prose (name/description routing plus body) is loaded and injected as a project skill, with only the `skills_guard` quarantine in between. The PR's own `test_forged_gitdir_backref_mismatch_rejected` covers only the *mismatch* shape — a forged repo pointing at a real worktree's metadata — not this self-consistent forgery. Fix: additionally require the worktree to be registered in the canonical repo before granting trust, e.g. `gitdir_path.parent.resolve() == (commondir_path / "worktrees").resolve()` (git always writes `<repo>/.git/worktrees/<name>`), or read `<canonical>/.git/worktrees/<name>/gitdir` and require it to name the caller's `.git` file. Forging then requires write access to the trusted repo's `.git`, which is the correct boundary. Please add a test for the self-consistent forgery either way.

2. Non-blocking — the new untrusted-skills notice fires on every skills-prompt build and rescans the project each time. `agent/prompt_builder.py:1263-1272` logs at INFO whenever `project_dirs` is empty and `get_untrusted_project_skills_root()` returns a root; that helper walks every candidate skill dir and counts `SKILL.md` files (`agent/skill_utils.py:501-510`) on each call, so in an untrusted project every system-prompt build costs a directory scan plus a repeated log line. Suggest logging once per root (or at DEBUG after the first occurrence per session) and/or caching the count alongside the existing external-dir cache.

Minor: worktree trust is inherited unconditionally — a user who wants a worktree to stay untrusted (e.g. a worktree of a shared/checked-out repo carrying someone else's skills) has no opt-out short of untrusting the repo itself; a `skills.trust_worktrees: false` switch (or documenting that untrust is repo-wide) would help. Also `hermes_cli/main_agent_cmds.py:212-214` silently rewrites the trusted path to the canonical root, so `hermes skills untrust` from inside a worktree removes the *repo's* trust — accurate, but worth a one-line CLI message so the user knows the scope of what they just did.
