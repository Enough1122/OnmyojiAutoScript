I verified the two load-bearing assumptions: (a) the sweep's `f".{path.stem}_"` + `.tmp` match exactly mirrors the tempfile naming in `utils._atomic_write` (`mkstemp(dir=str(path.parent), prefix=f".{path.stem}_", suffix=".tmp")`, utils.py:253 / utils.py:331) — no other file in the hermes root shares the `spawn-ledger` stem, so the scope is right; (b) both call sites of `_read_ledger_or_quarantine` do hold `_LEDGER_LOCK` (`_append_entry` line 289, `ledger_entries` line 345). The change is small, correctly scoped, and quiet on the hot path. One concurrency caveat below (non-blocking) and two minors.

**1. (non-blocking) The sweep can unlink a *live* tempfile of a concurrent writer in another process; the docstring's safety justification does not hold cross-process.**

- Evidence: `hermes_cli/process_identity.py:182` (unconditional `os.unlink(parent / name)` — no age check) and `hermes_cli/process_identity.py:166` ("Caller holds `_LEDGER_LOCK` so this can't race a concurrent `register_self`").
- Why: `_LEDGER_LOCK` is a `threading.Lock` (line 40), i.e. it only serializes writers inside one process. The ledger is machine-wide and every long-lived entry point writes it from its own process (`register_self` → `_append_entry` → `atomic_json_write`, e.g. `gateway/run.py:5543`, `hermes_cli/web_server.py:1268`), while `ledger_entries()` is called from other processes too (`hermes_cli/update_cmd_windows.py:530`, `hermes_cli/update_inventory.py:264`, `hermes_cli/_scan_venv_blockers.py:199`). A reader in process B that lists the directory between process A's `mkstemp` (utils.py:253) and its `atomic_replace` will delete A's tmpfile; A's replace then raises `FileNotFoundError` (an `OSError`), which `_append_entry` swallows at lines 306–308 and reports as `False` — A's registration is silently lost.
- Risk / repro: the window is mkstemp→write→fsync→replace (millisecond scale), so probability is low; the consequence is bounded (one lost best-effort registration — at worst a later update/relaunch sweep does not see that process). On Windows an open handle normally blocks unlink, narrowing the window, but the fd is closed before the replace, so it is not zero. Deterministic repro: in one process, patch `atomic_json_write` to pause after mkstemp; from a second process call `ledger_entries()`; let the first resume — its replace fails.
- Suggested fix: age-gate the sweep, e.g. skip anything whose mtime is younger than a grace period:

  ```python
  st = os.stat(parent / name, follow_symlinks=False)
  if time.time() - st.st_mtime < 300:
      continue
  ```

  and correct the line-166 docstring claim to say the lock serializes same-process writers only.
