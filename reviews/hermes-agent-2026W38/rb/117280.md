## Blocker

### 1. Three permission bits map to a different permission than their name — `tools/discord_tool.py:417-418`

`_PERMISSION_FLAGS` is shifted by one bit for the last three entries. Verified against
discord.py's `Permissions` table and the Discord API permission list:

| key in the table | value in the table | permission that bit actually is |
| --- | --- | --- |
| `SEND_MESSAGES_IN_THREADS` | `0x2000000000` (1<<37) | `USE_EXTERNAL_STICKERS` |
| `USE_EMBEDDED_ACTIVITIES` | `0x4000000000` (1<<38) | `SEND_MESSAGES_IN_THREADS` |
| `MODERATE_MEMBERS` | `0x100000000000` (1<<44) | `CREATE_EVENTS` |

Correct values: `SEND_MESSAGES_IN_THREADS` = 1<<38 = `0x4000000000`,
`USE_EMBEDDED_ACTIVITIES` = 1<<39 = `0x8000000000`, `MODERATE_MEMBERS` = 1<<40 = `0x10000000000`.

Reproduced against the patched module:

```
_parse_permission_flags('SEND_MESSAGES_IN_THREADS') = 0x2000000000
_parse_permission_flags('USE_EMBEDDED_ACTIVITIES')  = 0x4000000000
_parse_permission_flags('MODERATE_MEMBERS')         = 0x100000000000
```

Why it matters: `edit_channel_permissions` is the only consumer, and the failure is silent —
the API accepts the bitfield, so the caller gets `{"success": true}` while the wrong
permission changed:

- `deny="MODERATE_MEMBERS"` denies `CREATE_EVENTS` instead and leaves moderation powers
  (timeouts/kicks) in place on the target role — the caller believes they revoked them.
- `deny="USE_EMBEDDED_ACTIVITIES"` actually denies `SEND_MESSAGES_IN_THREADS`, so members
  silently lose the ability to reply in threads.
- `allow="SEND_MESSAGES_IN_THREADS"` actually grants `USE_EXTERNAL_STICKERS`.

Fix: correct the three constants. While there, `USE_EXTERNAL_STICKERS` (1<<37) is missing from
the table entirely, so that name is logged as "Unknown permission name" and contributes 0
(verified: `_parse_permission_flags('USE_EXTERNAL_STICKERS') == 0`). The PR adds no test file,
so a typo here has nothing to catch it — a small parametrized test over `_PERMISSION_FLAGS`
against a known-good copy of the table would be cheap insurance.

## Non-blocking

### 2. `_create_role` never sees its own `hoist`/`mentionable` defaults — `tools/discord_tool.py:794` (with `:485`, `:495`)

`_HANDLER_DEFAULTS` now supplies `"hoist": None, "mentionable": None`, and
`_run_discord_action` forwards every default as a keyword
(`kwargs = {k: params.get(k, v) for k, v in _HANDLER_DEFAULTS.items()}`), so the signature
defaults `hoist: bool = False, mentionable: bool = False` are unreachable and the create body
is `{"name": ..., "hoist": null, "mentionable": null}` (reproduced).

This is not a live bug — discord-api-types types both as `hoist?: null | boolean`, so Discord
accepts the null and applies its default. But the intent is unreadable at the call site. The
cleanest fix is to drop `hoist`/`mentionable` from `_HANDLER_DEFAULTS`: `_create_role` then gets
its own `False` defaults and `_edit_role` keeps its own `None` ("leave unchanged") defaults.
Alternatively guard the body (`if hoist is not None: body["hoist"] = hoist`), which is
equivalent since omitting the field means false.

### 3. `color` is parsed without validation — `tools/discord_tool.py:497` and `:516`

`int(color.lstrip("#"), 16)` raises `ValueError` for anything non-hex (`"red"`, `"rgb(1,2,3)"`,
`"#GGG"`). The exception is caught by the generic handler in `_run_discord_action` and surfaced
as `Unexpected error: invalid literal for int() with base 16: ...`, which tells the model
nothing about the expected format even though the schema advertises `#RRGGBB`. A `try/except`
returning a `tool_error` naming the format (or a regex check) would make the failure
actionable. Values above `0xFFFFFF` are also passed through unchanged.

### 4. Minor: `_CHANNEL_TYPES` duplicates `_CHANNEL_TYPE_NAMES` — `tools/discord_tool.py:394` vs `:84`

The module already carries the id→name map (`_CHANNEL_TYPE_NAMES`, which knows 10 types); the
new name→id map is a five-entry partial inverse of it. The five entries agree today, so this is
only a drift risk when a channel type is added — deriving one from the other would remove it.
