## Overview

This PR adds per-device microphone/speaker selection to desktop Settings (new `voice.mic_device_id` / `voice.speaker_device_id` config keys, a `VoiceDevicePicker` control, `exact`-constraint mic pinning with system-default fallback, and speaker routing via `setSinkId`). The device-selection design is careful and well tested. One unrelated behavior change slipped into `voice-playback.ts`: the `tts.min_len` argument is dropped from the `cutSentences` call, silently changing TTS sentence chunking for all playback.

## Findings

1. **Unrelated `tts.min_len` argument dropped from `cutSentences`** — apps/desktop/src/lib/voice-playback.ts:306 (non-blocking). `cutSentences(buffer, flush, tts.min_len)` becomes `cutSentences(buffer, flush)`, so the backend-configured `tts.streaming.min_len` is ignored and chunking always falls back to the historical default (`MIN_SENTENCE_CHARS` in `voice-client-direct.ts:389`). This affects CJK TTS playback, where a 5-7 char opener is a whole clause. Fix: restore the third argument, or if the drop is intentional, call it out in the PR description with the reason.

2. **Devices with empty `deviceId` collide on the "System default" value** — apps/desktop/src/app/settings/voice-device-picker.tsx:74 (non-blocking). `value={device.deviceId || EMPTY_SELECT_VALUE}` maps every label-less/empty-id device to the same select value as "System default", so selecting one such entry silently selects the default (and React keys fall back to index). In practice `enumerateDevices` ids are non-empty once permission is granted, but before permission all entries can be id-less. Fix: filter out empty-`deviceId` entries from the list, or key them by index with a distinct value.

## Minor

- `isMissingDeviceError` treats `NotFoundError` as "device gone" and retries on the default; when no microphone exists at all the retry fails into the same `micError` path, which is fine, just two permission prompts worth of latency in that corner.
- The `console.warn` fallback messages in `use-mic-recorder` and `voice-barge-in.ts` are identical strings, so a log reader cannot tell which path fell back; consider naming the source in each message.
