> AI code review — automated follow-up for reference; not a maintainer.

This PR touches a single file, `plugins/platforms/sms/adapter.py`. It adds inbound MMS support (fetch
`MediaUrl0..N` with Twilio basic auth on the first hop, transcode carrier audio via ffmpeg, cache to
local paths, raise VOICE/PHOTO/VIDEO/DOCUMENT events), a new `/webhooks/twilio/status` delivery-status
callback that turns `failed`/`undelivered` into an operator alert, and GSM-7 normalization of outbound
text with the segment cap lowered to `MAX_SMS_LENGTH = 900`. The shape is good: signature validation
still runs first, media work is moved off the request path (so Twilio's 15 s answer window is met at
line 438), the media fetch caps bytes per file and follows the Twilio→CDN redirect without leaking basic
auth, and `audio/mp4` resolves to `.m4a` in `gateway/platforms/media_cache.py`, so transcoded voice memos
land with the right extension. The items below are non-blocking.

1. **GSM-7 normalization is applied on only one of the two send paths.** `plugins/platforms/sms/adapter.py:189`
   normalizes inside `SmsAdapter.send()`, but the plugin's out-of-process sender `_standalone_send()`
   (registered as `standalone_sender_fn`, `plugins/platforms/sms/adapter.py:338` in the pre-image) still
   calls only `_strip_markdown_for_sms()`. That path is what cron/CLI delivery uses when no live gateway
   adapter exists, and `tools/send_message_tool.py:595-606` chunks it at the registry's
   `max_message_length` — which this PR lowers to 900 via `MAX_SMS_LENGTH` (`adapter.py:43`). So a
   cron notification containing `—`, `…`, `’` or `•` is sent as UCS-2: 900 chars / 67 = ~14 segments,
   i.e. exactly the "> 10 segments (Twilio 30019)" rejection the new `_gsm_normalize` docstring
   (`adapter.py:94-95`) is written to prevent. Suggested fix: call `_gsm_normalize()` from
   `_standalone_send()` too (right after `_strip_markdown_for_sms`), or move normalization into a shared
   helper both paths use.

2. **`MAX_SMS_LENGTH = 900` does not bound the chunk size in `send()`.** `adapter.py:43` documents the
   new cap as "~6 GSM-7 segments per message; longer replies are sent as several texts", and
   `adapter.py:189` is the one place that is supposed to enforce it — but
   `BasePlatformAdapter.truncate_message()` (`gateway/platforms/base.py:4569`) defaults to
   `max_length=4096` and the SMS adapter passes nothing. Every sibling adapter passes its cap
   explicitly (`discord/adapter.py:3003`, `feishu/adapter.py:1654`, `matrix/adapter.py:1391`,
   `slack/adapter.py:1469`, `mattermost/adapter.py:278`). The streaming/run-turn consumers do read
   `MAX_MESSAGE_LENGTH`, so the main reply path is capped, but any caller that hands `send()` more than
   900 chars directly gets one ~4096-char message (~27 GSM-7 segments). Suggested fix (one token):
   `self.truncate_message(_gsm_normalize(self.format_message(content)), self.MAX_MESSAGE_LENGTH)` —
   please confirm whether direct `send()` callers are expected to pre-chunk.

3. **The new HTTP clients ignore the gateway proxy / `trust_env` settings.** `adapter.py:315`
   (`aiohttp.ClientSession(timeout=timeout)` for media download) and `adapter.py:394`
   (`_notify_operator`) build bare sessions, while this file's own outbound paths deliberately wire the
   proxy: `adapter.py:187` uses `_new_session(trust_env=gateway_trust_env())` and `_standalone_send()`
   uses `proxy_kwargs_for_aiohttp(resolve_proxy_url())`. On a proxy-only egress (no direct route to
   `api.twilio.com` / `media.twiliocdn.com`), the download fails after its 4 attempts and the user sees
   the "[The client sent an attachment that could not be retrieved…]" placeholder (`adapter.py:263-264`)
   instead of their photo, with only a `type(e).__name__` warning. Suggested fix: use the same
   `_new_session(trust_env=gateway_trust_env())` / proxy kwargs as the outbound path, or state in the
   docstring that media fetch is intentionally proxy-free.

4. **~200 new lines ship without tests.** The diff adds media download/transcode, the status endpoint
   and the normalizer, but `tests/gateway/test_sms.py` (which already covers signature validation and
   webhook body caps) is untouched. At minimum worth pinning: `_gsm_normalize()` output (e.g. `—`/`…`
   → ASCII, and that the result stays ≤ `MAX_SMS_LENGTH`), and a status-callback test mirroring the
   existing 403/200 signature cases for `_handle_status` (`adapter.py:359`, check at `adapter.py:375`),
   including the `SMS_STATUS_WEBHOOK_URL`-unset derivation at `adapter.py:370-371`.

Minor:
- `_ingest_with_media` (`adapter.py:257`) takes `to_number` and never uses it (only `from_number` is
  logged/passed to `build_source`).
- `import shutil` sits mid-module at `adapter.py:85` (and `import os, tempfile` inside
  `_transcode_to_m4a` at `adapter.py:284`) — module imports live at the top of this file.
- Oversized status bodies: the `len(raw) > _TWILIO_WEBHOOK_MAX_BODY_BYTES` guard at `adapter.py:364-365`
  sits inside the same `try` as `request.read()`; with `client_max_size` set to the same value on the
  Application, the read raises `HTTPRequestEntityTooLarge` and the bare `except Exception`
  (`adapter.py:368-369`) answers 400 instead of 413. The sibling `_handle_webhook` pre-checks
  `content_length` first — please confirm the intended code for the status route (not runtime-verified
  here).
- Signature validation is skipped entirely when `status_url` is empty (`adapter.py:372`). That is
  consistent with the documented `SMS_INSECURE_NO_SIGNATURE` dev mode, but note the new endpoint then
  lets any reachable client trigger Telegram messages to the operator (`adapter.py:384-386`).
- `min(num_media, 5)` (`adapter.py:438`) silently drops attachments 6-10 (Twilio delivers up to 10) with
  no note to the agent or the sender.
- Media memory: the cap is per file (`_MAX_MEDIA_BYTES`, `adapter.py:255`) — 5 × 20 MiB per inbound
  message, read fully into memory; the 20 MiB temp-file write/read at `adapter.py:291-292` and
  `adapter.py:304-305` is also blocking I/O on the event loop.
- ffmpeg timeout path (`adapter.py:300`) calls `proc.kill()` without awaiting the child; `await
  proc.wait()` afterwards avoids an unreaped process/ResourceWarning on repeated failures.
- `SMS_STATUS_WEBHOOK_URL` is read at `adapter.py:370` but documented nowhere: the module docstring's
  env list, `website/docs/user-guide/messaging/sms.md` (env table) and
  `website/docs/reference/environment-variables.md` all omit it.
- The status handler pulls `TELEGRAM_BOT_TOKEN` / `TELEGRAM_HOME_CHANNEL` into the SMS adapter
  (`adapter.py:384`) and sends one alert per failed/undelivered callback with no dedupe or rate limit —
  a burst of failures will spam the operator's Telegram.
