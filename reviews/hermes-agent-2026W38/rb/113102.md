`hermes peer dm` (`hermes_cli/subcommands/peer.py`): when the Bot Chat session was already resolved and the chat POST then times out, the command now reports "message accepted, turn still running — do NOT resend" instead of "could not reach peer", because the receiving gateway runs the turn to completion regardless of the client and the old message caused resends/double turns. `TimeoutError` and `URLError(reason=TimeoutError)` are classified as read timeouts; everything else (connection refused, OSError, timeout before session resolution, HTTP status) keeps the old reporting. Tests in the new `test_peer_dm_reporting.py` pin all five discriminators plus the HTTP-rejection path; docs updated to match.

1. **A URLError-wrapped TimeoutError is usually the connect-phase signature, not a read timeout** — `hermes_cli/subcommands/peer.py` `_is_read_timeout`: urllib wraps connection-establishment errors in `URLError.reason` (including socket.timeout on connect), while a mid-response read timeout typically surfaces as a bare `TimeoutError`. If the peer goes down between `_ensure_bot_chat` and the chat POST, the connect timeout will be reported as "the message is already in its Bot Chat… Do NOT resend" and the message is silently never delivered — the inverse of the bug this PR fixes. The test explicitly pins the wrapped case as delivered, so the interpretation is deliberate, but the evidence for "delivered" is weak in exactly that path. Suggested fix: treat only a bare `TimeoutError` (socket read) as delivered and keep `URLError`-wrapped timeouts on the unreachable path (or probe reachability once before claiming delivery). Non-blocking but worth an explicit decision.
