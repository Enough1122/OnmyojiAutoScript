Two gaps worth a look.

1. **Adoption never checks that the entry is usable** — `_adopt_rotated_entry_unlocked` (`agent/credential_pool.py:1906`) validates only that the runtime key differs from the failed hint (`:1937`) and that the token is not itself expiring (`:1939`); it never consults availability. On the `_rotate_unmatched` path that is fine, because the entry arrives from `_select_unlocked()`/`_available_entries()` and is therefore available. The new block in `try_refresh_matching()` (`credential_pool.py:2140-2157`, adopting at `:2155`) instead takes `entry` straight from `self._find(lambda e: e.id == credential_id)` and hands it back as a "recovery". A stale id whose entry is currently benched — `last_status == STATUS_EXHAUSTED` with `last_error_reset_at` in the future, or `STATUS_DEAD` — is adopted anyway, and `agent/agent_runtime_helpers.py:736-758` swaps the live session onto it. `_sync_entry_from_auth_store()` happens to clear status via `_CLEAR_STATUS`, but only when it actually adopts from the store (`should_adopt` true); a singleton whose store tokens already match the entry's is returned unchanged with its cooldown intact (note `should_adopt` also adopts-and-clears when only the refresh token differs, so the full-equality case is the narrow one). The result is one wasted retry on a credential the pool considers benched before the refresh-attempt cap stops it — a delayed fallback rather than a wrong outcome, so non-blocking. Suggested fix: gate on availability (e.g. require the entry to be in `_available_entries()[0]`, or clear the status explicitly) inside `_adopt_rotated_entry_unlocked` so both callers share one contract.
