## 1. The ladder silently assumes `platform_connect_timeout` > 23s

The new comment (`api_server.py:205-206`, and `:4101`) says the ladder exists so the failure reaches the parked fallback instead of "the gateway's default 30s connect timeout (which would bypass the parked fallback)". The 23s of sleeps leaves 7s of headroom under that default (`gateway/run.py:48`, `_PLATFORM_CONNECT_TIMEOUT_SECS_DEFAULT = 30.0`; config default `platform_connect_timeout: 30` at `hermes_cli/config_defaults.py:2046`) — but the deadline is operator-overridable and the ladder does not consult it:

```python
override = self._env_timeout_override("HERMES_GATEWAY_PLATFORM_CONNECT_TIMEOUT")
if override is not None:
    return override
```
(`gateway/run_adapters.py:141-143`; the API server takes the non-Telegram branch at `:144-145`. Fed from `gateway.platform_connect_timeout` via `gateway/run.py:2054-2057`.)

Set that to 10 or 20 and the deadline lands inside the retry loop: `_wait_or_detach` cancels the connect task at the deadline (`run_adapters.py:42-53`) and `_connect_adapter_with_timeout` raises `TimeoutError` (`:161-167`). At startup that exception is not the parked path — `run_startup.py:1090-1091` turns it into an `"exception"` outcome and `:1146-1153` queues the platform as retryable (`platform_state="retrying"`, `:1126-1130`), i.e. the reconnect watcher loops at the backoff cap and the fd/log leak the park was added for (#52132) comes back. The ladder is what makes that window reachable; the old 2s window fit under any override.

Suggestion: derive the ladder from the effective timeout (drop trailing delays that would not fit inside `timeout - margin`), or at minimum state in the comment that `platform_connect_timeout` must exceed the ladder sum.
