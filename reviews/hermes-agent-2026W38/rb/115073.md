1. **Cost label bypasses `format_cost_label`, reintroducing the zero-looking sub-cent label** — `hermes_cli/cli_status_bar_mixin.py:307` — the label is `f"~${amount:.4f}"`: always 4 dp, with no zero-collapse. `agent/usage_pricing.py:29` already defines the shared cost label formatter, whose docstring says it is "Shared by per-response labels and insights cost buckets" and that it "fixes #79220 where sub-cent per-turn costs on cheap models (DeepSeek, etc.) rendered as `$0.00` despite amount_usd carrying full Decimal precision". It returns `"$0.00"` for zero, `"~$<0.0001"` when a nonzero amount would round to 0.0000, and `"~$1.23"` (2 dp) otherwise. Consequences here: a session whose total is a genuinely nonzero sub-cent amount renders `~$0.0000` — the #79220 dishonesty, a label that reads as zero for a nonzero cost — and every ordinary total renders 4 dp (`~$1.2300`) where the rest of the CLI shows `~$1.23`. The new test pins the wrong rendering rather than catching it: `tests/hermes_cli/test_cli_status_bar.py:83` asserts `("estimated", 0, "~$0.0000")` as the expected label. Fix: format via `format_cost_label(Decimal(str(amount)))` (keeping the `"cost included"` / `"cost unknown"` cases as they are) and update the expectation.

2. **A known cost can be displayed as "cost unknown"** — `hermes_cli/cli_status_bar_mixin.py:305` — the gate accepts only `("estimated", "included")`, but `CostStatus` in `agent/usage_pricing.py:48` is `Literal["actual", "estimated", "included", "unknown"]`.
