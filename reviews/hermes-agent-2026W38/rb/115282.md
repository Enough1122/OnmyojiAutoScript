The flat `img_*` layout is preserved when no key is passed, the monkeypatch seam in `_cache_dir_accessors` keeps the new tests honest, and cleanup is covered. One real flaw in the key derivation:

1. **Single-photo keys omit the chat id, so different chats share one album folder** — 非阻塞. adapter.py:6318 (new) returns `f"msg{mid}"` where `mid` is the Telegram `message_id`. Telegram message_ids are unique **per chat**, not globally, so chat A's message 45 and chat B's message 45 map to the same key, and `resolve_inbound_album_dir` then hands both the same directory — contradicting its own docstring, "Different keys never share a folder" (gateway/platforms/base.py:603-607, new). The isolation this PR exists to provide is therefore not per-conversation for single photos. Impact today is limited (each file keeps a distinct `photo-NN` name and no repo code scans `albums/`), but `_write_album_photo` allocates the name with a non-atomic `if not dest.exists(): dest.write_bytes(...)` (base.py:621-629, new), so any future concurrent writer — or a Telegram deployment with concurrent update processing enabled — can silently drop a photo into an existing name. Fix: include the chat/thread id in the key (e.g. `msg{chat_id}-{mid}`), and consider an `O_EXCL` open in `_write_album_photo` so the write is atomic.

Minor: `_ALBUM_DIRS` is a process-lifetime map with no eviction, and entries are not dropped when `_cleanup_cache_dir` removes the directory; a later photo reusing a stale key silently resurrects an old timestamped folder name (harmless, but makes "album folder age" no longer meaningful for the age-based prune).
