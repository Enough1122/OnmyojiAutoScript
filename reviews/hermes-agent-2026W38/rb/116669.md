This PR adds per-call `timeout` / `auto_select` controls to the clarify tool and threads them through the gateway, CLI, TUI, and modal callbacks. The plumbing (kwarg detection, validation, schema) is careful and backward compatible for legacy callbacks, but the TUI single-question path turns an explicit user skip into a first-option selection, and the documented `timeout: 0 = unlimited` contract is not honored by any implementation path.

1. **Skip is silently converted into a first-option selection — tui_gateway/server.py:1341 (blocker)** — `if not answer and auto_select and c: return c[0]` fires on every empty answer, but the same function's docstring defines `"" = skip`, and an empty answer also results from a cancelled/no-result request, not just a timeout. With the default `auto_select=True`, every legacy TUI single-question caller now reports `choices[0]` as the user's answer when the user actually skipped, so the agent can act on an option the user never picked. Fix: only auto-select on a genuine timeout (distinguish timeout from skip/empty at the `server_requests.send` result level), or default `auto_select` to `False` for callers that did not pass it explicitly.

2. **CLI modal timeout path no longer preserves legacy behavior — hermes_cli/cli_modal_mixin.py:625 (non-blocking)** — the timeout branch now returns `choices[0]` whenever `auto_select and choices and timeout is not None`. Because `timeout` is resolved from the global config just above (`resolve_clarify_timeout`), it is effectively never `None` here, so every pre-existing caller gets the new auto-select behavior without opting in. This contradicts the intent stated in the sibling gateway path (`gateway/run_turn_runner.py:1425`), where the `timeout is not None` gate deliberately preserves the old result for direct legacy callers. Fix: apply the same gate in the modal path (only auto-select when a per-call `timeout` was explicitly supplied), or confirm the global default change is intended and document it.

3. **`timeout: 0` is documented as unlimited but behaves as an instant timeout — tools/clarify_tool.py:320 (non-blocking)** — the schema description says `0 means unlimited`, yet a per-call `0` flows into `wait_for_response(timeout=0.0)` (`gateway/run_turn_runner_clarify_delivery.py`), `server_requests.send(..., timeout=0)` (`tui_gateway/server.py`), and the modal wait, i.e. an immediate timeout (followed by first-option auto-select under the default). The `<= 0 → null` unlimited convention of `resolve_clarify_timeout` is never applied to the per-call value. Fix: normalize per-call `timeout <= 0` to `None` (unlimited) at `_timeout_controls` or at each consumption site, and cover it with a test.
