## Overview

This PR adds a short-circuit to `_wait_for_pid_exit`: when `gateway_state.json` already records a terminal state for the PID, it delegates to `_force_exit_wedged_via_state_evidence` for a bounded SIGTERM-to-SIGKILL escalation. The intent is sound, but the implementation recurses infinitely in exactly the scenario it targets, turning a bounded ~6s escalation into unbounded recursion (verified: `RecursionError` after 149 SIGTERM sends with the PID alive and terminal state present).

## Findings

1. **hermes_cli/gateway.py:322 (`_force_exit_wedged_via_state_evidence`) calls `hermes_cli/gateway.py:331 (`_wait_for_pid_exit`), which at hermes_cli/gateway.py:354-355 calls back into `_force_exit_wedged_via_state_evidence` while the state witness is still true — unbounded mutual recursion (blocker).** The state file still says `"stopped"` for this PID during the whole escalation (nothing clears or rewrites it), so the inner `_wait_for_pid_exit(pid, term_grace)` immediately re-enters `_force_exit_wedged_via_state_evidence`, which sends SIGTERM again, waits again, re-enters again, and so on. Reproduced against the patched tree: PID alive forever plus terminal state yields `RecursionError` with 149 SIGTERM attempts and zero SIGKILL attempts — the SIGKILL escalation is never reached, and each cycle also re-sleeps inside the nested polls, so wall-clock cost is far worse than the full drain budget this PR tries to avoid. Suggested fix: give `_force_exit_wedged_via_state_evidence` its own non-recursive wait loop (poll `_pid_exists` only, never consulting the state witness), or thread a flag such as `_via_state_evidence=True` through the inner `_wait_for_pid_exit` calls so the short-circuit fires at most once per outer call.
