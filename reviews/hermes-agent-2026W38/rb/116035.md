The PR adds `gateway/disk_guard.py` (a >1 GiB stale `*.db` sweep of the temp root plus a <5 GiB free-space warning) and wires it into the gateway housekeeping loop every tick. The incident framing is sound and the liveness design (open-handle check + mtime grace) is the right shape, but the open-handle guard can never fire on Linux as written, and the sweep deletes from an ambient, shared directory with only a name-shape/age filter.

1. **BLOCKER — the liveness check hardcodes `/usr/sbin/lsof`, so on Linux the sweep silently removes nothing.** `gateway/disk_guard.py:90` runs `["/usr/sbin/lsof", "-w", "--", str(path)]`. A missing binary raises `FileNotFoundError`, which `except (OSError, subprocess.SubprocessError)` at `gateway/disk_guard.py:94-101` converts to `None` ("cannot prove it is abandoned"), and `sweep_abandoned_db_copies` then `continue`s past every candidate (`gateway/disk_guard.py:155-167`). `/usr/sbin/lsof` is macOS's path; Debian/Ubuntu and Fedora install lsof at `/usr/bin/lsof`, so on those hosts the chore logs nothing above DEBUG and never deletes a file — the exact protection this PR adds is disabled on the majority of Linux hosts (and in CI). Every other lsof call site in the repo goes through PATH (`plugins/platforms/whatsapp/adapter.py:42`, `plugins/platforms/photon/adapter.py:829`), and the repo already treats a missing lsof as a normal condition. Nothing in CI catches it either: the only two tests that exercise the real binary — `tests/gateway/test_disk_guard.py::TestSweepLivenessGuards::test_open_file_survives_real_lsof` and `::TestRealIncidentShape::test_real_large_leak_files_are_swept_end_to_end` — `pytest.skip` when `os.path.exists("/usr/sbin/lsof")` is false, so on ubuntu-latest they skip and the mocked-lsof tests stay green with the guard dead. Fix: resolve the binary once (`shutil.which("lsof")`, falling back to `/usr/sbin/lsof` on macOS) and fail loudly (or warn once) when it cannot be found, since "no lsof" currently means "never sweep". Use the same resolution for the tests' skip condition so the acceptance tests actually run in CI.

2. **Non-blocking — the sweep's blast radius is an ambient temp dir, not a Hermes-owned one.** `sweep_abandoned_db_copies()` defaults to `Path(tempfile.gettempdir())` (`gateway/disk_guard.py:129`) and matches `SWEEP_PATTERNS = ("*.db", "*.db-wal", "*.db-shm", "statedb_ro*")` (`:61`) above `SWEEP_MIN_BYTES = 1 GiB` with `SWEEP_GRACE_SECONDS = 10 * 60.0` (`:65`). On Linux the Hermes boot hook points `TMPDIR` at `HERMES_HOME/cache/scratch` when the user has not set one (`hermes_constants.export_scratch_tmp_env`, `hermes_constants.py:1107-1114`), which is Hermes-owned — but an operator-set `TMPDIR` is respected, and on macOS and Windows the hook deliberately keeps the OS-set `TMPDIR`/`TEMP`, so `gettempdir()` can be the per-user system temp dir shared with every other application. There, any unrelated tool's >1 GiB, 10-minute-old, handle-free `.db` (or a `-wal`/`-shm` sidecar whose writer is gone) is deleted with only a WARNING log; a user's own large SQLite working copy in temp is indistinguishable from a leak. `check_free_disk_warning()` samples the same ambient path by default (`:187`, `:212-215`). Suggest scoping the sweep explicitly to `hermes_constants.get_scratch_dir()` (which already prunes entries older than `SCRATCH_MAX_AGE_HOURS` via `prune_scratch_dir`, `hermes_constants.py:1026`) and/or requiring `st_uid == os.getuid()`, so the guard cannot reach into other workloads' temp files. Related: an unprivileged `lsof` cannot see other users' fds yet still exits 1, so for another uid's file "no holder" is not proof of abandonment — the same `st_uid` gate closes that.

Minor: `_has_open_handle` spawns one lsof per candidate on every 60 s tick, each allowed up to a 15 s timeout (`gateway/disk_guard.py:92`), all on the housekeeping thread — fine at incident scale, but a temp root with many large DBs can hold a tick open for seconds per file (and the same files are re-checked every tick); consider capping candidates per pass or caching the verdict briefly.
