## Overview

This PR intends to harden `SessionEntry.from_dict` against corrupt session rows (missing `session_key`/`session_id`, malformed timestamps). The validation intent is sound, but the helper `_parse_iso_or_raise` was inserted as a column-0 `def` between `SessionEntry.to_dict` and `SessionEntry.from_dict`, so the original `from_dict` method is now a nested function inside the helper instead of a method of `SessionEntry`. Every production and test caller of `SessionEntry.from_dict` (notably `gateway/session_persistence.py:260,306`) would raise `AttributeError`, breaking gateway session restore entirely. Verified by applying the diff to a temp copy of `gateway/session.py` at main `d6dd884` and inspecting the AST: `SessionEntry`'s method list becomes `['to_dict']` only.

## Findings

1. **`from_dict` swallowed into the new helper — gateway session restore breaks** — gateway/session.py:564 (blocker). The new module-level `def _parse_iso_or_raise` at line 564 sits inside the `SessionEntry` class region; the following `    @classmethod` / `    def from_dict` at lines 573-574 therefore defines a *local* function inside the helper rather than a method of the class. Fix: make the helper a `@staticmethod` of `SessionEntry` (indented, placed before `from_dict`), or move it above the `class SessionEntry` definition, then re-run `tests/gateway/test_session.py` and `test_active_turn_recovery.py`, which both call `SessionEntry.from_dict`.

2. **`_parse_iso_or_raise` returns `None` for a missing key despite its name** — gateway/session.py:564 (non-blocking). `data.get(key)` returning a falsy value yields `None`, so a row missing `created_at`/`updated_at` still constructs an entry with `None` timestamps and fails later instead of at parse time. Fix: raise `ValueError` when the key is absent (keep `None` only if optional timestamps are genuinely allowed), or rename to `_parse_iso_or_none`.

## Minor

- No test changes ship with this diff, although `tests/gateway/test_session.py` already covers `from_dict` traversal guards — a regression test for the missing-key/invalid-timestamp paths would have caught finding 1 immediately.
- Callers previously saw `KeyError` for missing `session_key`/`session_id` and now see `ValueError`; worth a note in the PR description in case anything catches `KeyError` specifically.
