This PR adds an opt-in Streamable HTTP transport to `hermes mcp serve`: new flags in `hermes_cli/subcommands/mcp.py` (`--transport/--host/--port/--path/--token-env/--allowed-host/--public-url`), forwarding in `hermes_cli/mcp_config.py`, a static bearer-token verifier plus fail-closed bind validation in `mcp_serve.py`, a new `HERMES_MCP_SERVER_TOKEN` entry in `hermes_cli/config_defaults.py`, a new `tests/test_mcp_serve_http.py`, and docs updates. The security shape is right (remote binds fail closed on token + allowed Host + public URL, the token is compared with `hmac.compare_digest`, TLS/reverse-proxy guidance is documented), and I verified the core claim end-to-end against the pinned `mcp==2.0.0`: no token → 401, wrong token → 401, correct token → 200 on `/mcp`. Both findings below share one root cause — the loopback branch delegates DNS-rebinding protection to the SDK's *exact-string* loopback auto-enable instead of constructing `TransportSecuritySettings` itself.

1. Loopback binds silently lose DNS-rebinding protection when `--host` is not exactly lowercase — mcp_serve.py:737, 764, 807, 819

   `_is_loopback_host()` lowercases (line 737), so `--host LOCALHOST` / `LocalHost` counts as loopback → `remote_http` is False (line 764) → all three fail-closed checks are skipped and `security = None` (line 807) is forwarded together with the **unmodified** host string (line 816) to `run_streamable_http_async` (line 819).

   mcp 2.0.0 auto-enables the loopback defaults only when `host in ("127.0.0.1", "localhost", "::1")` (exact, case-sensitive) inside `MCPServer.streamable_http_app`. Verified here: `streamable_http_app(host="LOCALHOST")` leaves `session_manager.security_settings is None`, and `TransportSecurityMiddleware(None)` builds `TransportSecuritySettings(enable_dns_rebinding_protection=False)`, which skips Host *and* Origin validation entirely.

   Repro (verified): `run_mcp_server(transport="http", host="LOCALHOST", port=8000, path="/mcp", ...)` forwards `host="LOCALHOST"` with `transport_security=None`. So `hermes mcp serve --transport http --host LOCALHOST` — the documented "unauthenticated local use" mode, no token required — accepts any `Host` header. A browser page that DNS-rebinds a hostname to 127.0.0.1 can then reach the bridge and use the whole tool surface (read conversations, send messages) without a token. Only case variants of `localhost` are affected, but the failure is silent.

   Suggested fix: normalize before both checks (`host = host.lower()`) and/or stop depending on the SDK default — always pass `TransportSecuritySettings(enable_dns_rebinding_protection=True, allowed_hosts=allowed_hosts or ["127.0.0.1:*", "localhost:*", "[::1]:*"], allowed_origins=[...])`.

2. `--allowed-host` is silently ignored on loopback binds, breaking the documented reverse-proxy setup — mcp_serve.py:808-813

   The settings object is built only when `remote_http` is true, so a loopback bind forwards `transport_security=None` even when the user passed `--allowed-host`. Verified: `run_mcp_server(transport="http", host="127.0.0.1", token_env=..., allowed_hosts=["mcp.example.com:*"])` forwards `transport_security=None` (the token *is* honored; the allowlist is not). The SDK's loopback defaults then allow only `127.0.0.1:*`, `localhost:*`, `[::1]:*`.

   Repro (verified): server created with `bearer_token="secret"`, `streamable_http_app(host="127.0.0.1")`, POST `/mcp` with `Host: mcp.example.com:443` and a **valid** `Authorization: Bearer secret` → **421 Misdirected Request**; the identical request with `Host: localhost:8000` → 200. That is precisely the deployment the docs recommend ("Put TLS in front of the listener…"): nginx/Traefik on the same host proxying to 127.0.0.1:8000 and passing the public `Host` header fails closed with no warning, and because the flag is accepted but dropped there is no supported way to make it work.

   Suggested fix: honor `allowed_hosts` whenever it is supplied — build the settings for every HTTP bind (`allowed_hosts=allowed_hosts or <loopback defaults>`) — or reject the combination with a clear error instead of ignoring it.

Minor:

- mcp_serve.py:701 — `hmac.compare_digest(candidate, token)` raises `TypeError: comparing strings with non-ASCII characters is not supported` for non-ASCII strings (verified). A non-ASCII configured secret, or a client sending one, turns every request into a 500 instead of 401; compare encoded bytes or catch `TypeError` and return `None`.
- `--public-url` is not validated: a value without a scheme reaches `AuthSettings.issuer_url` (`AnyHttpUrl`, required) and dies with a pydantic `ValidationError` traceback at startup (verified) instead of a clean CLI error.
- mcp_serve.py:813 — remote binds hard-code `allowed_origins=[]` and there is no `--allowed-origin` flag, so any client sending an `Origin` header is rejected with 403 (browser-based MCP clients are blocked). Reasonable as a fail-closed default; consider a flag or a doc note.
- Tests: `tests/test_mcp_serve_http.py` covers only the remote-bind paths (tests at lines 6, 49, 66, 110); the loopback branch (`security = None`) is untested, which is why both findings above survived. A test asserting `transport_security` for a loopback bind plus `--allowed-host` would catch them.
