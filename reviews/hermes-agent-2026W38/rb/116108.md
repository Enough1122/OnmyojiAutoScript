One design consequence is worth settling before merge.

1. **Enabling the rerank lets a low-trust result outrank an official one in the limit cut** — non-blocking — tools/skills_hub_search.py:264-266 (the ordering the new code replaces) and tools/skills_hub_rerank.py:114-126 (`rerank_by_relevance` sorts the whole list, ignoring `trust_level`).
   - The existing comment states the invariant: "Stable-sort by trust before truncating so the limit cut never drops a builtin/official entry because a high-volume community source finished first" (tools/skills_hub_search.py:264-266). Rerank runs over the full merged list and re-orders across trust ranks, so a community skill whose name/description scores well can push the official entry past `limit` — the user then sees (and is nudged to install) the community copy. That makes an attacker-controllable field (name/description of a third-party skill) decide which entry survives the cut.
   - Suggested fix: keep the trust invariant and rerank *within* each trust rank (sort by `(-TRUST_RANK, -score, index)`), or pin builtin/official entries above community ones; either way state the behaviour in the docs paragraph added at website/docs/user-guide/features/skills.md:666-679, which currently only mentions fail-open.
   - Minor: `jev_score_relevance` keys its `questions` dict by `meta.identifier` (tools/skills_hub_rerank.py:61-68); two candidates sharing an identifier collapse into one question and get the same score. `_dedupe_by_trust` makes that unlikely, but a `for i, meta in enumerate(candidates)` key is cheap insurance.
   - Minor: `float(answer.get("score", 0.0))` (tools/skills_hub_rerank.py:91) raises `AttributeError` when `answers[identifier]` is not a mapping; it is caught by the caller's blanket `except Exception` and fails open, so this is only a comment/log accuracy point ("Raises on any failure" is true, but not via the local `try`).
