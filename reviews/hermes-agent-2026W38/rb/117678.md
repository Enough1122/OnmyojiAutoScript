This PR teaches the file-handoff pattern in two places. On the docs side, `skills/software-development/github/references/issues.md` and `pr-workflow.md` now create issue/PR bodies via `--body-file` instead of an inline `--body`, and a new "Long bodies: hand off via a file" section states the rule (write the payload with `write_file`, never ASCII-normalize it, quoted-heredoc as the inline fallback). On the code side, `tools/terminal_hints.py` exports shared `PAYLOAD_QUOTING_PATTERNS` / `PAYLOAD_QUOTING_HINT`, consumed both by the terminal hint list in the same file and by `_FAILURE_HINT_RULES` in `tools/code_execution_tool.py`, with tests on both egresses. The code side looks sound: every pattern is non-capturing, the hint string contains no `{`/`}`, so `_regex_hint`'s `message.format(*m.groups())` path is a no-op rather than a silent `KeyError`; the sandbox rule is appended last so no earlier rule shadows it; and the deliberate breadth of `SyntaxError: invalid character` is fenced by tests that pin the `invalid non-printable character` boundary and unrelated `SyntaxError` shapes. The substantive issue is in the new doc recipe, which does not work as written on Windows.

1. The new recipe's bare `/tmp` path is not reachable by the native `gh` binary on Windows — `skills/software-development/github/references/issues.md:102,106`, same pattern at `skills/software-development/github/references/pr-workflow.md:108,111`.
   The text tells the agent to write the body with the **write_file tool** to `/tmp/issue-body.md` and then hand that same path to `gh ... --body-file`. On Windows these two steps disagree: the file tool puts the body where the shell's `/tmp` points (the Windows temp dir), while `gh.exe` — a native binary (verified: MZ header) — is passed the literal POSIX string `/tmp/issue-body.md` because Hermes' terminal runs bash with MSYS path conversion disabled, so the path is resolved by Go against the current drive root (`<drive>:\tmp\issue-body.md`) and the file is not found at the last step, after the agent did exactly what the doc says. Verified on a Windows host from the same shell: a native interpreter received `argv[1] == '/tmp/hermes_probe_117678.md'` with `os.path.exists -> False`, while bash saw the same file at `/tmp`. This is the case Hermes' own runtime guidance calls out ("never a bare `/tmp`" for scratch files a native tool must read); please confirm the exact `gh` failure text, but the resolution mechanism is the same class as the one verified.
   Suggested fix: use a path both sides resolve identically — `"${TMPDIR:-/tmp}/issue-body.md"`, a workspace-relative file, or the stdin form `gh issue create --body-file -` / `gh pr create --body-file -`; alternatively add a one-line Windows note next to the two code blocks. The same wording should be applied in both files so the recipe stays copy-pasteable.
