## Overview

This PR adds an opt-in `gateway.session_key_aliases` map (`gateway/config.py:610`, bridged through `gateway/config_loader.py:92`) and resolves an exact `X-Hermes-Session-Key` match into a native conversation identity: `_resolve_api_session_identity()` (`gateway/platforms/api_server.py:1702-1740`) builds a `SessionSource` plus the canonical `build_session_key()` value, and `POST /api/sessions/{session_id}/chat[/stream]` then requires the addressed transcript's stored `session_key` to equal that resolved key (`api_server.py:3139-3142`) before any turn runs. Tests exercise the real HTTP route over a 16-way matrix (group/thread isolation × thread_id × stream) plus the fail-closed invalid-alias path (`tests/gateway/test_api_session_aliases.py:186-311`), and the docs get a matching section (`website/docs/user-guide/features/api-server.md:661-694`).

The gating itself looks sound and I found no correctness or authorization bug: matching is exact, `profile`/`scope_id` overrides are rejected (`api_server.py:1723`), API_SERVER/WEBHOOK sources are rejected (`api_server.py:1719`), auth is still enforced by the route decorator, the transcript check happens before the body is read and before any agent run, and the doc claim that config + key namespace follow the request profile holds because `_make_profile_prefix_middleware` enters `_profile_scope` around the handler (`api_server.py:1556-1578`), so `load_gateway_config()` resolves the request's profile home. The items below are non-blocking.

1. **Every request carrying the header pays a full, synchronous config load on the event loop.** `api_server.py:1708` (`config = load_gateway_config()`) is reached unconditionally from `api_server.py:3130` whenever the header is non-empty — including when no aliases are configured at all. `load_gateway_config()` is not cached: it re-reads the YAML layers from disk and runs plugin discovery plus the platform-registry sweeps (`config_loader.load_yaml_layer` → `discover_plugins` / `shared_loop_targets` / `apply_plugin_yaml_hooks` / `bridge_core_env_settings`), then `_apply_env_overrides` and `_validate_gateway_config`, which re-emits its warnings/errors (enabled platform with empty/placeholder token) on every call. Risk: a client that sends the documented header on every turn (the Honcho per-session use case the docs describe) turns each request into disk I/O + registry work inside the aiohttp coroutine; the other config loads in this file happen inside `_create_agent`, which runs in the executor thread (`api_server.py:2206` with the `_run()` dispatch), so this is the one that blocks the loop and can spam logs. Suggested fix: cache the alias map keyed by config mtime (or do the load in `asyncio.to_thread`), and short-circuit when no aliases are configured.

2. **`session_source` (`api_server.py:3198`) has no consumer in this PR — it is the contract the paired #117456 reads; the two must not be treated as alternatives.** Evidence: in the pre-image nothing reads a `session_source` key out of the prepared ctx (the two `_prepare_session_chat` callers read `ctx["session_id"]`, `ctx["gateway_session_key"]`, …), while #117456 calls `self._fanout_completed_api_turn(session_source=ctx.get("session_source"), …)` in `_handle_session_chat` and in `_run_and_signal`. So #117456 depends on the key this PR adds, and because #117456's own tests monkeypatch `_prepare_session_chat` with a hand-built ctx, they would still pass while native final-response fanout silently no-ops in production if #117456 landed alone. The hunks do not conflict textually (this PR edits the `_prepare_session_chat` return; #117456 edits `_handle_session_chat`/`_run_and_signal`), but the merge order matters: land 117455 first (or together); if 117455 is dropped, 117456 must add the key itself. Please confirm this is the intended split.

3. **Alias entries are only validated per request, never at load time.** `GatewayConfig.from_dict` (`config.py:785-786`) checks only that the top-level value is a mapping; per-entry validation lives at request time (`api_server.py:1713-1727`), so a typo (`platform: discordx`, `chat_id: 123`, a `profile:` key) is silent until a request fails with 400 `invalid_session_alias`. The annotation `Dict[str, Dict[str, Any]]` (`config.py:610`) is also not enforced — `from_dict` keeps any value, as this PR's own second test configures (`broken: not-a-session-source`). Fix: validate entries once in `_validate_gateway_config` and log at startup (fail closed per entry, keep serving), and either narrow the annotation or drop non-mapping values at load.
