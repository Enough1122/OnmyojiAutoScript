> AI code review — automated follow-up for reference; not a maintainer.

This PR moves the per-turn `sessions.json` mirror write off the event-loop thread: `gateway/session_persistence.py` gains `_dispatch_sessions_json_save` (inline when there is no running loop, or when state.db did not commit and the mirror is therefore the primary copy), a single coalescing writer thread (`_queue_sessions_json_save` / `_sessions_json_writer_loop`, one pending snapshot, newest generation wins), a seq watermark + `drain_sessions_json_writes`, and `stop_sessions_json_writer`, wired into `close_all_db_handles`. `tests/gateway/test_sessions_json_write_off_loop.py` drives the real `clear_resume_pending -> _save -> _persist_routing_data -> atomic_json_write -> atomic_replace` seam with a 500 ms injected rename and measures loop lag, thread identity, coalescing, byte-format equality and shutdown drain. The design is sound in the normal path — queued generations are strictly increasing (`_persist_routing_data` holds `_save_lock` across the dispatch and the `_persisted_routing_generation` bump, so the coalescing drop at :535 can never drop newer data), the writer takes/clears the pending slot under the Condition, and the mirror byte format is unchanged. The findings below are about the paths that bypass the queue, plus two robustness details.

1. No generation fencing between the deferred writer and the inline write path — `sessions.json` can regress after all.

`_sessions_json_writer_loop` renames whatever snapshot it took, with no re-check against anything newer that landed in the meantime (`gateway/session_persistence.py:562-565`), and the inline branch (`:516-518`) writes directly, bypassing the pending slot and the `_sessions_json_queued_seq`/`_sessions_json_written_seq` watermark entirely. The coalescing guard only protects the *pending* slot (`:534-536`), not an *in-flight* rename, so an older write can land after a newer one:

- Turn N (loop thread, db_saved=True): snapshot generation 10 is queued; the writer takes it and enters a slow rename (the >=30 s `os.replace` stall this PR documents).
- Turn N+1: the state.db routing replace raises, so `db_saved` is False -> `must_be_synchronous=not db_saved` is True -> the gen-11 snapshot is written inline on the loop thread and lands (fast). This is exactly the mode in which the mirror is the primary copy.
- The writer's gen-10 rename then completes and replaces the file -> `sessions.json` now holds generation 10, while generation 11 was never committed to state.db and exists nowhere durable.

Same shape at shutdown: `stop_sessions_json_writer` sets `_sessions_json_writer = None` after `thread.join(timeout=timeout)` (`:604-606`), so if the join times out while the writer is stuck inside the rename the stale thread is still alive; the next queue then starts a *second* writer (`:542-548`) and the two renames can complete out of order.

Impact is bounded (legacy mirror, self-heals on the next successful save) and the window is narrow (a state.db failure, or a stop-timeout window), but it defeats the monotonicity the new docstrings assert (`:529-530` "an older one arriving late is dropped rather than allowed to regress the file"). Please confirm the interleaving is considered acceptable, or fence the file with a generation watermark: record the generation under `cv` before every write (including the inline one at `:517`) and have the writer skip its rename when its own generation is below the recorded one; and/or keep the thread reference until it is confirmed dead rather than clearing it after a timed-out join.

2. The Condition can be created twice, and a lost Condition means a queued snapshot never flushes.

`_sessions_json_cv()` builds the Condition through `_lazy` (`:521-523`), which is getattr -> factory -> setattr with no lock, so two threads that both see `None` each get their own `threading.Condition`. If the writer ends up waiting on one object while a producer notifies the other, the queued snapshot never flushes (silent mirror staleness, no error) and the shutdown drain spends its whole budget before returning False (`:589-592`). In practice the first call always happens in `_queue_sessions_json_save` under `_save_lock` before `thread.start()` (`:532`, `:548`), so this needs a shutdown drain (`close_all_db_handles`, `:216`) racing the very first deferred write — narrow, and not reproduced here. Creating the Condition once in `__init__` (or guarding the lazy init with a lock) would make it structurally impossible; `_lazy` is used the same way for `_save_lock`, where a double-created lock is harmless, but not for a Condition.

Minor:

- `close_all_db_handles` (`:213-221`) is also called by tests and other handle-sweep callers, not just shutdown; every such call now drains (up to 10 s) and joins (another 10 s), and a later save silently restarts the writer. Consider a dedicated close/shutdown hook, or note the side effect in the docstring.
- The writer is a daemon thread, so a hard exit (the watchdog kill with code 75 this PR is about) drops the pending snapshot; the same write was synchronous before. Acceptable for a legacy mirror, but worth stating in the PR body, since DB-down installs have no other durable copy.
- In DB-down installs the per-turn write still runs inline on the loop thread (`:516-518`), i.e. the stall this PR fixes remains exactly where the mirror is the primary copy — deliberate per the docstring, but the loop-liveness risk is unchanged there.
- `_generation` is unpacked and unused in the writer loop (`:562`); only the pending-slot check consumes it.
