The resolver hands the env value straight to the agent, which breaks two shapes of proxy value that were harmless before this PR.

1. **A scheme-less proxy value makes the update check fail** — `apps/desktop/electron/update-api-proxy.ts:6` — `proxy-from-env` prepends the *target's* scheme when the value carries none (its `index.js`: "Missing scheme in proxy, default to the requested URL's scheme"), so `HTTPS_PROXY=proxy.corp.com:8080` resolves to `https://proxy.corp.com:8080` and `HttpsProxyAgent` then opens a TLS connection *to the proxy*. Verified against the installed packages with a local plain-HTTP proxy: scheme-less value → the proxy received a TLS ClientHello and the request died with `EPROTO ... wrong version number`; `http://` value → the same proxy received `CONNECT api.github.com:443 HTTP/1.1`. curl, git and requests all treat a scheme-less proxy as an HTTP proxy, so a corporate config that worked before this PR now fails the check. Fix: prepend `http://` when the resolved value has no `://`.
2. **A malformed value throws out of the request setup** — `apps/desktop/electron/update-api-proxy.ts:8` — `new HttpsProxyAgent(...)` runs `new URL(...)` unguarded, so `"   "`, `http://`, `http://127.0.0.1:99999` or any non-URL value throw `TypeError: Invalid URL`. The call site evaluates it while building the options object inside the `new Promise` executor in `fetchGitHubApiOnce` (`main.ts:3387`), so the throw rejects the update check instead of falling back to a direct connection, and the diagnostic classifier in `update-api-check.ts` has no branch for it (no `code`, no `statusCode`), so the user gets the raw `api.github.com: Invalid URL` line. Before this PR the same env var was simply ignored. Fix: try/catch around the construction, returning `undefined` on failure.
