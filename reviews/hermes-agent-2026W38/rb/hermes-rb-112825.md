This PR adds an opt-in lazy launcher for `browser.cdp_url`: when the configured CDP override is an unreachable loopback endpoint and `browser.auto_launch` is true, `_resolve_backend_cdp` (tools/browser_use_cli.py:587) spawns a dedicated Chrome bound to that loopback endpoint with a per-session profile and waits up to 40s for `/json/version`, otherwise keeping the legacy attach-only behavior. The opt-in default and loopback-only gate (`_maybe_auto_launch_local_cdp`, tools/browser_use_cli.py:308), proxy-bypassed readiness probe (via `agent.proxy_bypass.loopback_request_kwargs`), and new config keys (hermes_cli/config_defaults.py:402-408) are sound, and tests/tools/test_browser_use_cli.py covers the gate, argv shape, and profile isolation. One lifecycle gap on the failure path, plus two smaller items.

1. **Spawned Chrome is leaked when the launch never becomes ready** — tools/browser_use_cli.py:283-305 (non-blocking). `_launch_configured_local_chrome` starts a detached Chrome (`start_new_session=True`, tools/browser_use_cli.py:290-292) and returns False at :305 when the 40s deadline expires or the process is observed to exit — but on the alive-but-not-ready path it never terminates the child, and the `Popen` handle is dropped. Any cause of "Chrome running, endpoint never ready" leaves a permanent, untracked headless Chrome: the configured port already held by another listener, or two concurrent `browser_exec` sessions auto-launching the same `cdp_url` with different per-session profile dirs (both pass the not-ready gate at :308-313; the loser can never bind the port, and unlike the same-profile case no Chrome singleton exits it), or startup slower than 40s. Since the gate re-runs on every call, each subsequent `browser_exec` spawns and leaks another Chrome and re-pays the wait before Browser Use reports its connection error. Suggested fix: on the failure return, best-effort `proc.terminate()` (escalate to `kill()`) then `proc.wait()` — Hermes owns the process it spawned.

Minor: `auto_launch_headful` docs don't hold for Windows binaries — hermes_cli/config_defaults.py:406 and website/docs/user-guide/features/browser.md:89 say `false` adds `--headless=new`, "useful on WSL/headless hosts", but `_auto_launch_chrome_argv` skips the flag for any `.exe` binary (tools/browser_use_cli.py:268,279; pinned by `test_windows_profile_path_is_translated_for_windows_binary`). The documented WSL case (a `/mnt/c/...chrome.exe` selected via `BH_CHROME_PATH`) always launches a visible window and cannot be made headless; align the docs or apply the flag to `.exe` too.

Minor: unguarded cache-glob fallback can raise out of the hook — tools/browser_use_cli.py:241-242: the `glob`/`path.stat()` fallback in `_find_auto_launch_chrome` runs outside any try (only the `get_chrome_debug_candidates` import is guarded), and the hook at :587 is not wrapped in `_quiet` like its neighboring lookups, so a file deleted between glob and stat or an unreadable cache subdir surfaces as a registry-level tool exception instead of the graceful fallback to the "normal connection error" promised at website/docs/user-guide/features/browser.md:94.
