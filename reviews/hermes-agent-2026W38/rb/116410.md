When `send()` cannot resolve `metadata["thread_id"]`, the Discord adapter now falls back to `chat_id` instead of returning "Thread … not found". Treating a *deleted/archived* thread as a reason to deliver into the parent channel is a defensible product call, but the same `except` also swallows `Forbidden`, which is a permission verdict rather than a missing destination — and the fallback re-addresses content the caller never targeted.

1. **Blocker candidate — a 403 on the thread is treated as "thread gone" and the reply is republished to the parent channel.**
   - `plugins/platforms/discord/adapter.py:2990-3014` — `except (discord.errors.NotFound, discord.errors.Forbidden): channel = None` on the thread lookup (line 2993), and the same pair again on the fallback lookup (line 3007); on the first hit, `thread_id = None` and the send proceeds against `chat_id`.
   - `discord.errors.Forbidden` is an HTTP 403 from `fetch_channel`, i.e. the bot may no longer see/write that thread (access revoked, permission stripped, locked/private thread) — not that the thread does not exist. `plugins/platforms/discord/adapter.py:5168-5173` (`_resolve_channel`) is the call that raises it.
   - Risk: content scoped to a thread the connector was denied becomes content published in the parent channel, where a different (often wider) audience reads it; the delivery ledger still records the send against the original target (`_target_id = thread_id or chat_id`, line 3027). The comment states the trade ("a message that shows up in the wrong place beats one that never shows up at all"), but for a permission verdict the wrong place is exactly what the operator's restriction was meant to prevent — and the previous behaviour (a failed send the caller can see and retry/report) is the safe one.
   - Suggestion: split the handlers — keep the parent-channel fallback for `NotFound` (thread deleted/archived, the case the PR describes) and let `Forbidden` surface as the "Thread … not found"-style failure (or a distinct error such as `"Thread <id> not accessible"`), so a revoked destination is never silently re-addressed.
