The in-code rationale ("the next tick shows the same text anyway") holds only while a later tick succeeds; the failure that ends the stream can land in the same skip window (ticks are ~0.8 s, the budget is 1.0 s, so two consecutive skips are normal under a burst).

A cheaper alternative on the adapter side is to return the skip only when the text is unchanged from what was last successfully edited, but the adapter has no view of that state, so the marker is the cleaner seam.
