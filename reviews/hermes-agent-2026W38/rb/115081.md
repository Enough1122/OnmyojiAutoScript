This PR adds the card context menu (block / unblock / request review / request changes / comment / reassign / add link / add child), runtime-cap and stale-blocked badges, hash-backed facet filters, and two new board-payload fields (`triage_signal`, `last_event_at`) read by the new badges. It touches `apps/desktop/src/plugins/kanban/{board.tsx,ui.tsx,drawer.tsx,types.ts,i18n.ts}` and `plugins/kanban/dashboard/plugin_api.py`. The structure is good — a data-tabled action map, all four locales updated, unit tests for the badge math and the board payload — but the new menu's visibility rules do not match the backend's accept-set, so two of the new actions can only ever fail.

1. **blocker — "Request review" can never succeed.** The row is shown only on `done` cards (`board.tsx:177`, `when: s => s === 'done'`) and the action maps to `patchTask(id, { status: 'review' })` (`board.tsx:1646`). That reaches `_STATUS_HANDLERS['review']` → `kanban_db.request_review`, whose UPDATE is gated `AND status IN ('running', 'ready')` (`hermes_cli/kanban_db.py:3307`), so `rowcount != 1` → `False` → the endpoint answers 409 "status transition to 'review' not valid from current state" (`plugins/kanban/dashboard/plugin_api.py:614`, `_patch_status`). Every click on every done card fails; there is no done→review verb in the backend today. Suggested fix: either gate the row on a status the backend accepts, or add/route a real "reopen for review" transition (the closest existing verb is `reopen_review_task`, which is `review`→`ready`/`todo`).

2. **blocker — "Block…" is offered on statuses the backend refuses.** `board.tsx:175` shows the row for every status except `blocked`. `BOARD_COLUMNS` is `["triage","todo","scheduled","ready","running","blocked","review","done"]` (`plugin_api.py:169`), and the submit PATCHes `status: 'blocked'` (`board.tsx:212`) → `kanban_db.block_task`, gated `AND status IN ('running', 'ready')` (`hermes_cli/kanban_db.py:3162`). So Block… returns 409 on triage, todo, scheduled, review and done — 5 of the 7 columns that show the item. Repro: right-click a `todo` card → Block… → type a reason → Block → error toast. The drawer's own move menu already applies this discipline (`isLockedTarget`, `ui.tsx:53`); the new menu needs the same. A `when` predicate of `['running','ready'].includes(s)` would match the backend exactly.

3. **non-blocking — the repeated-failure half of `triage_signal` ignores the documented lane exclusion.** The unblock-pair query excludes closed lanes (`plugin_api.py:303`, `AND t.status NOT IN ('triage','done','archived')`), but the failures set does not (`plugin_api.py:309-315`: `SELECT id FROM tasks WHERE consecutive_failures >= 2 AND id IN (...)`), while the docstring says "Cards already in `triage` / `done` / `archived` are excluded … a finished card must not keep the board's 'needs triage' filter pinned to history". `complete_task` clears `block_kind`/`block_recurrences` but not `consecutive_failures` (`hermes_cli/kanban_db.py:2763-2774`), so a card that failed twice and later finished stays flagged forever and the new "Needs triage" filter keeps showing it. Your test `test_triage_signal_absent_for_single_block_and_closed_cards` only exercises the pair path for a closed card, so it cannot catch this. Suggested fix: apply the same `status NOT IN (...)` predicate to the failures query and add a done-card-with-`consecutive_failures=2` case to that test.
