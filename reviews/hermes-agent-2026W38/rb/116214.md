The one issue I found is that the refresh overloads a column another feature orders by.

1. **Non-blocking — the retrieval refresh hijacks `updated_at`, which `contradict()` uses as content-recency.** The new `_mark_retrieved` (PR head `plugins/memory/holographic/retrieval.py:78-93`, its UPDATE at `:89-90`) writes `updated_at = CURRENT_TIMESTAMP` on every served fact. The decay-reinforcement effect on ranking is intentional and documented in the docstring, but `updated_at` is also the ordering key for an unrelated consumer: `contradict()` selects its O(n^2) comparison window with `rows = sorted(rows, key=lambda r: r["updated_at"] or r["created_at"], reverse=True)[:500]` (`plugins/memory/holographic/retrieval.py:128` on `main`, `:148` on this branch), and `_FACT_COLUMNS` (`retrieval.py:16`, unshifted) exposes `updated_at` to every caller that renders a fact, where it reads as "content last modified". Risk: after this change a stale-but-frequently-retrieved fact sorts as recently updated, so it can push genuinely recent facts out of `contradict()`'s 500-row window, and the row no longer means what its name says anywhere it is displayed. Suggested fix: record retrieval recency in its own column (e.g. `last_retrieved_at`, alongside the `retrieval_count` this PR is already reviving) and keep `updated_at` for content revision — or, if the single column is deliberate, key `contradict()`'s window on `created_at`/`trust_score` instead so its semantics do not ride on retrieval traffic.
