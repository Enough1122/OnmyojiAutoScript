One behavioral gap below, plus two nits.

1. The explainer never renders on the bot-active path — the case the linked issue describes. The guard is `Boolean(profile)` (providers-settings.tsx:183) where `profile` is `profile={scopeProfile}` (:563) and `scopeProfile = useStore($settingsRequestProfile)` (:378). That store is `override ?? undefined` (store/settings-scope.ts:45-48), i.e. it is only set when the user explicitly picked a scope chip for a profile *other than* the app-wide active one; `setSettingsScope` stores `null` when you pick the profile you are already on (settings-scope.ts:53-57), and an app-wide profile switch drops the override (settings-scope.ts:65-72). Meanwhile "no override" does not mean "launch profile": the same store documents that the scope then follows the app's active profile, "which, after opening any Bot Mode chat, is the BOT's profile" (settings-scope.ts:19-26), and `profileScoped(undefined)` resolves to `_apiProfile` (api/client.ts:66-73). Repro: open a bot chat (active profile = the bot), then Settings → Providers → Accounts. `listOAuthProviders(undefined)` returns the bot's own providers with no logins, so `connected.length === 0 && collapsible` is true — but `Boolean(profile)` is false, so the note is not rendered and the sign-in rows stay collapsed behind "Other providers": exactly the "the update wiped my sign-ins" state (#117325) this PR set out to explain. The only thing the user gets on that path is the generic loud "edits <profile>" chip note (app/settings/profile-scope.tsx:95-106), which says nothing about single-use logins. The comment at providers-settings.tsx:181-182 ("The launch profile (no `profile` scope) … keep the existing collapsed-by-default page") therefore contradicts the store's own semantics. Suggested fix: key the predicate on the scope *target* being a non-default profile rather than on the presence of an explicit override — e.g. reuse `$settingsScopeEditsNonDefault` (settings-scope.ts:27-31) or compare `$settingsScopeProfile` against the roster's `is_default` entry. That covers both paths and also avoids claiming "each bot signs in separately" when the explicitly-picked scope is the default profile. Please confirm whether the bot-active path was intentionally left out of scope.
