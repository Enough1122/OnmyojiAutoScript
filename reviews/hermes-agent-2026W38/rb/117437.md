This PR lets a scheduled cron job recover a fire that a provider quota hold consumed. `mark_job_run` gains a `quota_recover_occurrence` flag (cron/jobs.py:2352) that becomes `plan_hold(..., recover_consumed_fire=...)` (cron/quota_hold.py:86-87): when the flag is set and the job's natural next occurrence is already at/after the recovery boundary, the job is parked at the boundary itself (cron/quota_hold.py:110-114) instead of at the first legal occurrence after it, and `_reanchor_stale_cron` learns to let that one off-lattice instant fire rather than re-anchor past it (cron/jobs.py:2966-2973), guarded by a new `quota_hold_cron_expr` fingerprint so a hand-edited expr still re-anchors (cron/quota_hold.py:72-83, 118-120). The scheduler wires the flag from the dispatch snapshot's `_scheduled_instant`, so manual runs and interval jobs keep the natural schedule (cron/scheduler.py:2854). I checked the due-scan order (`_rearm_stale_error_recurring` → `d.next_run_dt > now` → `_reanchor_stale_cron`), the `_classify_stale_cron_next_run` discriminator (an off-lattice instant can only classify as `STALE_CRON_EXPR_EDIT`, so the new branch is reachable and `is_recovery_fire` is actually consulted), the `_repair_timezone_shifted_cron` guard (a park written from `_hermes_now()` carries the profile offset, so no offset mismatch grabs it first), and the manual-run path (`_scheduled_instant` is None for `manual_run`, jobs.py:3132 upstream). No correctness blocker found: the at-most-once story holds (completion rewrites the instant), and the new test does pin the fire path — `get_due_jobs()` excludes re-anchored jobs, so tests/cron/test_quota_hold.py:81 would fail if the recovery branch regressed. The two points below are behavioral/doc decisions I could not settle from the diff alone.

1. The recovery branch is not gated on "sparse" — every scheduled cron gets one off-lattice fire (cron/quota_hold.py:110-114). The branch triggers whenever `natural_next >= window_end` and the run was scheduled, with no cadence test. Repro: an hourly job (`0 * * * *`) fires 12:00 and fails with a rate-limited `AuthError` carrying `retry after 1800s`; `_advance_after_run` leaves `next_run_at = 13:00`, `window_end = 12:31`, `13:00 >= 12:31` → `parked = window_end.isoformat()` (12:31, an instant `0 * * * *` excludes) → `_reanchor_stale_cron` classifies it `STALE_CRON_EXPR_EDIT` → `is_recovery_fire` is true → the job runs at ~12:31 and again at 13:00. Before this PR that case took the `clear_state(); return False` path and simply kept 13:00 (upstream cron/quota_hold.py:81-83), i.e. the blocked occurrence was dropped because nothing was actually blocked. So for a dense schedule the PR adds an extra run at an off-lattice time, ~29 minutes before the next natural one, while every scope statement says sparse: cron/jobs.py:2369 ("a scheduled sparse cron"), cron/jobs.py:2969-2970 ("a sparse cron's next natural occurrence"), cron/quota_hold.py:90. Risk is low (one extra run per hold, same provider probe cost the coalesce path already pays), but it is a silent semantic widening of a deliberate rule — the surviving half of the old comment at cron/quota_hold.py:116 still says "first legal instant", and the recovery branch is exactly the "fire at a time the expression excludes" case the old code avoided. Suggested fix: gate on cadence (e.g. only recover when `natural_next - window_end` is at least one period, reusing `_schedule_cadence_seconds`), or, if the widening is intended, say "any scheduled cron" in the three places above and add a dense-schedule case to tests/cron/test_quota_hold.py.

2. "Retries once" is not what the code does — a failed recovery fire re-parks and retries at every new boundary (cron/quota_hold.py:110-114 + cron/jobs.py:2392-2394 + cron/scheduler.py:2854). The docs say "a blocked scheduled occurrence retries once at that recovery boundary" (website/docs/user-guide/features/cron.md:459-460), and jobs.py:2969-2970 says "one off-lattice recovery fire". But `quota_recover_occurrence` is derived from `bool(job.get("_scheduled_instant"))`, which the recovery fire itself carries (it is a normal scheduled dispatch), so if it fails again with a fresh `retry after` hint, `plan_hold` is re-entered with `recover_consumed_fire=True`; for a sparse job the natural next occurrence is once more at/after the new `window_end`, so the job is parked at that new boundary and fires off-lattice again. Consequence: a job whose provider keeps answering with short hints while staying closed is converted from its natural cadence into a probe loop at roughly one fire per hold window — a weekly job in a three-week outage probes ~25 times instead of 3, each probe a provider request plus a failure alert (subject to the incident cooldown). That is the cost cron/quota_hold.py:5-9 says the hold exists to avoid. Fairness note: dense crons already behaved this way pre-PR through the coalesce branch, so this extends existing behavior to sparse jobs rather than inventing a new mechanism — please confirm that is intended. If yes, fix the "once" wording in the three places above and consider bounding it (e.g. stop recovering after K consecutive recovery failures, or keep a counter next to `SCHEDULE_EXPR_KEY`); if no, only the original blocked occurrence should retry once.
