> AI code review — automated follow-up for reference; not a maintainer.

This PR adds a "synthetic native source" ingress mode to the webhook platform: a route may now declare `source_platform` + `source_chat_id`/`source_user_id` (plus optional `source_thread_id` / `source_new_thread`), and instead of spawning the webhook's own agent run the handler builds a `SessionSource`/`MessageEvent` and hands it to the target platform adapter's `handle_message`, so the run executes in that platform's session with its toolsets, history and reply routing. It also adds base64 media ingress (`audio_base64`/`voice_base64`, `screenshot_base64`/`image_base64`) that is written through `cache_audio_from_bytes` / `cache_image_from_bytes` and attached as `media_urls`/`media_types`, with MIME allowlists, one-media-per-request enforcement, and delivery-marker/media rollback when the pre-202 steps fail. The design is careful about ordering (validation and adapter availability are checked before any side effect, idempotency marker is refunded on failure, media is cached only for synthetic routes so ordinary routes don't acknowledge-then-discard attachments) and the accompanying test file `tests/gateway/test_webhook_synthetic_source.py` covers the media, retry and rejection paths well. The one substantive gap is that the dispatch itself bypasses the inbound pre-processing the codebase requires for synthetic events, which silently breaks reply egress on relay-fronted targets.

1. **`handle_message` is called without the target adapter's synthetic-event priming — relay replies are declined (blocker).**
   `gateway/platforms/webhook.py:777` does `task = asyncio.create_task(target_adapter.handle_message(event))` directly. The codebase already has a contract for injecting synthetic events into `handle_message`: warm the egress routing caches first. `gateway/relay/adapter.py:1027-1031` (`prime_routing_cache`) states it explicitly — a synthetic event "reaches handle_message with the caches COLD, so its replies egress without scope_id/user_id and the connector's fail-closed tenant guard declines them" — and the existing injection path follows it: `gateway/run_notifications.py:1204-1207` ("Relay egress priming: post-restart routing caches are cold (they warm only on inbound), so replies would egress without tenant discriminators and be declined by the connector") calls `prime_routing_cache` before `handle_message`, with a dedicated regression test asserting the wiring at `tests/gateway/test_relay_injection_egress_priming.py:71-113`.
   Risk / repro: the discriminators are captured only from real inbound traffic (`gateway/relay/adapter.py:1036-1066`), so on a relay-fronted target (the platform this PR's own test uses — `tests/gateway/test_webhook_synthetic_source.py:58` builds a `RelayAdapter` for `telegram`) any webhook-triggered run for a chat that has not received a genuine inbound message since process start produces a reply that the connector declines; the webhook already returned 202 at `gateway/platforms/webhook.py:780-781`, so the failure is silent. The test cannot catch it because `_start_session_processing` is stubbed (`tests/gateway/test_webhook_synthetic_source.py:62`), so egress is never exercised.
   Suggested fix: before the `create_task`, mirror the existing call site —
   ```python
   _prime = getattr(target_adapter, "prime_routing_cache", None)
   if callable(_prime):
       _prime(event)          # relay: warms scope_id/user_id per chat
   ```
   and add an assertion in the test that priming happened before `handle_message` (the pattern used in `tests/gateway/test_relay_injection_egress_priming.py:71-113`).

2. **202 is returned before the target platform's authorization gate decides, and the configured source identity is never checked (nonblocking).**
   `gateway/platforms/webhook.py:780-781` acknowledges the delivery as soon as the adapter is running and callable; the runner's ingress gate `_is_user_authorized_for_source` runs later, inside the spawned run (`gateway/run_inbound.py:230`), and it does apply here because the synthetic event does not set `internal=True` (`gateway/run_inbound.py:191`). So a route whose `source_user_id` is not authorized on the target platform still gets `202 accepted`, and the run is then dropped. Worse, for DM sources the gate's unauthorized path can emit outbound traffic to `source_chat_id` (pairing code / one-time decline, `gateway/run_inbound.py:236-245`), i.e. the webhook can make the bot message an arbitrary chat id — please confirm that is intended.
   Suggested fix: validate the configured source identity against the target platform's authorization inside `_validate_synthetic_source` / the HTTP check at `gateway/platforms/webhook.py:615-618` (fail closed with 503/500 rather than 202), and document that `source_chat_id`/`source_user_id` must be an authorized identity on the target platform.

3. **Cached media is never reclaimed when the event is dropped after the 202 (nonblocking).**
   Files are written at `gateway/platforms/webhook.py:705/709` and are only unlinked by the pre-202 rollbacks (`gateway/platforms/webhook.py:712-718` and `744-749`). Once the 202 is returned, the target adapter can still drop the event (no message handler, unresolved identity, session guard / pending queue) and no hook reclaims the cache: `WebhookAdapter.on_processing_complete` (`gateway/platforms/webhook.py:670`) only closes its own per-delivery sessions and is not invoked for target-adapter runs (the hook belongs to the adapter that ran `handle_message`, `gateway/platforms/base.py:4450`).
   Suggested fix: best-effort unlink in a done-callback on the spawned task when `event._gateway_accepted` is not True, or state the cache directory's TTL as the intended reclamation path.

4. **`deliver` / `deliver_extra` are accepted but silently inert on synthetic routes (nonblocking).**
   `_validate_synthetic_source` rejects `coalesce`, `cron_job` and `deliver_only` (`gateway/platforms/webhook.py:247-249`) but not `deliver`/`deliver_extra`; the synthetic branch returns at `gateway/platforms/webhook.py:780` and never reaches `_spawn_agent_run`, which is what populates `_delivery_info` for cross-platform reply routing. A route configured with both `source_platform` and `deliver: telegram` therefore silently ignores the delivery config.
   Suggested fix: add `deliver` / `deliver_extra` to the mutually-exclusive list (or document them as ignored when `source_platform` is set).
