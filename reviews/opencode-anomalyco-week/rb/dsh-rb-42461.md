Good catch — comparing message IDs lexically (`id < to`) only worked while IDs happened to sort chronologically, and the updated fixtures (`msg_fff` before `msg_000`) pin down exactly that failure mode. Switching to identity-based `findIndex` + slice is the right call.

One behavior change worth a closer look:

1. **Boundary-not-found fallback**: previously the comparison always produced *some* partition. Now, when `event.data.to` isn't present in the local list, `input` keeps everything and `removed` is empty (`boundary < 0 ? items : ...`, `removed = []`). That's correct when all local messages precede the boundary, but in a partial-hydration scenario where the boundary itself was never fetched (everything local sits *after* it), stale messages stay visible until server reconciliation catches up. The `projectV2` pass may heal this, but it would be good to either confirm that path covers it or add an explicit test for "revert target missing from local state".
2. **Ordering assumption**: slicing relies on the input/message lists being chronological. That seems to be an existing invariant, just calling it out since the old code didn't depend on list order.
3. Nice consistent treatment across `server-session.ts`, TUI `data.tsx`, and `rows.ts` — including the matching `===` in the draft splice. The duplicated test updates in both app and TUI suites give this solid regression coverage.

LGTM modulo the not-found edge case above.
