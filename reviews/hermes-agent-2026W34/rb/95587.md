This PR fixes the Desktop Files rail so it stays rooted at the active top session tab instead of always the primary sidebar selection, keeps workspace-attached tools bound to that tab when a tool zone has keyboard focus, fronts the Files pane before a Reveal-in-File-Tree selection, and fails closed when the focused session belongs to a different remote filesystem route. The workspace-context / focused-session split and the remote-owner guard are well thought out, and the test coverage (unit + focused regression suite) is solid. A few observations:

1. **The CWD precedence for the primary chat changed (deliberate, but worth flagging for reviewers).** `resolveFocusedWorkspaceCwd` (use-focused-workspace-cwd.ts:57) now tries `primaryCwd` (`$currentCwd`) *before* `focusedRowCwd` (the stored session row), whereas the previous inline logic in `use-statusbar-items.tsx` tried `focusedRowCwd` first. The new unit test "keeps the live primary CWD ahead of its launch row after an in-session relocation" pins the new order, and the ownership-token guard (`workspaceCwdOwner === selectedStoredSessionId`) prevents the stale-path case, so it is fail-closed rather than a regression. Still, this now affects every consumer of the statusbar's `currentCwd` (project label, focus-sensitive status chrome), not just Files — if any of those relied on the stored-row snapshot winning over a live but unrelocated `$currentCwd`, the visible label can flip. Worth confirming the statusbar and Files both want the same precedence; the fact that both share the hook suggests they do.

2. **`projectNameForCwd` now runs on every statusbar render (minor).** use-statusbar-items.tsx:170 computes `projectNameForCwd(currentCwd)` directly after a subscribe-only `useStore($projectTree)` (line ~168), replacing the previous `useMemo(..., [currentCwd, projectTree])`. The statusbar re-renders on busy/usage/gateway state churn, so if `projectNameForCwd` scans the project tree each time this is avoidable recomputation. The tree value is already in scope from `useStore($projectTree)` — re-adding the memo with `[currentCwd, projectTree]` (or binding the tree to the dependency list) restores the old behavior with no cost.

3. **`sessionFilesystemSharesAmbientConnection` is fail-open for sessions with no resolvable owner (verify).** At session-states.ts:1014 a session with `!owner` returns `true`, i.e. it may use the ambient Files bridge. That is correct for ordinary top tabs, but it means the cross-remote guard is only as strong as `knownOwnerForSession`: any remote-owned session whose owner fails to resolve (stale tile, missing hint, untagged row) silently browses the ambient connection — exactly the wrong-machine case the guard exists to prevent. Since the failure mode is the very bug this PR fixes, it may be worth making the "no owner" branch explicit about the session being *known-local* (e.g. the primary or a local tile), and treating a remote-looking session with a missing owner as an error rather than allowing the ambient read. This is a verify-please note rather than a definite bug — the local-profile-pool case legitimately needs the fail-open default.

The refactor is clean: the `$workspaceContextStoredSessionId` derivation (session-states.ts:1614) correctly distinguishes "interacted zone is a chat strip" from "interacted zone is a tool zone", and the `revealFileInTree` change (store/layout.ts) correctly fronts the Files pane before the selection lands. Points 2 and 3 are minor.
