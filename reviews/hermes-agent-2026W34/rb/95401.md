This PR adds OMH's ephemeral runtime paths to the root `.gitignore` (`.omh/README.md`, `.omh/.gitignore`, `.omh/state/`, `.omh/logs/`, `.omh/progress/`) so repo-owned scaffolding doesn't make a parked checkout look dirty and block `hermes update`'s auto-switch. The premise is sound — git doesn't read an ignore file inside an untracked directory, so the nested `.omh/.gitignore` never helped — and the scoping is deliberately precise rather than a blanket `.omh/` rule.

Points:

1. The ignore list is an enumeration of today's runtime output, not a stable pattern. If OMH later materialises anything under `.omh/` that isn't in this list (a new per-session dir, a lock file, `.omh/.cache/`), it shows up as untracked, `git status --porcelain` is non-empty, and the `dirty` guard strands the checkout again — the same silent drift, just from a different file. Since the list is the whole fix, it's worth a comment (or a small note in `.omh/README.md`) stating this is the complete set of ephemeral paths that must be kept in sync, or preferring a rule that captures the per-session prefix more broadly if the runtime guarantees one.

2. Minor git-behavior note worth being explicit about: git reports an untracked directory with any unignored content as the folded `?? .omh/` entry. That's fine here — `specs/`, `plans/`, `research/` are intended to stay committable, and user content there *should* make the tree dirty — but it means the fix only holds if the runtime never writes unlisted transient files. Confirming that invariant (or adding a cheap `git check-ignore` / `git status --porcelain` guard in a test or CI step) would harden it.

The rules themselves are correctly scoped: `.omh/`-prefixed, trailing slashes on the directory patterns, files as exact paths — no accidental matches elsewhere.
