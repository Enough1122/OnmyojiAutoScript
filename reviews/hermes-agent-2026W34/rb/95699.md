This PR fixes stale bot avatars and stale intro previews in Bot Mode. The `tui_gateway` `profiles.list` rows now carry a cheap `avatar_size` + `avatar_mtime` fingerprint from a plain `stat()` (no asset read on the 5s roster poll), and the hermes-bots plugin revalidates the local avatar cache against it, drops server-cleared art, and stops showing the onboarding "Hey, tell me about yourself!" prompt once a profile has a description. The fingerprint is clean, the write-fence intent is sound, and test coverage is strong.

Points:

1. The backfilled-face early-return can cause an infinite refetch loop. In `fetchServerAvatar` (`apps/desktop/src/plugins/hermes-bots/plugin.js:2595`), when the fetched asset is a backfilled 160px face raster and the cached image is not a photo/pet, the function returns without updating `imageStamp`. On a revalidation fetch this leaves the stamp stale, so the next roster poll sees `stamp !== mine.imageStamp` again and refetches — repeating every 5s indefinitely for any bot whose server avatar is such a raster. Recording the stamp even on this early-return path (or excluding the early-return case from the refetch condition) would let the revalidation settle. Minor since the trigger is narrow, but the consequence is unbounded.

2. The write fence is checked at dispatch time, not write time (TOCTOU). In `pullServerAvatars` (`apps/desktop/src/plugins/hermes-bots/plugin.js:2673`), `fetchedAt < botMetaWriteAt.get(key)` is evaluated before `fetchServerAvatar` is dispatched, but the actual `$botMeta.set` overwrite happens later when the promise resolves. A local save landing between dispatch and resolve can still be clobbered by older server bytes, so the PR's claim that "all overwrites are fenced" isn't strictly true. Re-checking the fence inside `fetchServerAvatar` immediately before the `set` would close the window.

3. Legacy caches (image but no `imageStamp`) are not protected from resurrection. Both the server-cleared drop path (`mine.image && mine.imageStamp`, `plugin.js:2644-2645`) and the `pushLocalAvatars` guard (`has_avatar === false && imageStamp`, `plugin.js:2474`) require a recorded stamp. A cache that predates fingerprinting whose server avatar is cleared in the same window is backfilled by `pushLocalAvatars` (which runs before the per-bot loop) and then skipped by the drop path — so deleted art is resurrected once before a validation cycle records the stamp. Harmless after one cycle, but worth a test covering the legacy-cache + server-cleared combination.

The `introOnlyPreview` change and the shared `BOT_INTRO_PROMPT` constant are clean; message-count/preview heuristics look reasonable.
