This PR adds tappable follow-up actions to delivered agent replies: the finished answer is handed to the `suggested_actions` auxiliary task, and Telegram renders the proposed next steps as an inline keyboard edited onto the reply; a tap re-enters through the normal `handle_message` path as a fresh user turn. The design (auxiliary model rather than a main-model tool, off-by-default config gate, label-as-text containment, pop-once registry) is sound, well-tested, and keeps the main conversation's prompt untouched.

Points:

1. The auxiliary generation is awaited inline, so turn completion still blocks on the cheap model. `_maybe_offer_suggested_actions` runs `actions = await asyncio.to_thread(_sa.generate, ...)` inside `_process_message_background` (`gateway/platforms/base.py:4565`). There is no `threading.Event`, so the agent thread is free, but the turn's coroutine does not complete until the auxiliary call returns — with the default `timeout: 20` (`hermes_cli/config_defaults.py:1126`) and a slow/`:free` backend that could be tens of seconds. That delays the processing-complete hook, the session-busy release, and the drain of any message queued while generation runs. The guard `if session_key in self._pending_messages` (`gateway/platforms/base.py:4544`) only catches messages already pending before generation starts. Consider dispatching this as a fire-and-forget `asyncio.create_task` (moving the accounting-context setup inside the task) so the turn finishes independently of the auxiliary call's latency.

2. Dead code: `entry = _sa.get(set_id)` in `_handle_suggested_action_callback` (`plugins/platforms/telegram/adapter.py:7729`) fetches the set but the result is never used — `resolve()` is called immediately after and handles the pop. The lookup is a no-op; drop it.

3. The registry has no TTL. An unclaimed set lives until superseded by the same session's next set or evicted at the 512 cap (`MAX_TRACKED_SESSIONS`); there is no `expires_at` field. This is documented and memory-bounded, so it's minor, but a stale keyboard can resolve successfully well after the conversation has moved on if the session never gets a newer set — the user-facing "no longer available" path only triggers on double-tap/supersede. A modest time-based expiry on `resolve`/`get` would keep behavior closer to the 10-minute semantics the Telegram action-button PR (95594) documents for the same class of feature.

Minor: `_parse_response`'s fallback regex `\[.*\]` with `re.DOTALL` is greedy, so prose containing more than one bracketed span can over-capture past the real array and fail the JSON parse, silently yielding no buttons. Narrowing to a balanced-array match would be more robust on small models that narrate.
