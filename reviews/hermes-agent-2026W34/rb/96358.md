This PR fixes the Salesforce browser-storm (#96320) by gating `webbrowser.open()` in the MCP OAuth redirect handler on an explicit `force_interactive_oauth()` scope instead of the old `_is_interactive() && _can_open_browser()` heuristic, and adds a per-flow dedup set so one user-driven scope opens at most one tab per server. The gate is the right mechanism: CLI `hermes mcp login` (hermes_cli/mcp_config.py) and the dashboard Authorize flow (hermes_cli/web_server.py) both enter the forced scope, while reconnect and parked self-probes never do, and the dashboard flow returns before the browser-open code so no duplicate tab appears there. The fix is sound; a few observations:

1. **The "at most one tab per server per scope" guarantee only holds where `server_name` is passed (verify all call sites).** Dedup is keyed by `server_name`, and `_make_redirect_handler` explicitly disables it when `server_name is None` (tools/mcp_oauth.py:947 — `if server_name is not None and server_name in _oauth_browser_opened_for_flow`). The diff threads `server_name` through `build_oauth_auth` and one manager call site, but the gate itself is server-name-independent while dedup is not. If any `_make_redirect_handler(...)` caller — e.g. the provider-construction path in `mcp_oauth_manager.py` that also builds a redirect handler — is left without `server_name`, an SDK mid-flow re-entry there still opens multiple tabs within one forced scope (smaller scale than the original storm, but the same class). Worth a sweep of all `_make_redirect_handler` call sites to confirm none are missed.

2. **The reconnect/parked-probe cadence now produces recurring stderr noise instead of tabs (minor).** Every non-forced invocation that reaches the handler prints the multi-line "Skipped auto-open … Run `hermes mcp login <server>` to authorize" notice (tools/mcp_oauth.py:931-941) — at the same ~5-minute cadence that previously opened tabs. On a healthy parked server this is repeated log noise carrying an instruction the operator does not actually need (the server is fine; nothing is pending authorization). Since the URL is already printed above, consider downgrading this to a single line, making it debug-level, or rate-limiting it per server so a long-parked server doesn't accumulate hundreds of "run hermes mcp login" lines.

3. **The module-global dedup set is mutated with a non-atomic check-then-add (minor).** `_oauth_browser_opened_for_flow` (tools/mcp_oauth.py:184) is a plain module-level `set`, and the handler is async: two re-entries scheduled concurrently (e.g. overlapping tasks for the same server) can both pass the `in` check at line 947 before either adds, and both open a tab. In practice SDK re-entry appears sequential, and the snapshot/restore in `force_interactive_oauth` (line 380) correctly resets state per user-driven attempt — this is just a note that the dedup is a sequential-flow guard, not a concurrency-safe one, which the docstring's "re-entry" framing could make explicit.

The gate change is correct and well tested (the regression tests fail pre-fix with the right error, and the positive/dedup/re-entry/dashboard cases are all covered). Point 1 is the one to verify; points 2–3 are hardening notes.
