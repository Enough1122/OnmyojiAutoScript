This PR makes `/init` resolve the session's active directory (terminal per-session cwd record, then the `resolve_agent_cwd()` ladder) instead of `os.getcwd()`, so a desktop session attached to a workspace scans/writes that workspace's `AGENTS.md` rather than the home dir the process launched from. The design and tests are solid; one edge case leaks through.

- The stale-record fall-through is not applied on the TUI path. `hermes_cli/init_command.py:167` (`if recorded and os.path.isdir(recorded)`) correctly skips a deleted-directory record inside `_resolve_session_cwd`, and `test_stale_record_falls_back_to_process_cwd` covers it. But `tui_gateway/methods_tools.py:606` calls `get_session_cwd(_init_skey)` and passes the result straight through as `cwd` at `tui_gateway/methods_tools.py:617` — and `get_session_cwd` (tools/terminal_tool.py:1215) does not validate the directory. Since `build_init_prompt_for_cwd` uses `cwd if cwd else _resolve_session_cwd(session_key)`, a truthy but deleted record wins on the desktop/TUI surface, contradicting the PR's stated "stale record (directory deleted) falls through to the ladder". Suggest applying the same `os.path.isdir` guard before passing `cwd`, or moving the existence check inside `build_init_prompt_for_cwd` so all three dispatch surfaces share it. A regression test mirroring `test_stale_record_falls_back_to_process_cwd` but driving the TUI path (stale record + `_session_cwd` empty) would pin this.

- Minor: `gateway/run.py` passes `session_key=self._session_key_for_source(source)`; it would be worth confirming that key matches the `session_key` value the terminal tool records cwds under for gateway sessions (the tests use a literal `"gateway:999"`), so the record is actually consulted rather than silently missed.
