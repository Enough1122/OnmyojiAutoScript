This PR derives a stable model preference order from the configured primary model plus `fallback_providers`, and applies it to the shared model inventory payload, the classic `hermes model` picker, and the Desktop catalog menu (falling back to the historical alphabetical order when a backend doesn't advertise `preferred_models`). The Python side is well-tested and reads the correct config keys (`model.default` / `model.model` match existing call sites). Two cross-surface risks worth a look:

- Provider-identity normalization must agree between Python and TypeScript, or the Desktop sort silently no-ops. `hermes_cli/inventory.py:85` `_provider_order_identity` normalizes through `hermes_cli.models.normalize_provider`, and the payload emits those normalized identities; on the desktop side `model-catalog-menu.tsx:564` builds `preferredRanks` from `normalize(entry.provider)`. The Python test pins that `grok-oauth` → `xai-oauth` on the Python side, but there is no TS-side test proving `normalize()` yields the same identity for a slug that needs aliasing. If they diverge (e.g. `openai-codex` vs `openai`), the desktop falls back to alphabetical — the very bug being fixed. A TS test with an aliased provider would close this.

- `groupModels` sorts model *families* by the rank of `family.id` (`model-catalog-menu.tsx:617`), but `preferredRanks` is keyed by model name. When `collapseModelFamilies` produces a family id that differs from the configured model name (multi-model families), the within-provider model ordering silently no-ops. The new desktop test uses single-model families only, so this path is unexercised — worth verifying family-id semantics with a multi-model provider.

- Minor: the `hermes_cli/auth.py` reorder is wrapped in a bare `except Exception: pass`, so a malformed config entry silently degrades to the old ordering with no signal. A `logger.debug` would make that diagnosable.
