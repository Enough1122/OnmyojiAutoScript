This PR fixes a real spend-loop: `release_stale_claims()` now records each actual reclaim as a failed attempt via `_record_task_failure()`, so `max_retries` is enforced instead of a crashing worker requeueing forever. It also adds `enforce_runaway_limits()` (absolute per-task caps on total runs and total runtime, hard-blocking with `block_kind='capability'`) and classifies "Reached max turns" worker logs as an explicit failure reason. The integration test coverage is good.

Points:

1. The run-count cap counts ALL lifetime runs, including successful ones. `_task_run_totals` sums every row in `task_runs` for the task (`hermes_cli/kanban_db.py:8068`) and `enforce_runaway_limits` trips when `run_count >= max_runs` (`hermes_cli/kanban_db.py:8069`). A task that a user legitimately re-opens and re-dispatches (a recurring task, or a manual requeue after a fix) accrues run_count from its successful runs too, so after 8 total lifetime runs it is hard-blocked with `block_kind='capability'` even with zero failures. This is a deliberate cost-safety guard, but the cap is lifetime-total, not non-success count — worth documenting clearly (and possibly counting only non-success runs) so a legitimate long-lived task isn't silently bricked at run 8.

2. `_worker_hit_max_turns` scans the entire 64 KB log tail, not just the current run's span. `return b"reached max turns" in handle.read().lower()` (`hermes_cli/kanban_db.py:8326`) matches the phrase anywhere in the tail. If a previous run of the same task ended "Reached max turns" and the current run crashes with a different error (within the same tail window), the current crash is misclassified as turn-budget exhaustion — and the PR specifically relies on this classification to surface the right failure reason. A substring match can also fire if the agent merely quotes the phrase in a reply. Scoping the search to the current run's log portion (or anchoring on a run-start marker) would reduce false positives.

3. Minor (repo convention): the new `kanban.max_total_runs_per_task` / `kanban.max_total_runtime_seconds_per_task` keys are read at runtime via `load_config_readonly()` but are not added to `DEFAULT_CONFIG` in `hermes_cli/config_defaults.py` (the diff doesn't touch it). They work if a user sets them manually in config.yaml (the deep-merge preserves unknown keys), but they are undiscoverable and undocumented in the defaults — adding them to the kanban defaults block would surface them through the usual config paths.

4. Minor: `release_stale_claims` stores per-call state on the function object (`release_stale_claims._last_auto_blocked = []`, `hermes_cli/kanban_db.py:4985`), which `_dispatch_once_locked` reads back immediately after the call. This works for the single dispatcher path, but it's shared mutable state on a module function; if the function is ever invoked from another context, the attribute read could see stale data. A local return value would be cleaner. (Also a nit: `failure_limit: int = None` should be `Optional[int]`.)
