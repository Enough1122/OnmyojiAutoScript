This PR fixes the Desktop fleet rail when the registry primary is a remote gateway: a deferred local source is inventoried from `$HERMES_HOME/profiles` on disk (no backend spawned), shown at rest as "connect-on-demand" instead of "unreachable", kept out of the plugin route table so relay sweeps can't dial it, and the rail re-pulls the roster when the active gateway changes. The separation between display rows (roster) and dialable routes (plugin routes) is a clean solution to the phantom-spawn problem, and the e2e is thorough. A few observations:

1. **`$activeConnectionId.listen` fires on every `set`, even with an identical value (verify).** use-fleet-roster.ts:37 subscribes with `listen` and the comment claims it "fires only when the active gateway actually moves" and produces "no extra IPC on same-source clicks". nanostore's `listen` does not dedupe by value equality — it fires on every `.set()`. If any code path re-sets the already-active connection id (e.g. re-homing on the current gateway, a startup restore, or a same-source square click that still writes the id), each such set triggers a forced `refreshFleetRoster({ force: true })`, i.e. a `hermes:agents:roster` IPC round-trip that also ignores the 60s stale window. If the set sites only ever write on an actual change this is moot; otherwise a value-equality guard inside the listener (or comparing against the previous id) would make the "no same-source churn" claim robust.

2. **A runtime-less "This device" is now painted reachable with an undialable `default` square.** The reachability rule at fleet-rail.ts:97 (`source.reachable || source.error === 'connect-on-demand'`) forces `reachable: true` whenever the source carries `error: 'connect-on-demand'`. But that error is also emitted when `localRuntimeAvailable()` is false — `readLocalProfileInventory()` returns `null` (main.ts:14005) and the source is `{ profiles: null, error: 'connect-on-demand' }`. The rail then renders This device green/at-rest with only the always-rendered `default` square; clicking it dials a backend that cannot start (no runtime). Before this PR that desktop showed the amber dot (clearly broken); now it looks healthy and fails only on click. Distinguishing "no runtime at all" (render at rest but non-actionable / omit the group) from "runtime present but deferred" would avoid the misleading green state. The new unit test at fleet-rail.test.ts (the `noRuntime` case) explicitly bakes in `reachable === true` for this scenario, so it's a deliberate choice — worth confirming it reads as intended to end users.

3. **`readLocalProfileInventory` returns `['default']` for any existing `HERMES_HOME`, initialized or not (minor).** `profileInventoryFromNames([])` always yields `['default']` (connection-registry.ts), so if `HERMES_HOME` merely exists — created by an earlier partial setup or a leftover directory — a This-device `default` square is seeded even though Hermes has never initialized the home. Clicking it then spawns the backend, which is acceptable user intent, but combined with point 2 a stale/empty home on a machine with a runtime available shows a green square where nothing real exists yet. Requiring a sentinel (e.g. the home containing `config.yaml` or a `profiles/` dir, mirroring how the SSH listing only surfaces real dirs) would tighten the disk inventory.

Points 2 and 3 are minor and the second is clearly a deliberate design trade-off; point 1 is the one worth a quick verification. The core fix — display-only seeded rows, routes filtered from the sweep, fresh re-pull on switch — is sound and well covered by tests.
