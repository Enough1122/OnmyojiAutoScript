This PR makes the Feishu doc/drive tools usable outside the Feishu comment-event context by adding a `get_client()` fallback that builds a `lark_oapi` client from the `FEISHU_APP_ID` / `FEISHU_APP_SECRET` env credentials (the same ones the Feishu platform adapter reads), cached per-thread with the injected client always taking priority. It is minimal, backward-compatible for the comment path, and well unit-tested. A few observations:

1. **The fallback widens Feishu doc/drive access to every session in a process that has the env credentials — including delegated children.** `get_client()` (tools/feishu_doc_tool.py:25) builds the client whenever the env vars are present, with no context check beyond "no injected client" — so CLI sessions, DMs, and `delegate_task` child contexts all gain runtime access to the tenant. The tools were already exposed in the schema (their `check_fn` only gates on `lark_oapi` being importable), so the schema surface is unchanged — but the *runtime* authority boundary is: previously doc/drive access was restricted to comment-event contexts; now it is process-wide whenever credentials are in the environment. Given the repo's care about delegated-child least-privilege (the `_assert_not_delegated_child_mutation` pattern elsewhere), it is worth confirming this process-wide access is intended, or gating the env fallback out of delegated-child contexts.

2. **The failure mode changes from a clean "not available" to app-credential authorization errors.** When the fallback engages, the tool no longer returns the clear `Feishu client not available (not in a Feishu comment context)` message; it attempts a real API call with the raw app credentials, which may not be granted access to an arbitrary user's doc. The user then sees a Feishu-side permission error (or a truncated/failed read) instead of the explicit "not available" signal. This is arguably the better trade — attempt and surface the real error — but the two failure modes are now conflated from the agent's perspective, so a short note (or a distinct message when falling back) would help agents attribute permission failures correctly.

3. **The ~25-line `get_client()` fallback body is duplicated verbatim across `feishu_doc_tool.py` and `feishu_drive_tool.py`.** Both copies (env reads, `lark_oapi` import, fluent builder chain, `_local.client` write) must be kept in lockstep; the repo convention favors extending shared code over duplication. Extracting the fallback into a single shared helper both tools import would remove the drift risk and let the env-cache/per-thread semantics live in one place.

4. **Stale per-thread env cache (minor).** The built client is cached in `_local.client` (tools/feishu_doc_tool.py:48), so if the env credentials are removed or swapped mid-process (e.g. a profile/home switch that changes which `.env` applies), the cached client persists rather than rebuilding. Env creds rarely change at runtime, so this is low-impact, but a thread-local that keyed on the credential values (or cleared on `set_client(None)`) would be strictly more correct.

The fix's core direction is sound and the tests cover construction, caching, priority, and partial-credential rejection well. Points 1–2 are the ones worth an explicit decision; 3–4 are maintainability/hardening notes.
