This PR (stacked on #80207) adds user-customisable prompt templates to the desktop composer's `+` menu, with collapsible folder nesting and drag-and-drop on top of a flat `parentId` tree persisted through `persistentAtom`. The store logic is careful — cycle guards, descendant-block moves, legacy-v1 normalization, locale-aware lazy seeding, and a 449-line vitest suite covering CRUD/tree/`placeNode` — and the DnD commit path is well thought out.

Points:

1. Tree traversal is recursive with no depth bound. `visibleTreeRows` (`apps/desktop/src/store/prompt-templates.ts:200`) recurses `walk(parentId, depth+1)` for every expanded folder, and nothing caps nesting depth. `placeNode` allows arbitrarily deep nesting by repeated `inside` drops (it only rejects self-subtree/cycle cases), so a tree can legitimately grow hundreds of levels deep, at which point the recursive walk and the per-level `paddingLeft: ${0.625 + depth * 0.75}rem` rendering become both a stack and a layout concern. `collectDescendantIds` is already iterative — making `visibleTreeRows` iterative, or adding a depth cap in `placeNode`/`repairTree`, would close the edge. Minor, but cheap to harden.

2. Collapsed folders can only be a drop *target*, never a drop *after* target. In `resolvePlacement` (`apps/desktop/src/app/chat/composer/context-menu.tsx:262`), a collapsed folder always resolves to `inside` — the `before` branch is unreachable for collapsed rows, so there is no way to drag a sibling directly above a collapsed folder; the user must expand it first. This is clearly a deliberate design choice ("children are hidden, so nest is the intent"), but it's a real usability gap: reordering a node above a collapsed folder (a common action) silently becomes a nest. Consider supporting `before` on collapsed folders (drop on the upper edge) or at least documenting the limitation in the UI copy.

3. Minor robustness note on the DnD drop math: `placeNode`'s `after`/`inside`(expanded) `insertAt` correctly recomputes `over`'s descendants against `rest` (the moved block already removed), so index math is right. Worth a regression test for the specific case of moving a node *forward* across a folder boundary where the moved block originally sat before `over` — that's the trickiest ordering path and the current suite doesn't appear to exercise it explicitly.

The persistence/seeding story is solid: `shouldSeed` is derived from the raw persisted payload (so a valid emptied list stays empty), and the `ensureSeeded()` call site is well tested.
