This PR adds Phase 0 "epic orchestration" infrastructure: durable, append-only epic state primitives (fenced leases, content-addressed evidence, chained receipts, integrity validation) in `hermes_cli/epic_state.py`, shadow-only orchestration profiles in `hermes_cli/epic_profiles.py`, an exact `tools.enabled_toolsets` profile pin that is propagated through CLI, gateway, coding context, and the Desktop hermes-bots plugin, plus a new protected `artifact_read` toolset. The wiring is defensive and fail-closed throughout; overall it is a coherent, well-tested change. A few observations:

1. **Delegated-child reads of a legacy (pre-Phase-0) board hard-fail, while writable reads recover.** `_connect_delegated_child_readonly` runs `_validate_schema_contract(conn, allow_missing=False)` (hermes_cli/kanban_db.py:2453) with no recovery branch. A board that has the Kanban sentinel but not the additive epic schema — e.g. restored from a pre-Phase-0 backup, or written by an older Hermes version before this PR — raises `IntegrityError` for every delegated-child read. The writable path in the same diff deliberately handles exactly this case (the `except EpicIntegrityError` → `schema_present = False` branch at kanban_db.py:2534), letting init add the missing objects. The asymmetry means the same legacy board is readable by the gateway but unreadable by a `delegate_task` child. If that is intentional fail-closed posture, consider raising a more specific, clearer error than the generic contract-mismatch `IntegrityError`; otherwise a recovery branch (validate `allow_missing=True`, then require a non-delegated re-init) would close the gap.

2. **`create_shadow_profiles` is not self-cleaning on partial failure (minor).** `target.mkdir(mode=0o700)` (hermes_cli/epic_profiles.py:247) reserves the root before any child is written, and the manifest is only published last via `os.replace` (epic_profiles.py:297). The manifest-last ordering is good, but if any write between the `mkdir` and the manifest `os.replace` raises, the partially populated `target` root is left behind; a subsequent call then fails in `_assert_disposable_target` with `ShadowProfileConflict` because the target exists. A retry therefore can never succeed until a human removes the directory. Since the whole point of the staging-dir pattern is atomic publication, wrapping the body so a failed attempt cleans up the reserved root (or records an explicit "aborted" marker a later call can reclaim) would make re-runs self-healing.

3. **`model_tools.py` re-reads and re-parses config on every tool-definition build when `HERMES_KANBAN_TASK` is set (minor).** The `has_exact_profile_toolset_pin(load_config() or {})` probe (model_tools.py:435) runs inside `_compute_tool_definitions`, which is a hot path for dispatcher-owned workers. The result of the probe is stable for the life of a process (a pin does not change mid-turn), so a small module-level memo (invalidated on explicit reconfig) would avoid the config load + YAML parse on each invocation. This is minor and bounded, but it is measurable churn on long-running workers.

4. **Schema-contract semantic snapshot includes `pragma_index_xinfo` columns like `coll`/`key` that can vary across SQLite builds (minor, verify).** `_schema_semantics` (hermes_cli/epic_state.py:1132) digests `pragma_index_xinfo` output including `coll` and `key`. These can differ between SQLite versions/compilations for the same schema (e.g. default collation normalization). If that turns out to be the case in the wild, `_validate_schema_contract` would spuriously flag a healthy DB as mismatched on every open and force re-init. Worth a quick check against the SQLite versions Hermes actually ships with; if it is version-sensitive, restricting the semantic digest to the stable columns (`seqno`, `cid`, `name`, `desc`) would be safer.

Points 2–4 are minor; point 1 is the only one that changes observable behavior for a real (if narrow) class of boards. The lease/evidence/receipt invariants and the fail-closed toolset-pin propagation look sound.
