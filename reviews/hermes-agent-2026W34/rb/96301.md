This PR fixes a Kanban lifecycle race where a worker whose run reached a terminal state
(`done`, `blocked`, review, dependency wait, timeout/give-up) left its process tree alive and
lost its PID identity. It retains run-scoped claim/PID/start-fingerprint/boot-incarnation
identity until `cleanup_terminal_workers` proves the exact tree is gone, then releases the
claim with compare-and-swap guards, with identity-bound `SIGTERM → grace → SIGKILL` escalation
in `terminate_process_tree`. The identity-gated reaping and the compare-and-swap cleanup are
solid, and the test coverage (process-level, PID-reuse, reboot/incarnation, terminal-transition)
is unusually thorough. A few points:

1. `cli.py:1512` — `os._exit(0)` runs from the outer `finally` of `_finalize_single_query`
   (cli.py:1515) whenever a terminal kanban handoff is detected. `_notify_single_query_session_finalize`
   and `_run_cleanup` have no internal guard; if either raises, the exception is silently
   discarded and the process exits 0, hiding the failure from logs and any wrapper. The
   durable DB handoff is already committed so this is acceptable, but consider logging the
   original exception at ERROR level before the forced exit (and possibly preserving a
   non-zero exit code) so a cleanup failure isn't invisible.

2. `hermes_cli/kanban_db.py:8738` — the deferral in `cleanup_terminal_workers` is unbounded:
   a surviving-but-unverifiable worker (e.g. a legacy row with no boot-id/start fingerprint
   whose PID is still alive) gets a fresh `now + RECLAIM_DEFER_GRACE_SECONDS` every tick,
   with no retry cap, no escalation, and no operator-visible marker. The duplicate-spawn
   guarantee is sound, but there is no automatic recovery path — the claim is pinned until
   the process dies or a human intervenes. Consider bounding the number of defers and/or
   surfacing these rows in `hermes kanban tail` / dashboard serialization.

3. `hermes_cli/kanban_db.py:8524` — the `signal_fn` branch of `_terminate_reclaimed_worker`
   bypasses all identity verification and signals the PID unconditionally, diverging from the
   production path. It's a documented test hook so there's no production exposure today, but
   every caller that forwards `signal_fn` (`enforce_max_runtime`, `release_stale_claims`,
   `detect_stale_running`, `reclaim_task`) silently loses the "never signal a recycled PID"
   guarantee if the hook is ever wired into a real path. Worth a guard or a stronger comment
   so the identity checks can't be skipped accidentally; also confirm the identity-mismatch /
   unavailable branches are exercised by tests that do *not* stub `signal_fn`.

4. Minor — `hermes_cli/kanban_db.py:9857`: the start-time retry in `_set_worker_pid` is
   bounded at 4 × 20ms; if the fingerprint isn't readable in time (slow process table on
   Windows/macOS), a legacy-style `worker_start_time = None` row is persisted, which then
   routes into the held-forever path from point 2. Consider logging a warning when persisting
   `None` so these rows are visible.
