This PR keeps populated Desktop/TUI sessions resumable across a gateway reload: process-exit teardown (`tui_shutdown`) no longer ends an existing durable row, WS close codes 1001/1012 map to a "service restart" teardown that parks sessions instead of arming the orphan reap, and `delete_session` / `delete_session_if_empty` gain audit logging. The tests are thorough (unit + E2E for the keep-open path, the missing-row fallback, and the close-code mapping).

- Asymmetry for `close_on_disconnect` sessions on a service restart: the guard at `tui_gateway/server.py:1461` (`if end_reason != "ws_service_restart"`) only skips the orphan reap in the *detached* branch. The `close_on_disconnect` branch above it still calls `_close_session_by_id(sid, end_reason="ws_service_restart")` unconditionally, which ends that row with reason `ws_service_restart` — and `ws_service_restart` is in neither `_KEEP_OPEN_END_REASONS` nor `_RECOVERABLE_END_REASONS` (tui_gateway/server.py:959, hermes_state_common.py). So on the same 1012 restart a sidecar/dashboard session is hard-ended and non-resumable while a detached desktop session is parked. That may be intentional (close_on_disconnect opted in), but it's worth confirming, and a one-line comment on the branch would prevent a future reader from "fixing" the asymmetry wrongly.

- The keep-open path relies on process exit. On `ws_service_restart` the detached session is parked on `_detached_ws_transport` with no orphan reap armed, assuming atexit `_shutdown_sessions` soon fires `tui_shutdown` to persist and keep it open. If the backend does *not* exit (a transient client-side 1012, or a reload that keeps the process alive), the parked session lingers with no end stamp until the 6-hour TTL idle sweep reclaims it. Acceptable trade-off for resumability, but the reliance on exit (vs. e.g. a short grace-reap that rebinds on reconnect) is worth noting.
