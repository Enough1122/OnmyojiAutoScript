This PR converts a silent `except: pass` in `_finalize_session` (tui_gateway/server.py) into a logged warning when the final transcript persist fails, on the justified grounds that finalize is the sole persist path after a WS disconnect/restart and `AIAgent._persist_session` has no internal error handling, so the unflushed turn would be silently lost. The fix is minimal, correct, and well-motivated (verified rather than assumed). Two observations:

1. **The regression test's assertion is too loose to pin the failure being logged.** At tests/tui_gateway/test_finalize_session_persist.py:221 the test asserts any warning whose message contains `"persist"` or `"session"` — a very low bar that could pass on an unrelated warning emitted during session setup/teardown (e.g. a SessionDB or agent warning containing "session"), even if the actual persist failure was still swallowed. Tighter options: assert the specific message text (`"Final session persist failed"`), assert `exc_info` is populated on the matched record, or assert the record count/logger name (`tui_gateway.server`). As written, the test would go green if the fix were reverted but some other code path happened to log a session-related warning.

2. **The warning doesn't include the session key, which limits its diagnostic value in multi-session logs (minor).** `_finalize_session` has the `session` dict (with `session_key`) in scope, but the warning at tui_gateway/server.py:832-833 logs only the static text + traceback. Adding the session id (and `end_reason`) would let an operator correlate "unflushed turn may be lost" to the specific conversation in a busy gateway log, and is a one-line change.

Both points are minor — the fix itself is the right call and the analysis (no later retry, finalize is last) is accurate.
