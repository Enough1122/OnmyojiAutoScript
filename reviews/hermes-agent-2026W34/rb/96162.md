This PR enables the **New Group Chat** menu item whenever the full multi-source Bot roster contains at least two selectable (non-`ghost`) bots, instead of counting only `activeSourceRoster` (which excludes remote-source rows). The change is one line, matches the creation dialog's own selection rules, and fixes a real gating inconsistency for local-plus-remote Bot fleets. Two observations:

1. **The new test is a source-regex test, which the repo explicitly discourages.** `create-group-chat.test.mjs` asserts `assert.match(pluginSource, /disabled:\s*roster\.filter\(bot => !bot\?\.ghost\)\.length < 2/)` and `assert.doesNotMatch(pluginSource, /disabled:\s*activeSourceRoster\.length < 2/)`. This reads the plugin's *source text* and asserts its shape — the pattern the root AGENTS.md calls out as a hard antipattern ("Never read source code in tests": it passes when the wiring is subtly broken, fails on cosmetic refactors, and cannot run against a built artifact). I note the surrounding tests in this file are already source-contract tests (a pre-existing pattern in the hermes-bots suite, likely a pragmatic choice for testing a bundled file), so this is consistent with the local file — but a behavioral test (render `BotsPane`/the dropdown with a roster containing remote non-ghost bots and assert the item is not disabled) would be more robust and convention-aligned, and would catch a rename/refactor the regex test would miss.

2. **`roster.filter(...)` assumes `roster` is always an array (verify).** The old gate (`activeSourceRoster.length`) could tolerate a falsy value only if `activeSourceRoster` was always an array; the new expression calls `.filter` directly on `roster`. If `roster` can be `null`/`undefined` for a frame before the multi-source roster resolves (or if a source load error path leaves it unset), this throws during render and breaks the entire BotsPane rather than just disabling the item. If `roster` is guaranteed by the surrounding component to be an array (likely, since it feeds the dialog), this is moot — worth a `roster?.filter(...)` guard or a one-line confirmation either way.

The fix's logic is sound and the ghost-exclusion matches the dialog's selection behavior. Point 1 is the more substantive one (test quality/convention); point 2 is a quick robustness check.
