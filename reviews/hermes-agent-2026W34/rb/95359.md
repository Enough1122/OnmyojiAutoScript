This PR adds WebKit AutoFill suppression to the two Desktop composer surfaces (visible `contentEditable` editor + `ComposerPrimitive.Root` form) and ships two test files that assert the suppression attributes are present. The attribute changes themselves are sound: `data-1p-ignore` / `data-lpignore` are the standard password-manager opt-outs, and `autoComplete="off"` on the form root addresses Safari's form-level autofill default.

- The two new tests (`apps/desktop/src/app/chat/composer/autofill-suppression.test.ts`, `apps/desktop/src/app/chat/composer/safari-autofill-suppression.test.ts`) read the `.tsx` source text via `readFileSync` and assert on substrings/regex (e.g. `autofill-suppression.test.ts:15` `readComposerSource()`). This is the "Never read source code in tests" antipattern the repo explicitly bans — it fails on harmless formatting/refactors and never exercises runtime behavior. Consider a render-level test (assert the actual DOM attributes after rendering the composer) or extracting the suppression metadata into a small pure/DI-testable constant that both the component and a behavior test consume. The "static-analysis guard in the same category as an ESLint rule" framing is exactly the pattern the guidance calls out as a hard ban.

- Minor: in `autofill-suppression.test.ts:29` (and the sibling at line 39) the defensive branches call `new Error(...)` without `throw`. If an anchor disappears the function silently continues (e.g. `indexOf('onCompositionEnd=', -1)` clamps to 0) and the test fails in a confusing way (an empty/garbage slice) instead of reporting the missing anchor. These should `throw` or use `expect(...).fail()`.
