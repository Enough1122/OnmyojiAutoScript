This PR adds a generic outbound sent-text index (`gateway/sent_text_store.py`) and wires it into the Photon adapter so a reply to one of the assistant's own messages — including cron/background sends whose text never entered session history — gets its quoted text hydrated at inbound time, letting the gateway's existing `[Replying to: "..."]` prefix fire. The store is best-effort, bounded, profile-scoped via `get_hermes_home()`, and well unit-tested. The core concern below is a key-form mismatch that specifically undermines the standalone/cron path the PR is built around.

1. **Chat-id form mismatch defeats hydration for the exact cron scenario (#75131).** Outbound sends are recorded under the raw `chat_id`/`space_id` — `_remember_sent_message(space_id, message_id, text)` in `_sidecar_send` (plugins/platforms/photon/adapter.py:2630) and `_sent_record(chat_id, last_message_id, message)` in `_standalone_send` (adapter.py:2949) — while inbound hydration looks up under the raw `space.id` from the event (`_hydrated_reply_text` at adapter.py:2238, lookup at adapter.py:2265). For in-session replies both sides are the chat GUID, so those match. But the standalone path is driven by `PHOTON_HOME_CHANNEL`, which is the **bare E.164 phone** (`_env_enablement` seeds `home_channel.chat_id` from the env var), while inbound events carry `space.id` in the GUID form `any;-;+1555...`. The adapter already bridges this exact gap with `_normalize_chat_key` (adapter.py:2176, "the sidecar's resolveSpace treats them as the same space; normalize to the bare phone") for its in-memory maps, but the new store bypasses it. So a cron-delivered message is recorded under `+1555...:<msgid>` and the reply is looked up under `any;-;+1555...:<msgid>` → miss, and hydration silently no-ops on precisely the path this PR exists to fix. The tests dodge this by using the same string form (`+155****4567`) on both the record and lookup sides; a test that records under the bare phone and hydrates from a GUID `space.id` (or applies `_normalize_chat_key` on both sides of the store calls) would surface it. Applying `_normalize_chat_key` to both the record key and the lookup key before `record`/`lookup` is the minimal fix.

2. **"Tolerates concurrent writers" overstates what atomic `os.replace` buys (minor).** The read-modify-write cycle at sent_text_store.py:80 — read whole file, mutate, dump to `.tmp.<pid>`, `os.replace` — is atomic per publish and crash-safe, but two concurrent writers (the gateway process and a standalone cron subprocess both feed this same file) each replace the file with their own snapshot, so one writer's entries are silently dropped (last-writer-wins). For a best-effort index whose failure mode is "a reply isn't hydrated" that is acceptable, but the comment should say "tolerates crashes/partial writes," not concurrent writers; if true cross-process safety is wanted, a lock around the read-modify-write (or appending to a WAL-style file) would be needed.

3. **Plaintext message text at default file permissions, rewritten on every send (minor).** `$HERMES_HOME/state/sent_text_index.json` (sent_text_store.py:46) stores up to 1000 messages × up to 2000 chars of message content in plaintext with default umask (0644), with no explicit `chmod` and no in-memory cache — every outbound send rewrites the whole file and every inbound reply re-reads it. Message content is a sensitive class (the plugin already marks iMessage descriptions as PII-safe at adapter.py:2892), so a `0600` mode on the store file (matching `.env`) would be a cheap hardening step, and an in-process cache would avoid the per-message full-file rewrite on busy gateways. Both are minor given the store is bounded and best-effort.

Point 1 is the one that changes observable behavior for the headline use case; points 2–3 are hardening notes. The rest of the change — preserving the previously-dropped top-level reply fields, never overriding sidecar-recovered text, degrading silently on unknown targets, and the bounded/per-chat-scoped index — is sound and well tested.
