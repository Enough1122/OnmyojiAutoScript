This PR fixes a Slack native-streaming collision by keying `_active_streams` per turn `(chat_id, draft_id)` instead of per chat, so concurrent turns in one channel no longer seize each other's stream slot. It also adds anchor-based same-turn segment hand-off and content-based stream resolution for the final send, with focused tests that assert one stream per turn, per-turn finalization, and sibling survival. The root-cause analysis (cause C of #95430) is convincing and the tests are well designed. A few observations:

1. **The thread-anchor discrimination in `_seal_superseded_segment` only separates turns in *different* threads.** The same-turn hand-off recognizes a superseded stream by `other.get("thread_ts") == anchor` (plugins/platforms/slack/adapter.py:3337), and `thread_ts` is stamped from `reply_to_message_id`/`thread_id` at stream creation. That cleanly distinguishes two people in separate threads, which is the reported scenario — but two concurrent turns in the *same* thread (e.g. a background/scheduled turn and an interactive turn replying to the same parent) share the anchor. A `draft_id` bump in one then seals the sibling's live stream via the same code path, reproducing the split-answer symptom this PR exists to remove (just more narrowly than before). Since the seal is keyed on `(chat_id, draft_id)` + anchor, and draft_id is the only turn identity available here, there is no perfect discriminator — but it is worth a comment (or a guard that never seals a stream younger than some tiny age) acknowledging the same-thread residual case, since the docstring currently claims it cannot split a sibling.

2. **Per-turn keying removes the old single-slot self-limiting, with no reaper for abandoned turns.** Previously one slot per chat meant a crashed/interrupted turn's stream was naturally evicted by the next turn's start. Now an entry survives until `disconnect()` or a same-thread supersede — a turn that calls `startStream` but never reaches a matching finalize (agent interrupted, process killed mid-turn, or a final `send()` whose text fails the `startswith` prefix match) leaves a stale stream in `_active_streams` plus a live typing indicator indefinitely. The stream already stores `"started": time.time()` (adapter.py:3222) but it is never read. An age-based sweep (seal + evict streams older than a threshold, e.g. on each `send_draft`) would bound the map and clean up orphaned indicators without touching the concurrency fix. Low frequency, but the map is no longer self-bounding.

3. **`_find_stream_for_final` is inherently heuristic when one turn's streamed prefix nests inside another's (minor).** The longest-prefix rule (adapter.py:3367) is a good defense, but consider two concurrent same-thread turns where turn A streams `"The"` and turn B streams `"The answer"`, and A finalizes with `"The answer is 42"` — the final text starts with both prefixes, longest wins, so A's final is attributed to B's stream (sealed with A's text) while A's own stream dangles. This is strictly better than the old single-slot behavior and is a documented trade-off of content-based matching (`send()` carries no `draft_id`), so it is acceptable — but the same-thread case in point 1 makes this degeneracy reachable, and the two together are worth a comment so future maintainers know the heuristic's limits.

The change is a genuine improvement and the regression tests are the right shape. Points 1 and 2 are the most actionable; point 3 is a documented-limitation note.
